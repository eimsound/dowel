### 1.3 可以拉开差距的地方

1. 开源、可自托管的持久化协作（CRDT + 评论 + 评审）。
2. 类似 PR 的 schema 变更流程：分支 → 可视化 diff → 评审 → 合并后生成迁移。
3. 迁移安全：锁表风险、在线拆分（expand / contract）、不可逆操作提示、漂移检测。
4. 和代码仓库双向同步，迁移文件进 Git。
5. AI / MCP 不算差异化（erd-editor、ERD Online 已有），只是基本配置。

## 2. 实验：PGlite 作为影子库

环境：`@electric-sql/pglite` 0.5.16（内置 PostgreSQL 18.6），Node v26.13.0。

### 2.1 导入时由引擎归一化

DDL 在 PGlite 里执行后，从 `pg_catalog` 读出的是规范形式：`serial` → `integer` + `nextval('users_id_seq'::regclass)`；`varchar(255)` → `character varying(255)`；`'anon'` → `'anon'::text`；`check (age > 0)` → `CHECK ((age > 0))` 并自动命名；PG 18 还会把 NOT NULL 记成约束（如 `users_email_not_null`）。

意义：从 SQL 文本导入、从线上库导入共用同一套读取系统目录的代码；漂移检测时比较的两边都是引擎输出的形式，不会因写法不同而误报。

### 2.2 语义校验（语法正确，纯解析器发现不了）

外键指向非唯一列、外键类型不兼容、默认值类型不对、枚举默认值不在枚举里、生成列引用生成列、索引引用不存在的列，全部由引擎当场报错。

### 2.3 带样本数据试跑迁移

text 改 int 不写 USING、有 NULL 时加 NOT NULL、有重复值时加 UNIQUE、`lower(email)` 唯一索引冲突、删除被外键引用的列、枚举新值在同一事务里使用，全部被引擎拦下。

### 2.4 锁、重写整表、全表扫描由引擎报告

方法：在事务里执行一条 ALTER，查 `pg_locks`、对比 `relfilenode`（变了就是重写整表）、看 `pg_stat_xact_user_tables`（全表扫描），然后回滚。

| 语句                               | 锁                     | 重写整表 | 全表扫描 |
| ---------------------------------- | ---------------------- | -------- | -------- |
| `add column x text`                | AccessExclusive        | 否       | 否       |
| `add column ... int default 0`     | AccessExclusive        | 否       | —        |
| `add column ... default random()`  | AccessExclusive        | **是**   | —        |
| `varchar(50) → varchar(500)`       | AccessExclusive        | 否       | —        |
| `varchar(50) → varchar(20)`        | AccessExclusive        | **是**   | —        |
| `int → bigint`                     | AccessExclusive        | **是**   | —        |
| `set not null`                     | AccessExclusive        | 否       | **是**   |
| `add check (...)`                  | AccessExclusive        | 否       | **是**   |
| `add check (...) not valid`        | AccessExclusive        | 否       | 否       |
| `create index`                     | Share                  | 否       | —        |
| `add foreign key`                  | 两表 ShareRowExclusive | 否       | —        |
| 事务内 `create index concurrently` | 报错                   |          |          |

（`—` 表示未测。）引擎给出“拿什么锁、会不会重写或扫描”；“要多久”还需结合线上 `reltuples` / `pg_relation_size` 估算。

## 3. 实验：SQL 解析器

环境：`@polyglot-sql/sdk` 0.14.1、`node-sql-parser` 5.4.0、`pgsql-parser` 18.3.5，共 24 个 DDL 用例。“✓”表示解析成功且再输出成 SQL 后关键信息不丢。

|                  | polyglot                                   | node-sql-parser                 | pgsql-parser   |
| ---------------- | ------------------------------------------ | ------------------------------- | -------------- |
| 通过数           | 18/24                                      | 15/24                           | 13/13（仅 PG） |
| 浏览器体积       | 28MB，gzip 6.3MB（所有方言一个包）         | 每方言单独一个包，gzip 40～55KB | gzip 0.3MB     |
| 能否识别错误 SQL | **不能**（拼错关键字、多余逗号都返回成功） | 能                              | 能             |

polyglot 的具体问题：PG 的 `CREATE POLICY` 只能原样保留；MSSQL 建表时**带名字的默认值约束的名字没进语法树**；`EXEC sp_rename` 解析失败；SQLite 的 `STRICT`、`WITHOUT ROWID` 解析失败。项目创建于 2026-01，约 1k star，基本由一人维护。

node-sql-parser：PG 的 identity / 生成列 / 分区 / EXCLUDE / NULLS NOT DISTINCT / plpgsql 函数、MySQL 分区、MSSQL 建表都失败；SQLite 用例全部通过。

pgsql-parser：PG 官方解析器（libpg_query）编译成的 WASM，结果和 PG 完全一致。

sqlglot（Python，30.32.0）对照：DDL 解析成结构化数据很好用，但跨方言转换 DDL 的结果不能直接用（MySQL → PG 输出了 `UBIGINT`、丢了 `AUTO_INCREMENT`、保留了 `ENGINE=InnoDB`）。

## 5. 实验：迁移后的结构 vs 直接按新结构建出来的结构

环境同第 2 节（PGlite 0.5.16 / PG 18.6）。

做法：库 A 建旧结构后执行迁移；库 B 直接建新结构；从系统目录读出两边的列、约束、索引、序列，逐项比较。这正是闭环验证（Q6）要做的比较。

| 用例                                                          | 差异                                                                                                                   |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 改列名 `email → mail`（带 UNIQUE、CHECK、NOT NULL、索引）     | 5 处：约束名 `users_email_key` / `users_email_check` / `users_email_not_null`、索引名 `users_email_idx` **都不跟着改** |
| 改表名 `users → accounts`（serial、identity、PK、被 FK 引用） | 7 处：`users_pkey`、两个 `*_not_null`、两个序列名、`nextval('users_id_seq')` 都保留旧名                                |
| 加列 `b`（希望放在 a、c 之间）                                | 物理顺序不同（ADD COLUMN 永远追加到最后）                                                                              |
| 删列再加同名列                                                | 物理顺序不同（attnum 不复用）                                                                                          |

结论：

- **自动生成的名字不会跟着改名走。** 如果 IR 不记录这些名字，闭环验证必然失败；如果按名字比较又会把改名后的库当成“漂移”。
- **列的物理顺序无法通过普通 ALTER 控制**，闭环比较时不能比较顺序（除非重建表）。

PG 18 的 NOT NULL 约束可以 `ALTER TABLE … RENAME CONSTRAINT`（已验证）。

### 5.1 PG 自动命名规则

| 对象              | 规则                                                            | 例子                                      |
| ----------------- | --------------------------------------------------------------- | ----------------------------------------- |
| 主键              | `{表}_pkey`                                                     | `t_pkey`                                  |
| 唯一              | `{表}_{列1}_{列2}…_key`                                         | `t_a_b_key`                               |
| 外键              | `{表}_{列…}_fkey`                                               | `posts_uid_fkey`                          |
| CHECK             | 只引用一列：`{表}_{列}_check`；引用多列或不引用列：`{表}_check` | `t_a_check`、`t_check`                    |
| NOT NULL（PG 18） | `{表}_{列}_not_null`                                            |                                           |
| 普通索引          | `{表}_{列或表达式的函数名…}_idx`                                | `t_a_idx`、`t_lower_idx`、`t_a_lower_idx` |
| 序列              | `{表}_{列}_seq`                                                 |                                           |
| 重名              | 末尾加 1、2、3…                                                 | `t_a_idx1`、`t_a_check1`                  |
| 超长              | 总长截到 63 字节，**两段名字按比例各截一部分**，后缀保留        | `aaa…(27)_bbb…(26)_not_null`              |

规则是确定的，可以用纯 TS 复现；但“重名加数字”取决于创建顺序，只能在知道已有名字时算出来。另外，同一个 `CREATE TABLE` 里重复写两次 `unique(a)` 只会产生一个约束。

## 6. 实验：表达式归一化的稳定性，以及会话参数的影响

### 6.1 归一化是不动点

把用户写的表达式放进 CHECK / DEFAULT 执行，读出规范形式，再把规范形式放回去执行一次，比较两次结果：**18 个 CHECK 表达式、9 个默认值全部稳定**（`canon(canon(x)) == canon(x)`）。例如：

| 输入                 | 规范形式                     |
| -------------------- | ---------------------------- |
| `a in (1,2,3)`       | `(a = ANY (ARRAY[1, 2, 3]))` |
| `a between 1 and 10` | `((a >= 1) AND (a <= 10))`   |
| `b like 'x%'`        | `(b ~~ 'x%'::text)`          |
| `trim(b)`            | `TRIM(BOTH FROM b)`          |
| `m <> 'sad'`（枚举） | `(m <> 'sad'::mood)`         |
| `case when … end`    | 多行文本（带换行和缩进）     |

意义：比较两份结构时只需比较规范形式，不需要自己写表达式等价判断。

### 6.2 会话参数会改变规范形式，甚至改变语义

同一条 `check (ts > '2020-01-01 08:00' and d > '01/02/2020' and iv < '1 day 2 hours')`：

| 会话参数                  | 读出的规范形式（节选）                                                       | 影响                               |
| ------------------------- | ---------------------------------------------------------------------------- | ---------------------------------- |
| `TimeZone=UTC`            | `'2020-01-01 08:00:00+00'`                                                   |                                    |
| `TimeZone=Asia/Shanghai`  | `'2020-01-01 08:00:00+08'`                                                   | **语义变了**：存进去的是另一个时刻 |
| `DateStyle='ISO, MDY'`    | `'2020-01-02'::date`                                                         |                                    |
| `DateStyle='SQL, DMY'`    | `'01/02/2020'`，实际是 2 月 1 日                                             | **语义变了**                       |
| `IntervalStyle=iso_8601`  | `'P1DT2H'`                                                                   | 只影响文本                         |
| `search_path=app, public` | `nextval('t_id_seq')`（`search_path=public` 时是 `nextval('app.t_id_seq')`） | 只影响文本，但会造成误报           |

结论：

- 影子库会话必须固定这些参数，否则同一个 IR 在不同环境里归一化结果不同。
- 规范形式里的字面量是**自带完整信息的**（ISO 日期、带时区偏移的时间戳），在任何会话参数下重新执行都得到同样的值。所以**迁移 SQL 应输出规范形式，而不是用户的原文**。
- `search_path` 设为空时，所有非 `pg_catalog` 的名字都会带 schema 前缀（`pg_dump` 也是这么做的）。

## 7. 实验：Yjs 映射方案

> 后来决定不用 Yjs（见第 8 节）。本节数据保留作参考，其中“对象扁平存放”“按属性粒度修改”“顺序用排序键”的结论与同步方案无关，仍然适用。

yjs 13.6.33。

| 场景                                                                | 结果                                       |
| ------------------------------------------------------------------- | ------------------------------------------ |
| A 删表，B 同时给这张表加列 —— **嵌套**（表的 Y.Map 里套列的 Y.Map） | B 加的列随表一起消失，**没有任何痕迹**     |
| 同上 —— **扁平**（顶层一个 Map 按 ID 存所有对象，列记录 `parent`）  | 合并后留下孤儿列，可以检测出来交给人处理   |
| 同一张表，A 改 c1 的名字，B 改 c2 的类型 —— 每个对象一个 Y.Map      | 两边的修改都保留                           |
| 同上，C 也改 c1 的名字                                              | 同一属性后写者胜，没有提示                 |
| 对象存成普通 JSON 值（整体替换）                                    | 一方的修改**整个丢失**                     |
| 两人同时移动同一列 —— `Y.Array` 删除再插入                          | 结果 `["d","a","d","b","c"]`，**出现重复** |
| 同上 —— 每列一个排序键（分数索引）                                  | 不重复，后写者胜                           |

规模（扁平方案，1000 张表 × 15 列 + 每表 2 个索引 + 1 个外键，共 1.9 万个对象，ID 用 36 字符的 UUID）：

| 项目                   | 实测                              |
| ---------------------- | --------------------------------- |
| 一次性构建             | 119ms                             |
| 编码后体积             | 4.2MB（同样内容的 JSON 是 3.2MB） |
| 从编码加载             | 146ms                             |
| 转成普通对象（toJSON） | 9ms                               |
| 再做 2 万次改名后      | 4.6MB，加载 183ms                 |

上千张表的量级下，文档体积和加载时间都可以接受；瓶颈更可能在画布渲染和自动布局（Q17）。

## 8. 调研：协作冲突的处理方式与同步组件

调研日期：2026-11-17。GitHub 数据来自 GitHub API。

### 8.1 其他产品怎么处理“并发修改导致语义错误”

| 类别                     | 例子                          | 做法                                                                                                                                                                                                         |
| ------------------------ | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 基于 Yjs 的富文本 / 笔记 | Tiptap、BlockNote、JupyterLab | 全部自动合并，不提示、不拒绝；合并后不合规的内容事后清理（y-prosemirror 直接删掉不合规节点，BlockNote 同步后补一次修正）                                                                                     |
| 表单 / 内容管理          | Contentstack、Directus        | 有人编辑某字段时把它**锁住**，避免冲突；锁由产品自己实现                                                                                                                                                     |
| 结构化数据工具           | Figma、tldraw、Linear         | **不用 CRDT 处理结构化数据**，由服务器决定顺序：Figma 每个文档一个服务器进程，同一属性以服务器最后收到的为准；tldraw 服务器权威，客户端类似 git rebase；Linear 结构化字段走服务器事务，只有长文本描述用 CRDT |

Yjs 自身的限制（来自 Yjs 论坛维护者的回答和 Hocuspocus 文档）：

- 没有办法拒绝单条修改；Hocuspocus 的 `beforeHandleMessage` 校验不通过只能断开连接。
- 合并后再发一个修正事务会破坏原子性，其他客户端可能短暂看到不合规的状态。
- 维护者建议：在服务端先把修改应用到副本上，校验通过再正式应用。

结论：Dowel 的数据是结构化对象，需要“后到的冲突修改被拒绝”，应采用服务器权威、按顺序处理的方案（已写入 02-consensus.md 4.2）。

### 8.3 Zero 的细节

来源：Zero 官方文档（mutators、when-to-use、self-host、connecting-to-postgres、status）。

- **状态**：2026-03 发布 1.0，官方称“正式可用、完整支持”；当前 1.12。
- **写入**：mutator 是普通 TS 函数，客户端先执行让界面立即更新，同时把“函数名 + 参数”发给服务端；服务端在 PG 事务里再执行一次（可以执行不同的、更严格的逻辑）。抛错 → 整个修改回滚，客户端撤回乐观修改。
- **部署**：除了应用和 PG，还要部署 `zero-cache` 容器（把 PG 复制成 SQLite 副本供查询，需要持久化卷）。PG 要求 15+ 且 `wal_level=logical`，占用一个复制槽。
- **数据模型**：数据必须是 PG 里的表，IR 对象要存成行。
- **官方写明的不适用场景**：不支持离线写入；不是 local-first；只支持 TS 客户端。
- **没有的功能**：在线状态、光标等临时数据需要另外实现（文档索引里没有相关章节）。
- **厂商风险**：同一家公司之前的 Replicache 被 Zero 取代，托管服务 Reflect 已于 2024-11 关闭。

### 8.4 自己写

对“单个服务器进程处理一个项目”的场景，服务器排序的核心并不复杂，有成熟的设计可参考（Figma 的公开文章、Replicache / Zero 的 mutator 模型、Logux 的 undo 协议）：

- 客户端：已确认状态 + 待确认修改队列；收到服务器广播后，在新状态上重新执行队列里的修改（rebase）；被拒绝的修改丢弃并提示。
- 服务器：每个项目在内存里保持一份当前状态；Node 单线程天然按顺序处理；每条修改校验后写入 PG 的操作日志表，定期写快照；断线重连时按序号补发。
- 操作函数放在 `@dowel/core`，客户端和服务器共用。
- 难点在于扩展到多台服务器（需要把同一项目的连接路由到同一台），自托管单机不涉及。

## 9. 原型：自己写的服务器排序同步层

原型代码约 570 行（协议本身约 300 行，其余为模拟网络、场景和随机测试），未保留在仓库中；协议说明见 [04-ir-design.md](04-ir-design.md) 第 2 节。

模拟网络：虚拟时钟，每条消息随机延迟 1～30 个时间单位，同一条连接内保持顺序；断线时在途消息丢失，重连是新连接。

| 场景                                                                                          | 结果                                            |
| --------------------------------------------------------------------------------------------- | ----------------------------------------------- |

| 张三改 `age`，李四同时给 `email` 加 CHECK                                                     | ✅ 都成功                                       |

| 李四连发三个修改，第 1 个冲突                                                                 | ✅ 依赖它的第 2 个也被拒绝，无关的第 3 个成功   |
| 李四断线期间双方各自修改，重连                                                                | ✅ 补发后一致                                   |
| 修改已送达但确认丢失，重连后重发                                                              | ✅ 服务器去重，只生效一次                       |

### 9.2 随机测试

4 个客户端 × 400 步，随机执行：加列 / 改名 / 删列 / 设置 CHECK（列名从 5 个候选中随机选，刻意制造冲突）、打开编辑框（之后一半的修改基于较早的草稿）、断线 / 重连。结束后让所有客户端重连并送完所有消息，检查：

- 所有客户端的已确认状态和界面状态都与服务器一致，待确认队列为空；
- 服务器每次提交后都满足语义不变量：CHECK 只引用本表存在的列，同一张表内列名不重复。

| 轮次 | 断线概率 | 修改总数 | 本地直接报错 | 服务器接受 | 服务器拒绝 | 失败 |
| ---- | -------- | -------- | ------------ | ---------- | ---------- | ---- |
| 300  | 5%       | 10.2 万  | 6.4 万       | 2.6 万     | 1.2 万     | 0    |
| 3000 | 10%      | 102 万   | 63 万        | 26.7 万    | 12.3 万    | 0    |

（本地报错多，是因为随机修改经常不合法，例如改成已存在的列名。）

随机测试过程中发现并修正了两个协议漏洞，第一版原型的场景测试都没有暴露出来：

1. **重连后、收到服务器回复前就发送新修改** → 新修改先于积压的旧修改到达，顺序被打乱。修正：收到 welcome 前只入队不发送。
2. **新客户端还没收到快照就断线，重连后收到快照** → 客户端靠“收到自己修改的 commit”清理队列，快照里没有这些 commit，修改永远卡在队列里（300 轮中 13 轮出现）。修正：快照带上该客户端的 `lastProcessed`（Replicache 也是这样做的）。

结论：服务器排序方案的核心逻辑约 300 行即可实现，语义符合“先到先得、后到冲突者被拒绝”；断线重连的边界情况必须靠随机测试覆盖。
