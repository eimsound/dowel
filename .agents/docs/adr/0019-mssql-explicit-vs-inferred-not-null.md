# SQL Server 持久化计算列：显式 NOT NULL 与引擎推断的非空分开存

2026-11-28 决定（[Issue #161](https://github.com/eimsound/dowel/issues/161)，来源 PR #157；部分修订 [ADR 0016](0016-on-demand-shadow-normalization.md) 决定 5）。

## 背景

SQL Server 按表达式推断持久化计算列是否可空：`cp AS ([code]) PERSISTED` 在 `code` 为 NOT NULL 时读回 `is_nullable = 0`。模型原先只有一个 `notNull`，影子库规范化把推断结果写回 `notNull`，规划器又把 `notNull: true` 渲染成 `PERSISTED NOT NULL`。于是“用户写的 NOT NULL”和“引擎推断出来的非空”混在一起：`code` 改回可空后，迁移仍带着用户从没写过的 `NOT NULL`，目标库插不进 `code` 为 NULL 的行。

实测（SQL Server 2022）：`sys.columns.is_nullable`、`COLUMNPROPERTY(…, 'AllowsNull')`、`sys.computed_columns` 的所有列，对 `AS ([code]) PERSISTED` 与 `AS ([code]) PERSISTED NOT NULL` 完全一样，也没有对应的约束对象。系统目录分不出两者。

## 决定

1. **两个字段**：`notNull` 只表示用户显式声明的 `PERSISTED NOT NULL`，生成 DDL 只看它；`ext.mssql.inferredNotNull` 表示引擎从表达式推断为非空，只由影子库规范化写回，从不渲染进 DDL，写入入口（`addColumn`、`setColumnExt`、MCP 宏）忽略调用方传入的值。普通列、非持久化计算列不用这个字段。
2. **有效可空性** = `notNull || inferredNotNull`。规划器按它比较（显式与推断互换、有效值不变时不生成迁移），执行读回校验复用规划器，因此同样按它严格比较；不加任何容忍。主键校验也按有效可空性。
3. **规范化怎么算推断值**：保证推断结果不依赖影子库的构建路径（从零建库或从基线增量迁移）。读回已可空时推断值必为 false；读回非空时，只有当该列在本次构建中确定以非显式从零新建（整库从零建或所在表不在基线中）才直接取读回值，其余情形（`next` 为显式声明，或所在表已存在于基线中、增量迁移后物理列可能保留基线的显式 `NOT NULL`）均在影子库同表临时加一个同表达式的非持久化计算列，读它的 `is_nullable` 再删掉（实测 27 个表达式，持久化与非持久化计算列的推断结果一致）。推断与显式无关，显式 `notNull` 永不被改写。
4. **导入与拉取**：系统目录分不出显式与推断，读结构时先一律记成推断（`notNull: false` + `inferredNotNull: true`），再按下面的规则拆分（`apps/server/src/mssql-nullability.ts`）。
   - **主键成员**：一律记成显式 `notNull: true`，不探测（见决定 7）。
   - **其余读回非空的持久化计算列**：在影子库里按模型建库（这些列先按显式 `NOT NULL` 建，引用它们的约束才建得出来），再用决定 3 的临时列探测表达式本身的推断——推断为可空记成显式，推断为非空记成推断。模型里没有这样的列时不连影子库。
   - **没有可用的影子库**（没有配置、生产环境不允许同实例、连不上，或影子库里建不出模型）：不拦下导入 / 拉取，这些列全部记成显式，并在结果里列出受影响的列（向导完成页、拉取弹窗的完成态），用户在影子库可用后可以自行取消勾选。
   - 覆盖范围：向导「从已有数据库」（冻结基线之前拆分，与基线验证共用同一个影子库句柄）；环境页「保留线上的修改」只拆分不能从工作副本沿用的列（`alignMssqlImportedLive` 按 ID 找不到同一列、表达式变了或有效可空性不一致），差异预览照旧按有效可空性比较，拆分在确认覆盖、写入工作副本之前完成。
   - 不用拆分的路径：漂移检查、标记核对、执行读回（只比较、不写模型，沿用参考模型的拆分即可）；接手、接入领先版本（用版本模型）；向导「SQL」与项目内导入 SQL（影子库导入时已经探测：表达式本身推断为可空、读回却非空的还原成显式）。
5. **待规范化判定**（`derive-pending.ts`）：在 #145 的“所在表按列名对齐的普通列 notNull 变了”之外，列自己的推断值相对基线变了也算；列自己的显式 `notNull` 变了仍算（推断与它无关，但旧规则写回的存量基线没有 `inferredNotNull`，借此补算）。稳态仍是 0 影子库 I/O。
6. **界面**：“非空”复选框只绑显式 `notNull`；只由推断得出非空时不勾选，下方显示只读提示“由表达式推断为非空……”，列表 `NN` 按有效值显示，推断的用虚线框区分。
7. **主键例外**：建主键（以及导入 / 拉取时的主键成员）视为对主键列显式声明非空。在只由推断得出非空的计算列上建主键，会把它设为显式 `notNull: true`；之后被引用列改成可空，主键列仍保持非空约束，不会因推断变化而失去主键的前提。

## Considered Options

- **一个字段，读回比较时把推断值当等价**：改动小，但规划器仍会把写回的推断值渲染成 NOT NULL，问题原样存在；而且是 ADR 0017 明确拒绝的“比较时容忍”。
- **规范化不写回**：模型 `notNull: false`、读回非空，读回校验报不一致，推断非空的列永远执行不了。
- **导入时用 `sys.dm_exec_describe_first_result_set` 在目标库上只读推断表达式**（已否决）：不需要影子库，但它推断的是查询结果集的可空性，不是计算列自己的推断路径，两者一致只是实测结论；负责人不接受这种不一致的风险，任何路径（包括兜底）都不使用它。
- **导入时一律记成推断**：实现最简单，但“显式声明在可空表达式上”的列（主键常见）会在下一次规范化时被写回为可空，迁移把它重建成可空，作主键时整个分支无法规范化。
- **没有影子库时拦下导入 / 拉取**：结果最准确，但生产环境默认不允许同实例影子库，会让“从生产库新建项目”变得不可用；改为按显式记录并提示，最坏情况只是多了一个用户可以取消的 `NOT NULL`。

## 影响

- 存量数据（不考虑兼容，同 ADR 0017 原则）：旧规则写回过 `notNull: true` 的列，模型分不出是不是用户写的，按显式处理——DDL 与以前相同，仍会带 NOT NULL；用户取消勾选后会触发一次规范化，补上推断值，有效值不变时不生成迁移。
- 从已有数据库导入 / 拉取会多一次影子库访问（只在有读回非空、非主键的持久化计算列时）。没有可用的影子库时这些列按显式记录：DDL 带 `NOT NULL`、有效可空性与线上一致，不会生成迁移；代价只是之后被引用列改成可空时这列仍保持非空，用户在影子库可用后可以取消勾选改由推断。
- 主键成员一律显式（决定 7），导入的 v0 基线在影子库里总能建出来。
- `ext.mssql` 只被 SQL Server 方言读取，其他方言即使带着这个键也不理会；粘贴不跨方言，同方言粘贴的列不带推断值，由下一次规范化算出。
