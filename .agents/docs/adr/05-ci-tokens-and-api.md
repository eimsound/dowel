# CI 令牌与 API：哈希存储、`/api/ci` 隔离、不能回滚、同步执行契约、三层取与的创建规则

- **状态**：已生效（Implemented）
- **领域 / 范围**：项目级 CI 令牌（`dwl_`）的存储、能力边界与执行契约；CI 只读接口；“谁能创建 CI 令牌”的规则与它带来的权限传导
- **合并自**：原 ADR 0009（2026-11-20，P6，T1 / T3；2026-11-21 修订）、原 ADR 0010（2026-11-20，P6，T2；2026-11-26 / 2026-11-27 补充）；相关 PR：#204（`verifiedOn` / `engineVersion` / `verifiedHere`）；用户文档 `docs/{zh,en}/api.md`
- **重审触发条件**：出现真实的 CI 令牌越权执行事件，或用户明确要求 CI 令牌也受环境 `whoCanExecute` 约束（第 10 节）；需要 CI 异步执行 / 流式进度

## 1. 令牌用 SHA-256 存储，不用慢哈希、不绑 `DOWEL_SECRET`

令牌格式为 `dwl_` + 32 字节密码学随机数的 base64url（256 位熵）；列表辨认用的前缀取前 12 个字符（`dwl_` + 8 字符，只占 48 位，剩余 208 位熵）。库里只存 SHA-256。

- 高熵随机令牌不存在离线词典爆破风险，不需要 Argon2 / scrypt；每个 API 请求都要校验令牌，慢哈希只会引入额外的 CPU 放大面。
- 不与 `DOWEL_SECRET` 做 HMAC：会话令牌与邀请令牌已统一用 SHA-256；若 CI 令牌依赖 `DOWEL_SECRET`，轮换实例加密密钥会让所有流水线里的长期令牌瞬间失效，运维成本过高。拿到哈希值无法反推 256 位随机明文。

## 2. 令牌只能访问 `/api/ci/…`

在路由最前面统一拦截：携带 `Authorization: Bearer dwl_…` 访问 `/api/ci/…` 之外的任何接口一律 `403 forbidden`，不回落到会话 Cookie。这在结构上锁死了“只读 + 向前执行”的能力边界：编辑模型、发布、改策略、改连接串、标记为已执行、认领、接手、令牌管理本身都不可能被令牌调用，并由权限矩阵测试遍历全部路由表穷举断言。非 `dwl_` 的 Bearer 头在普通路由上放行（例如反向代理注入的 OIDC 令牌），在 `/api/ci/*` 里按 `token_invalid` 拒绝。MCP 令牌（`dwm_`）的对称隔离见 [06-mcp-and-canvas-editing.md](06-mcp-and-canvas-editing.md) 第 4 节；CI 接口的 OpenAPI 文档见同文第 6 节。

## 3. 令牌不能回滚

执行接口固定 `direction: 'up'`。目标版本早于环境当前版本时返回 `409 rollback_not_allowed`（`details.current` 标明当前版本）；环境停在已作废岔路上、到目标版本需要先回滚到最近公共祖先时返回 `409 switch_requires_web`，目标版本已作废时返回 `409 version_retired`（[02-version-chain-and-recovery.md](02-version-chain-and-recovery.md) 第 4 节）。回滚往往伴随 `DROP TABLE` / `DROP COLUMN`，应由人在界面上确认并经过审批流程或紧急执行，而不是由流水线在分支切换或误填旧版本号时静默触发。

## 4. 执行接口同步等待完成，错误码一对一映射 HTTP 状态

CI 最直接的交互是一次 HTTP POST 拿到最终结果和退出码，不需要在 shell 里解析 SSE 或自己写轮询。执行请求必须显式给出目标版本（`latest` / `vN` / `N`），支持 `dryRun`（做完全部检查、列出要执行的迁移、不写目标库）。错误码与 HTTP 状态一一映射：认证失败 `401`、策略拒绝 `403`、资源或归属不符 `404`（不区分“不存在”和“不属于这个令牌”，避免探测）、状态冲突 `409`（漂移、回滚被拒、缺少验证记录 `unverified`、上次执行停在中途、他实例认领等）、目标版本不存在或执行失败 `422`、等执行锁超时 `423`、限速 `429`、目标库不可达 `502`。

`409 unverified` 的 `details` 带目标库的数据库完整版本号 `engineVersion`（读不到为 `null`）与该版本已通过验证的完整版本号列表 `verifiedOn`，规则见 [07-normalization-and-verification.md](07-normalization-and-verification.md) 第 8 节；CI 令牌与紧急执行一样不绕过这道门禁。

## 5. 只读接口按开销拆清职责，不返回过期缓存

| 接口                               | 是否连目标库           | 返回                                                                                                                                                                                |
| ---------------------------------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/ci/token`                | 否                     | 令牌自检：所属项目、过期时间                                                                                                                                                        |
| `GET …/projects/:owner/:project`   | 否                     | 平台配置：项目、最新版本、各环境是否允许令牌执行；不返回缓存状态                                                                                                                    |
| `GET …/versions`                   | 否                     | 版本链；每个版本带 `verified`（通过过闭环验证且脚本之后未被人工修改）与 `verifiedOn`（通过验证的数据库完整版本号，与 Web 版本详情同一算法）                                         |
| `GET …/environments/:env`          | 是（只读历史与版本号） | 实时 `currentVersion` / `unfinished` / `pending`、目标库数据库完整版本号 `engineVersion`，以及每个版本相对当前版本的状态与 `verifiedHere`；同步平台缓存，不返回缓存漂移；受连接限速 |
| `POST …/environments/:env/drift`   | 是（读全库结构快照）   | 实时漂移检测，同时更新平台侧漂移状态；受连接限速                                                                                                                                    |
| `GET …/environments/:env/history`  | 是                     | 目标库最近 100 条迁移历史并同步平台缓存；受连接限速                                                                                                                                 |
| `POST …/environments/:env/execute` | 是                     | 同步执行或预演（第 4 节）                                                                                                                                                           |

**`verifiedHere`** 与执行前检查是同一条规则，CI 据此能预知 `409 unverified`：需要外部影子库的方言（PostgreSQL / MySQL / SQL Server），`verified` 且目标库完整版本号在 `verifiedOn` 里才为 `true`，读不到目标库版本号一律 `false`；SQLite 的影子库与目标库是同一个内置库，视为恒等，等于 `verified`。`verified` 本身不代表能执行到任一环境。

## 6. 等锁期间的并发保护与锁内复查

CI 执行与界面执行、执行申请共用环境锁与目标库项目锁；总等待时间（默认 30 秒，可在请求里调小）扣除等环境锁消耗后交给目标库项目锁。拿到环境锁之后、连接目标库之前复查令牌是否被吊销 / 过期、环境生效的 `allowTokens` 是否被关闭，并取最新的语句 / 锁等待超时，避免等锁窗口内的状态变化导致越权执行。

## 7. 通知范围：Webhook 覆盖全部环境，收件箱只通知生产环境

非生产环境在 CI 里高频执行，每次都发站内通知会淹没审批消息。所有环境都发 `token.executed` 组级 Webhook 事件（可按需订阅）；只有生产环境的令牌执行（成功或失败）才给项目管理员和当前审批流程里的审批人发站内通知。

## 8. 谁能创建 CI 令牌：三层逐层取与（AND），层内取或（OR）

实例、组、项目三层各可存一条可选规则 `{ roles, groups }`（未设置即继承）：

- **层内**：满足 `roles` 中任一项目角色（项目管理员 / 编辑者及以上），**或**满足 `groups` 中任一组条件（指定组的管理员或成员）即通过这一层；两个数组都为空表示这一层不允许任何人（实例管理员除外）。
- **跨层**：必须**同时满足**每一个已设置的层；三层都未设置时用默认规则“项目管理员”。实例管理员始终放行。

逐层取与在结构上保证下级只能在上级允许的集合里继续收窄、绝不可能放宽上级（与 [03-execution-governance.md](03-execution-governance.md) 第 1.2 节审批流程“只能追加”同构），不需要写入期的集合包含推理，并能自然表达“必须在运维组（实例层）且是本项目管理员（项目层）”这类企业约束。

## 9. 被允许创建令牌的人自动获得只读可见性

例如公司设一个独立的安全 / 流水线组专门签发和轮换 CI 令牌，成员不必逐个项目授权。为避免“可见性依赖创建资格、创建资格又依赖角色”的循环，角色计算分两步：先算不含令牌规则的**基础角色**，再用基础角色评估角色条件、用组成员关系评估组条件；基础角色为空、规则含组条件且满足时，有效角色为 `viewer`。

- 角色条件本来就要求基础角色非空，所以只有组条件会让原本不可见的用户获得可见性；规则里没有组条件时直接短路，无额外开销。
- 规则涉及的组成员同样进入审批 / 通知等受众计算；修改任一层的令牌创建规则后，在线 WebSocket 连接的角色即时刷新。

## 10. 权限传导边界

CI 执行只校验目标环境生效执行策略的 `allowTokens === true`（非生产默认开启、生产默认关闭），**不受**环境的 `whoCanExecute` 与审批流程约束。因此满足创建规则的成员——即使只通过组条件获得 `viewer`，或在界面上受 `whoCanExecute` / 审批约束——都能通过签发令牌间接获得范围内所有 `allowTokens = true` 环境的免审批**向前**执行权（不能回滚、不能改模型或环境配置；漂移、完整性、验证记录、超时等安全检查照常生效）。基于这一传导关系：

- “谁能创建 CI 令牌”默认仅限项目管理员，并三层取与防止下级放宽；
- 令牌规则配置、项目令牌管理页与用户文档都显式警示这条传导边界，提醒对需要强制 `whoCanExecute` 或审批的非生产环境关闭“允许 CI 令牌执行”，或收紧创建规则；
- 执行策略配置页在**非生产**那一套生效策略已收紧（谁能执行严于项目编辑者，或有任一审批环节）而 `allowTokens` 仍为 `true` 时显示提示条，有修改权限的人可一键在草稿里改为“不允许”；关掉令牌执行是收紧，不受上级锁定限制。生产那一套默认不允许，显式打开视为有意选择，不提示。**默认值与服务端语义不变**。

**重审触发条件**：维持现行做法。只有出现真实的越权执行事件，或用户明确要求 CI 令牌也受 `whoCanExecute` 约束时，才重新评估“要求令牌创建者本人满足目标环境的 `whoCanExecute`”。保留现行做法不是为了兼容旧数据（Dowel 尚未公开发布），而是避免每次收紧非生产环境的谁能执行 / 审批时，依赖 CI 自动部署的非生产流水线随之失效。

## 被否决的方案

- **慢哈希（Argon2 / scrypt）存令牌**：高熵随机令牌没有词典攻击面，只增加每个请求的 CPU 开销。
- **令牌 HMAC 绑定 `DOWEL_SECRET`**：轮换实例密钥会让所有流水线令牌失效。
- **令牌回落到会话 Cookie / 访问普通界面接口**：能力边界不再是结构性的，难以穷举验证。
- **允许令牌回滚**：高风险破坏性操作不应由流水线静默触发。
- **异步执行 + SSE / 轮询**：CI 脚本要自己处理流和循环，失败语义更难映射到退出码。
- **状态接口返回平台缓存的版本与漂移**：缓存可能过期，CI 据此做判断会出错；改为按开销拆分的实时接口。
- **创建规则与执行策略一样对标量字段做偏序比较**：“角色 ∪ 多个组”的集合包含关系没有静态全序（实例层要求“安全组成员”、组层想写“项目管理员”时是交集关系而非子集关系）。
- **用有效角色计算创建资格**：有效角色又依赖创建资格，形成循环。
- **CI 令牌也受 `whoCanExecute` / 审批约束**：见第 10 节的重审触发条件。
