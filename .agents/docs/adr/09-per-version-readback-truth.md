# 按数据库完整版本号分别记录闭环读回差异，以各版本真实结构为真相

## 背景

当前工作副本规范化与发布验证运行在两种选影粒度上：按需规范化只用**一个**影子库（最低已知版本组里第一个可用的，见 07 第 1 节），产出单份基准模型；发布与重新验证在项目环境的**每一个**数据库完整版本号上做闭环验证与严格读回核对（07 第 6～8 节），执行与漂移检查复用同一个严格比较。

一个版本只冻结一份模型（02 第 1 节）。当同一项目下有不同版本的环境，而这些数据库版本对同一表达式、视图、函数或约束的系统目录反解析写法不同时，单一模型无法同时等于两种读回文本：

1. 非规范化那一侧会稳定触发 `readback_mismatch`；现有提示引导用户“按数据库读回修改模型后重试”，照改后下次发布又会被另一侧打回，形成死循环。
2. 项目原地完成全量大版本升级后，工作副本里未改动的旧对象仍带旧版本的规范写法；强求“规范化同版本零差异”或全量重刷，都会卡死后续发布或为未改动的历史对象制造多余的重建迁移。

## 原则

- **以真相为主，按完整版本号分别记录差异。** 各数据库完整版本在影子库闭环执行后实测读回的结构就是该版本的真实结构。不靠读回层的模糊或纯格式容忍抹平差异，也不强求不同版本的反解析文本一致，而是在单一基准模型之上按数据库完整版本号分别记录增量差异。
- **不考虑旧数据兼容**（同 07）。平台库与目标库历史表结构直接演进，不做存量迁移。

## 决定

1. **验证门禁与读回真相记录**
   - **外部影子库方言**（PostgreSQL、MySQL、SQL Server）：以影子库闭环一致性（升级与回滚两个方向的闭环比较都为空）作为验证通过的门禁，**不设硬编码的“可差异字段白名单”**。通过后按冻结的 scope 读回升级后与回滚后的真实结构、对齐对象 ID，把相对基准模型的全部差异如实记录为该完整版本号的增量差异；无差异不写记录。
   - **SQLite**：只有一个内置内存影子库，不存在跨版本反解析分歧，继续严格零差异读回核对。
   - **写入层与规范化防线不变**：07 第 9 节的写入层规范化继续由各写入入口与测试（断言同版本零差异）守门；闭环验证期间，**只有与规范化所用影子库相同的完整版本号**仍产生非空读回差异时记服务端告警日志便于排查，不阻断跨版本或大版本升级后的发布。

2. **平台库独立增量表 `version_engine_diffs`**
   - 主键 `(version_id, engine_version)`，存相对基准模型的增量差异（`diff`）与记录时间（`recorded_at`），外键关联 `versions(id) ON DELETE CASCADE`；稀疏存储，无差异不存行。
   - **零侵入**：记录或更新差异绝不改写已冻结的版本模型，也不改变版本验证记录的通过状态。
   - **双向采集**：闭环验证 `vN`（`from → to`）在完整版本号 `E` 上通过时，升级方向读回相对 `to` 的差异写入 `(vN, E)`；回滚方向读回相对父版本 `from` 的差异，若 `(from, E)` 已有记录则核对一致，若没有（例如先在 PG 15 发布 `v1`、新增 PG 18 后直接发布 `v2`）就按需写入 `(from, E)`——**绝不**因此把 `from` 标记为在 `E` 上已验证，父版本自身的脚本仍须专门重新验证通过才能执行。
   - 链上最新且尚未在任何环境执行过的版本，在人工编辑冻结脚本、清空验证记录时，同步清理它的差异记录。

3. **统一的有效模型与全链路消费**
   - 纯函数 `effectiveModel(version, engineVersion)`：把该版本在该完整版本号上的差异叠加到基准模型；没有差异记录时就是基准模型。
   - **执行读回校验、漂移检测、标记为已执行、修复脚本**统一改用“目标库完整版本号的有效模型”与目标库实测快照做严格比较，不引入任何近似或格式容忍。
   - **缺少当前版本差异记录时回退**：目标库处于尚未采集过差异的完整版本号（例如刚原地升级、尚未重新验证）时，漂移检测、标记与修复脚本回退用基准模型比较，绝不在只读或标记路径上自动连接影子库或猜测；因此报出漂移或标记不一致、且该版本尚未在该完整版本号上验证通过时，提示用户“若目标库刚升级过数据库版本，请先在版本详情页对该版本重新验证以采集新版本的读回真相”。

4. **目标库迁移历史存基准 + 本库差异**（修订 02 第 2 节）
   - 四种方言的目标库版本表 `dowel.versions`（PostgreSQL / SQL Server）与 `dowel_versions`（MySQL / SQLite）直接新增 `engine_version`（写入时的目标库完整版本号）与 `version_diff`（该版本号对应的增量差异）两列（版本表没有只追加触发器；按不考虑旧数据原则直接调整建表定义）。
   - 模型列在所有目标库继续统一存**基准模型**；差异结构与平台库一致，无差异存 `null`；指纹继续存该库实测快照哈希。
   - **多环境接手合并无冲突**：合并时照常严格校验各来源同名版本的基准模型、校验和、升级 / 回滚步骤、scope 完全一致，保留防篡改能力；各环境各自记录的（完整版本号，差异）按版本汇总，互不冲突。

5. **接手与接入领先环境按每个完整版本号验证**（修订 02 第 5 节）
   - 恢复时的验证从单个影子库升级为按参与环境中每个不同的数据库完整版本号逐组挑选可用影子库做闭环验证（与发布、重新验证同一套分组），把实测差异写入新平台库的差异表（并汇总目标库历史自带的差异）。
   - 某些参与环境的完整版本号暂缺可用影子库时，对应环境照常标为未覆盖，配置同版本影子库并重新验证后补采；在此之前，只要目标库未被手工篡改，它自己记录的指纹仍能保证日常漂移检查不误报。

6. **画布按需规范化保持单影子库，补齐 SQL Server 最低主版本选影**
   - 规范化的职责是为工作副本产出一份基准写法，保持单影子库选择（07 第 1 节）不变，不为规范化引入多影子库并发连接。
   - 补齐 SQL Server 的版本分组与按最低主版本（2019 < 2022 < 2025）优先排序，使其选影行为与 PostgreSQL、MySQL 一致。

7. **界面透明展示“数据库版本差异”**
   - 版本详情页与迁移预览验证报告中，某个完整版本号闭环验证通过且记录了非空差异时，以中性、直白的“数据库版本差异”展示（如“有 N 处数据库版本差异”），可展开对照对象、属性、基准模型值与该版本实测读回值；不报错、不阻断发布。

8. **增量差异格式与规划器边界**
   - 增量差异按稳定对象 ID 记录相对基准模型发生变化的字段值（及必要的对象级差异），平台库与目标库共用同一结构。
   - 迁移规划、版本差异与画布编辑始终基于**基准模型**计算，确保跨版本验证或全量原地大版本升级后，未发生业务变更的历史对象不会产生多余的 `DROP / ADD` 迁移步骤。

## 被否决的方案

- **坚持单一模型同源一致（跨版本回显分歧时在发布阶段拒发并提示改写）**：保住了单模型的简单性，但对引擎内部反解析规则改版导致、用户无法通过改写 SQL 消除的差异，会彻底阻断多版本混部窗口的发布与旧版本重检。
- **在读回比较中恢复纯格式或词法容忍**：直接破坏 07 的核心原则（PR #162 刚移除 MySQL 纯格式容忍），会重新掩盖规范化漏刷与写入层缺陷。
- **硬编码“可差异派生字段白名单” + 要求规范化同版本零差异**：白名单难以覆盖跨版本系统目录演进（如 PG 17 / 18 的非显式 `NOT NULL`、域约束）；全部环境原地升级后，工作副本中未改动的旧对象仍带旧版写法，会卡死下一次发布。
- **按每个完整版本号保存一份完整模型快照**：查询时无需合成，但多版本项目的平台库存储成倍膨胀，也无法直接告诉用户“具体差了哪几处”。
- **不建独立表，把双向覆写塞进版本验证记录，或发布时反向更新父版本的验证记录**：要么数据结构别扭，要么打破“发布新版本不修改已冻结父版本行”的边界，并发锁与半状态处理都不如独立表干净。
- **目标库版本表的模型列各自直接存本库的有效模型**：单看一个目标库直观，但多环境接手合并无法分辨“合法的跨版本差异”与“历史模型被篡改”。
- **漂移检测 / 标记缺差异记录时现场连影子库采集**：能消除原地升级后首次检查的临时提示，但打破漂移检测“不连影子库、不写版本数据”的只读边界，拖慢状态查询并引入影子库限速复杂度。

## 影响与边界

- **零额外存储膨胀**：单版本项目或跨版本回显完全一致的对象不产生差异行，目标库差异列为 `null`。
- **多版本混部与大版本升级畅通**：跨大版本混部及单环境原地大版本升级后发布的迁移，只要闭环一致即可发布，并在各版本目标库上以对应的有效模型通过执行读回校验。
- **接手黄金基线不变量（#123）保持有效**：工作副本与黄金基线仍统一围绕基准模型；接手与接入领先环境通过多版本闭环验证保证基准模型与冻结脚本的严格一致。
- **范围外**：不改变发布流水线的顺序（规范化 → 验证 → 冻结）、不改变“按目标库完整版本号把关执行”的门禁（07 第 8 节），也不改变 SQLite 的严格零差异核对。
