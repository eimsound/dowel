# 执行申请绑定“起止版本 + 迁移校验和 + 环境指纹”，失效在三处判定，最终以目标库历史为准

2026-11-20 决定（P5b，E3）。审批规则见 [ADR 0006](0006-approval-snapshot-and-execution-right.md)。实现：`apps/server/src/requests.ts` 的 `bindingProblem`、`packages/executor` 的 `ExecuteOptions.expect`。

**绑定什么。** 提交前先跑一次预演（和直接执行前完全相同的检查），预演的计划就是申请绑定的内容：起始版本（提交时环境的当前版本，可以为空）、目标版本和方向、要执行的迁移列表（版本、方向、顺序）和每个版本的校验和；另外记下提交时的“生产”标记、连接串的指纹和审批流程快照。审批人看到的就是这些，批准的也只是这些。

**绑定预演用的那一份校验和**（第一轮审查）：预演在锁外，写入申请在锁内；预演计划里带着每个迁移在预演时的校验和，锁内读到的和它不一样（预演之后脚本被改了）就 409、让用户重新预演，而不是绑定锁内新读到的、没预演过的那份。

**连接串指纹是带密钥的 HMAC**（第一轮审查）：连接串里有密码，无盐 SHA-256 可以离线撞出来；改用 `DOWEL_SECRET` 派生密钥（再按用途派生）的 HMAC-SHA256（`secrets.ts` 的 `keyedDigest`）。DOWEL_SECRET 换了、解不开连接串时用密文的摘要（密文的摘要不泄露任何东西，之后再改连接串密文一定会变）。指纹由代码在写入时计算，表里从一开始就是这个格式（P5b 合入前改的，没有需要迁移的旧数据）。

**失效条件（`bindingProblem`）。** 有效期过了 → 过期；环境当前版本 ≠ 起始版本、检测到漂移、“生产”标记变了、连接串变了、目标版本或绑定的任一版本不存在、任一版本的校验和变了、生效审批流程变严 → 失效。每个失效都有给人看的原因（例如“环境的当前版本变了：提交时是 v1，现在是 v2”）。（2026-11-21 修订：原前置环境功能已移除。）

**在哪里判定。** ① 审批 / 驳回 / 执行前，在执行策略锁里重新读环境、版本、策略后判定，失效就在同一个事务里把申请转为终态（提交），请求返回 409；② 定时检查（每 30 秒，全部还没结束的**普通**申请——失败 / 中断的紧急执行记录是终态，不再检查，第二轮审查）和“按范围的快速检查”（执行 / 标记结束、漂移检查、读历史同步、改脚本、改环境、改策略、转组的路由**显式**带上受影响的环境 / 项目 / 组排一次，合并成一轮；检查进行中又来的会再跑一轮，不会丢）把失效 / 过期的申请转为终态并通知申请人——这只为及时通知，正确性不依赖它。检查分两步：先在锁外只读地找出绑定已经不成立的申请（多数时候一个都没有，不拿全局锁），再在锁内重新读、重新判断、条件更新；详情页打开时的检查同样如此（第一轮审查：原来每次都拿全局写锁）；③ 执行时，执行器在**目标库的项目锁**里、写任何东西之前，按目标库自己的历史核对当前版本、算出的迁移列表和校验和（`ExecuteOptions.expect`），不一致就抛 `request_stale`，什么都不写，申请转为失效。

**为什么必须有第 ③ 处。** ①② 用的是平台库里的缓存（环境当前版本、漂移结果），缓存可能落后于目标库：别的实例执行过、有人绕过 Dowel 写了历史、上一次同步失败。目标库历史才是事实来源（ADR 0003），所以最终的判定放在执行器里、目标库锁内。它也覆盖了并发：审批和直接执行同时发生时，两者都要拿环境锁和目标库项目锁，后执行的那个看到的当前版本已经变了——直接执行变成空操作或按新起点执行，申请则 `request_stale` 失效，目标库只会被执行一次。库已经在目标版本（别人先执行到了）也算不一致：不能把“什么都没做”当作申请执行成功。

**为什么失效而不是“重新绑定”。** 环境状态变了以后，原来的批准对应的是另一组迁移（起点不同，要执行的迁移就不同），自动换绑等于替审批人批准了他没看过的东西。重新提交的成本是再走一遍审批，这正是审批要的效果。

**执行失败后的状态。** 执行失败（脚本报错、锁等待超时……）记为“执行失败”，不是终态：绑定仍然成立时（事务整体回滚、或者非事务步骤停在断点、当前版本没变）可以重试，断点续跑语义不变；执行了一部分、当前版本已经变了的，下一次检查转为失效。服务重启时“执行中”的申请记为执行失败（单进程部署下它一定已经中断；结果以目标库历史为准）。这一步在开始接受连接**之前**、在锁内做，并且只条件更新 `updated_at` 早于本进程启动时间、仍是“执行中”的行——不会把本进程刚开始的真实执行记成失败（第一轮审查）；被记为中断（`result.code = interrupted`）的申请如果之后还收到真实的执行结果，结束处理仍然接受并用真实结果覆盖。

**有效期是执行策略的一个字段（`requestTtlHours`）**，参与四层逐层取更严：越短越严、没有“不限”（1～720 小时，默认 24）。批准绑定的是提交时的状态，拖得越久，审批人看到的情况和执行时的实际情况差得越远。
