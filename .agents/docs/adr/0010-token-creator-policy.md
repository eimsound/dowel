# 谁能创建 CI 令牌：三层逐层取与（AND）与自动只读可见性

2026-11-20 决定（P6，T2）：实例、组、项目三层都可以配置“谁能创建 CI 令牌”，允许指定项目角色（项目管理员 / 编辑者及以上）或指定组的管理员 / 成员；被允许创建令牌的人自动能只读查看范围内的项目。实现见 `packages/api/src/tokens.ts`、`apps/server/src/token-rules.ts`、`apps/server/src/roles.ts`、`apps/server/src/routes/tokens.ts`。

**三层合并规则采用“逐层取与（AND）”，层内各条件取或（OR）。** 每一层存储一条可选规则 `{ roles, groups }`（未设置 = 继承，无行记录）：

- 单层内部：满足 `roles` 中的任一项目角色，**或**满足 `groups` 中的任一组条件（指定组的管理员或成员）即通过这一层；两个数组都为空表示这一层不允许任何人（实例管理员除外）。
- 跨层合并：用户必须**同时满足**实例层、组层、项目层中每一个已设置的层；三层都未设置时退回到默认规则（`{ roles: ['admin'], groups: [] }`，即项目管理员）。实例管理员始终放行。

选择“逐层取与”而不是和 P5a 执行策略一样对标量字段做偏序比较，是因为“角色 ∪ 多个组”的集合包含关系没有静态全序（例如实例层要求“安全组成员”，组层想写成“项目管理员”时，两者不是子集关系而是交集关系）。逐层取与在结构上保证了**下级永远只能在上级允许的集合里继续收窄，绝不可能放宽上级**（与 ADR 0005 审批流程“只能追加”同构），也不需要复杂的写入期集合包含推理；同时能自然表达“必须在运维组（实例层）且是本项目管理员（项目层）”这类常见企业约束。

**自动只读可见性与 `baseRole` 分离，避免循环依赖。** 路线图与共识 11.4 规定“被允许创建令牌的人自动能只读查看范围内的项目”（例如公司设了一个独立的安全 / 流水线组，专门负责给各项目签发和轮换 CI 令牌，成员不必逐个项目授权）。如果计算“谁能创建令牌”时读取 `effectiveRole`，而 `effectiveRole` 又依赖 `canCreateToken`，就会形成环。因此 `roles.ts` 拆成两步：

1. `baseRole(rc, project)` 只算前四项（实例管理员、组管理员、组默认权限、授权），不含令牌规则；
2. `canCreateToken(rc, project)` 用 `baseRole` 评估角色条件、用组成员关系评估组条件；
3. `effectiveRole(rc, project)` 在 `baseRole` 为空且存在组条件且 `canCreateToken` 为真时返回 `'viewer'`。

因为角色条件（`editor` / `admin`）本来就要求 `baseRole` 非空，只有组条件会让原本不可见的用户获得 `viewer` 可见性；规则里没有任何组条件时 `effectiveRole` 直接短路，不增加额外开销。同时，`requests.ts` 的 `loadAudience` 也把规则里涉及的组成员纳入受众，保证他们能正常进入审批 / 通知等受众计算，且修改任意一层的令牌创建规则后会调用 `rooms.refreshLoaded()` 让在线 WebSocket 角色即时生效。
