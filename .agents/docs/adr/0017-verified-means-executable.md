# 发布必须通过影子库验证；“已验证”与执行读回用同一把尺子，并按数据库完整版本号记录

2026-11-27 决定（[Issue #132](https://github.com/eimsound/dowel/issues/132)；部分修订 [ADR 0016](0016-on-demand-shadow-normalization.md) 决定 2、决定 4 与「影响与边界」，补充 [ADR 0012](0012-strict-verify-on-restore.md)）。本 ADR 落盘时主体实现尚未合入：代码与用户文档的现状以 Issue #132 的实现 PR 为准（其中移除 MySQL `alignMysqlImportedLive` 读回纯格式容忍已先行于 PR #162 合入）。

## 背景

“已验证”和“能执行成功”原先用的是两把尺子：

- **闭环验证**在影子库里按模型建一遍、再按冻结脚本跑一遍，比较两次读回的结构。两边都经过引擎改写，所以模型里留着用户原文（例如 `note <> ''`）也照样一致。
- **执行读回校验**把目标库读回的结构（例如 `(note <> ''::text)`）与版本模型逐字比较，对不上就报 `readback_mismatch`，这次执行不算数。

于是会出现“已验证，却永远执行不了”的版本。在它上面再发布修正版本没有用（执行卡在坏版本上），“标记为已执行”也走不通（同一把尺子），首个版本还不能作废。进入路径有三条：

1. 没有影子库时发布（原先允许，标为未验证），之后配了影子库再重新验证：验证通过，但模型里仍是原文。
2. 发布瞬间的自动规范化被跳过（写回冲突、影子库瞬时出错、停机），或规范化完成后、读取模型前被并发编辑插队。
3. 规范化正常完成也会中招：普通列的类型与 SQLite 内置排序规则不在规范化范围内，而只有 Web 界面的输入框会把它们换成标准写法。

路径 2、3 已在 SQLite 上用测试复现；PostgreSQL、MySQL、SQL Server 的结论来自读代码，实现时须在真实数据库上验证。

## 原则

- **版本模型里只存数据库的写法。** 出现别的写法一律视为缺陷，在发布时拦下并指出差异；不在比较时容忍，也不在流程里自动绕过，以免遮蔽缺陷。
- **不考虑旧数据兼容。** Dowel 尚未公开发布，也没有被实际使用过的数据；不做存量扫描、迁移或自救功能。

## 决定

1. **发布是一条流水线：规范化 → 影子库闭环验证 → 冻结，任何一步不通过就不发布。**
   - 没有可用影子库时拒绝发布；影子库暂时连不上同样拒绝，稍后重试。SQLite 永远有内存影子库，不受影响。
   - 规范化被跳过且仍有待规范化对象时，在验证之前就拒绝，并返回原因与待处理对象清单。
   - 发布使用规范化步骤判定过的那一份模型，不再二次读取工作副本。
   - 发布成功的版本一定带有至少一条通过的验证记录，不再有“发布为未验证”。
2. **闭环验证增加读回核对。** 在现有的两份影子库快照比较之外，用执行读回校验的**同一个比较**，核对“升级后读回的结构 对 本版本模型”与“回滚后读回的结构 对 上一个版本模型”。不一致即验证失败，报告列出对象、属性、模型里的值、数据库读回的值；回滚方向的差异标明属于上一个版本的模型。由此“已验证”意味着：在同版本的数据库上执行，读回校验一定通过。
   - 读回比较在四种方言上都是严格的：移除 MySQL `alignMysqlImportedLive` 对表达式纯格式差异（字符集前导 `_utf8mb4`、反引号、字符串转义、外层括号与空白）的容忍，读回结构必须与冻结的版本模型一致。
3. **发布时发现写法不一致：拒绝并指路，不自动修复。** 用户重试；仍被拒就按报告把模型改成数据库的写法。出现这种拒绝说明规范化有缺陷，服务端记日志以便定位。
4. **所有验证入口统一。** 发布、重新验证、接手、接入领先的环境、向导基线共用同一套验证（含读回核对）。
   - 向导从已有数据库导入时，基线验证不通过或没有影子库都不阻止项目创建，基线标为未验证。这是唯一“没验证就存在”的版本：它的模型是从数据库读出来的，不是手写的。
   - “写入基线”与“标记为已执行”仍然不要求版本已验证，它们各自在目标库上做结构核对（[ADR 0004](0004-drift-resolution-by-mark-as-applied.md)）。
   - 除此之外，“未验证”只会出现在人工修改过脚本、尚未重新验证的版本上。
5. **验证结果按影子库的数据库完整版本号逐条记录**（PostgreSQL 两段，如 17.4；MySQL 三段，如 8.4.3；SQL Server 为构建号；SQLite 的影子库与目标库用同一个内置库，视为恒等）。多次验证的结果合并，脚本被人工修改后清空。
   - **发布**：只有与项目某个环境的数据库完整版本号一致的影子库才算验证依据；至少一条通过、且没有任何可用影子库验证失败，才发布。尚未覆盖到的环境在发布结果里列出，不阻止发布。
   - **执行与回滚**：目标库的完整版本号必须有通过的验证记录，否则拒绝；预演做同样的检查；紧急执行与 CI 令牌不绕过。
   - 原先“最低目标版本组必须有影子库”的规则随之删除：每个环境由自己的数据库版本把关。
6. **写入模型时换成数据库的写法，这是唯一的一层。**
   - 列类型、SQLite 内置排序规则在所有写入入口共用的位置规范化（Web、MCP 宏、粘贴、WebSocket）；只处理内置类型，用户自定义、带引号区分大小写的类型名不折叠。
   - 规划器不为 PostgreSQL、SQLite 增加别名或大小写容忍。MySQL、SQL Server 现有的类型规范化比较保留，那是引擎回显类型的方式决定的，不是为了容错。
   - 执行读回校验不再有任何方言的表达式写法容忍：MySQL `alignMysqlImportedLive` 的纯格式容忍移除，四种方言都按冻结的版本模型严格读回校验。模型里表达式写法与数据库不一致，应在写入与发布时被规范化或拦下，而不是在读回时放过。
   - PostgreSQL 的 `serial` 类写法不是真正的类型：写入时展开成数据库实际建出的结构（整数列、非空、归属于该列并随表名列名派生命名的序列、指向该序列的默认值），模型里不存 `serial`。界面在“整数类型、默认值指向一个序列、该序列归属于此列”同时成立时把类型显示为 `serial (integer)`（`bigserial (bigint)`、`smallserial (smallint)` 同理），这只是显示，不另存标记，从数据库导入的同类列也这样显示。之后改类型只改类型，默认值与序列不动；取消自增的做法是清空默认值。

## Considered Options

- **继续允许没有影子库时发布，重新验证时把版本模型回填成规范形式**：能保留“先发布、后补影子库”的用法，但要给 [ADR 0002](0002-frozen-migration-chain.md)“版本发布后不可变”开例外，并牵连接手与黄金基线的判断；收紧以后再放开容易，反过来很难。
- **发布时自动修复**（不看黄金基线，把差异涉及的对象重新规范化后重试）：用户无感，但要在发布流程里加一段改写与重试逻辑，并把规范化的缺陷悄悄绕过去。
- **允许作废从未执行过的首个版本**：能原地救回首个版本就坏掉的旧项目，但动了 [ADR 0013](0013-retire-tail-version-instead-of-branches.md)“版本链单根”的前提；不考虑旧数据后没有必要。
- **接手与接入暂不启用读回核对**：只为照顾旧数据；不考虑旧数据后，统一核对反而让“已验证”在所有入口含义一致。
- **只按大版本系列把关**（PostgreSQL 17、MySQL 8.4）：小版本升级与分批升级期间不会被卡住，但小版本之间回显万一有差异，要拖到执行时才发现。
- **发布时要求覆盖项目里所有环境的数据库版本**：发布出去的版本保证能执行到当时的每个环境，但任何一个环境的影子库没跟上，整个项目都不能发布。
- **规划器把类型别名、大小写当成等价**：语义上成立，但会让“某个写入入口漏了规范化”这类缺陷不再暴露。
- **`serial` 写入时拒绝并提示改用 identity，或自动换成 identity**：实现更小，但前者让习惯写法多一步，后者替用户做了一个不完全等价的选择。

## 影响

- 没有连接任何数据库的 PostgreSQL、MySQL、SQL Server 项目不能发布版本，仍可建模、预览迁移、导出 DDL。
- 生产环境需要版本一致的影子库：打开“允许同实例影子库”，或配置一个版本相同的独立影子库。目标库升级小版本后，以及先升级预发、后升级生产的那段时间里，尚未在新版本上验证的版本不能执行或回滚到该环境，紧急回滚也不例外。同实例影子库随实例一起升级，重新验证一次即可。
- 给项目新增一个不同数据库版本的环境后，已有版本要重新验证才能执行到它。
- 待观察：如果版本一致的要求在实际运维中过严，可评估按环境放宽到大版本系列；现在不做开关。
- MySQL `alignMysqlImportedLive` 的表达式纯格式容忍移除后，四种方言的执行读回校验都按冻结的版本模型严格比较；此前依赖这层容忍才能执行的 MySQL 版本会报 `readback_mismatch`（不考虑旧数据，不做兼容）。
- ADR 0016 决定 4 里已验证版本用 `canonical: 'ifClean'` 的做法保留，理由不再是 MySQL 纯格式容忍，而是：验证记录按数据库完整版本号区分，在其他版本上验证通过的版本不保证是当前影子库的规范形式；SQL Server 生成列的 `type` 规划器不比较，“已验证”不约束它；以及作为防御性保护，推进黄金基线前再确认一次没有待规范化对象。
- 接手、接入领先版本时把链头版本模型直接当作黄金基线的做法（Issue #123）依赖两道严格读回：执行读回校验（`verifyAndRecord`）与恢复时闭环验证的读回核对。本决定不放宽前者，并让恢复进来的每个版本都经过后者；今后放宽其中任何一道，都要重新审视接手与接入领先版本的这条路径。
