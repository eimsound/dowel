# 组织与部署：一个实例一家公司、用“组”承载归属；高可用只靠平台 PostgreSQL 多活

- **状态**：已生效（Implemented）
- **领域 / 范围**：实例的组织模型（公司、组、用户、项目归属）与部署形态（单机 SQLite、多副本 HA）
- **合并自**：原 ADR 0001（2026-11-19）、原 ADR 0011（2026-11-21，P7）
- **重审触发条件**：需要多家公司共用一个实例（多租户）；或 HA 部署出现平台 PostgreSQL 无法承受的吞吐（实时协作、限流写压），需要引入额外中间件

## 1. 一个实例只服务一家公司，用“组”统一承载人和项目归属

一个 Dowel 实例只服务一家公司。公司内部用**组**划分：组是一群用户，可以拥有项目，一个用户可以属于多个组。组和用户对所有人可见；组的项目只对有权限的人可见（无权限时当作不存在）。不另设“组织”和“团队”两层。

- 跨组的特权（如 DBA 执行生产迁移）通过“在某个范围内把权限授给某个组”来表达，不需要把同一批人重复加进多个组织。
- 因为只服务一家公司，组级的“必须通过某个 OIDC 登录”永远不做。
- 以后若要支持多家公司共用一个实例，需要在组之上加一层租户，并重做所有归属和权限检查。

## 2. 高可用采用纯平台 PostgreSQL 多活，不引入 Redis

多副本高可用部署只依赖外部平台 PostgreSQL，不引入 Redis 等额外中间件。单机 SQLite 模式保留，只支持单副本。副本之间完全对等、无状态，负载均衡不需要粘性路由（Sticky Session）。

1. **无状态实时协作房间**：WebSocket 写操作通过平台 PG 按 `branch_id` 行锁串行提交到 `room_commits`，提交后经 `LISTEN/NOTIFY` 向其他副本广播轻量通知（事件 ID / `seq`），各副本向本地连接推送，或按 `seq` 从库里补齐（规避 `NOTIFY` 8 KB 负载上限与断线不重放）。停用踢人、角色即时降级、收件箱 SSE 实时推送复用同一条 `NOTIFY` 通道。
2. **持久化后台任务与巡检**：Webhook 投递与重试队列放在平台库表里，多副本用 `FOR UPDATE SKIP LOCKED` 认领（细节见 [04-webhooks.md](04-webhooks.md) 第 5 节）；审批过期巡检、定时漂移检查与影子库派生通过平台 PG 锁 / 租约防止多副本重复执行；首次启动的管理员引导用事务级 advisory lock，保证多副本冷启动只建一次管理员；执行中的申请记录所属副本，按副本心跳判断是否真的中断（见 [03-execution-governance.md](03-execution-governance.md) 第 3.6 节）。
3. **限流器保留副本本地内存计数**：登录失败、连库探测、CI 令牌失败与请求速率等限流器不迁入数据库，避免给数据库增加限流写压。全部限流维度（上限与窗口）开放环境变量配置，并在 `docker-compose.yml` 与运维文档中明确提示“HA 多副本下实际总配额约为设定值 × 副本数”。

## 被否决的方案

- **类似 GitHub 的多组织 + 组织内团队**：用一家真实公司推演时推翻。只有一家公司时，组织其实就是部门，下面再套团队是两层几乎一样的概念；跨部门的 DBA 只能被重复加进每个组织、在每个组织里各建一个 DBA 团队。
- **平台 PG + Redis 多活**：吞吐更高、限流可全局精确，但公司内网自托管要多维护一套 Redis（高可用还需 Sentinel / Cluster），且与平台 PG 跨系统双写带来一致性与降级复杂度。
- **平台 PG + Active / Passive 选主**：内存逻辑改动小，但流量压在单主节点，主备切换时全员 WebSocket 断线冷启动，不具备多活扩展能力。
- **限流计数迁入数据库以获得全局精确配额**：每次请求都写库，限流本身成了数据库压力源；按副本计数的误差已在运维文档中说明，可由运维按副本数调整配置。
