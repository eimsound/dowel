# Webhook 出站：独立允许列表、默认只放行公网、连接时检查、不跟随重定向、有限重试、平台库持久化队列

- **状态**：已生效（Implemented）
- **领域 / 范围**：组级 Webhook（通用 JSON、钉钉、飞书、企业微信、Slack）的出站安全（SSRF）、投递与重试、密钥保管与签名
- **合并自**：原 ADR 0008（2026-11-20，P5b，E8），其中“进程内队列、重启丢失”一段按原 ADR 0011（2026-11-21，P7 HA3）的持久化队列改写为当前实现；用户文档 `docs/{zh,en}/webhooks.md`
- **重审触发条件**：需要经 HTTP 代理发送 Webhook；需要按事件年龄丢弃积压投递；接收端普遍要求跟随重定向

组管理员可以给组配置 Webhook，执行申请、审批结果、执行结束等事件发生时由服务端发 HTTP 请求出去。这意味着**服务端会替用户访问一个用户给的 URL**，和数据库连接一样是 SSRF 面；同时 Webhook 地址里常常带着令牌（钉钉的 `access_token`、企业微信的 `key`、Slack 的整段路径），本身就是密钥。

## 1. 另设允许列表 `webhookAllowlist`，默认只允许公网地址

不复用数据库的 `connectionAllowlist`，两者语义相反：数据库通常在内网，`connectionAllowlist` 是“只能连到这些地址”，空表示不限制（自托管的默认）；Webhook 接收端通常在公网，要防的恰恰是被指向内网（云元数据 `169.254.169.254`、内网管理接口、本机端口）。

- **默认拒绝**：回环、私有（10/8、172.16/12、192.168/16）、链路本地（169.254/16、fe80::/10）、CGNAT（100.64/10）、唯一本地（fc00::/7）、0.0.0.0/8 与未指定地址、组播、保留 / 文档地址；IPv6 里嵌着 IPv4 的写法（IPv4-mapped、NAT64、6to4）按里面的 IPv4 再判断一次。
- **额外放行**：`webhookAllowlist` 里的 CIDR / IP / 主机名（内网的自建接收服务）。主机名项按名字匹配、不检查解析结果——实例管理员写进去就是明确信任它的 DNS。

## 2. 检查在真正连接时做（防 DNS 重绑定）

保存时解析一次主机名只能给用户及时反馈，挡不住 DNS 重绑定（保存时解析到公网、发送时解析到内网），也挡不住保存之后 DNS 记录被改。所以每次发送都给 HTTP 客户端传自定义 `lookup`：调系统解析，对**每一个**解析结果做第 1 节的判断，有一个不通过就整个拒绝（不挑一个能用的——混着内网地址的记录本身就可疑），通过后才把地址交给 Node 去连。

- 同时支持 Node 单地址与 `{ all: true }`（`autoSelectFamily`）两种 lookup 回调形式。
- URL 主机是 IP 字面量时 Node 不调用 lookup，发请求前单独检查。
- 每次请求不复用连接池里的连接，保证 lookup 一定执行。
- 不支持经 HTTP 代理发送：经过代理时连接的是代理，连接时的检查就失去意义。

## 3. 不跟随重定向

3xx 一律算失败（提示填写最终地址），不重试。跟随重定向等于让接收端把请求转向任意地址（包括内网），而且重定向目标收到的是带签名、带内容的请求；真正的 Webhook 服务不需要重定向。

## 4. 有限重试

- 只有可能自行恢复的失败才重试：网络错误、超时、429、5xx；最多重试 3 次（共 4 次尝试），指数退避 2 秒、8 秒、32 秒。
- 不重试：4xx（地址或令牌错了）、出站限制拒绝、3xx、钉钉 / 飞书 / 企业微信在 HTTP 200 里返回的业务错误码——重试也一样失败，只会刷屏。
- 一次尝试总时限 5 秒（连接 + 发送 + 读响应），响应体最多读 4 KB。
- 每次尝试写一行投递记录；同一事件的多次尝试共用 `delivery_id`，接收方据此去重。每个 Webhook 只保留最近 50 条投递记录。

## 5. 投递队列持久化在平台库里，重启不丢

投递与重试任务写入平台库的 `webhook_jobs` 表（单机 SQLite 与 HA PostgreSQL 同一张表、同一套逻辑），`emit` 只负责入队，不阻塞调用方、不抛错。

- **认领**：投递工作者按 `next_run_at` 拉取到期任务，写入认领者与租约到期时间后发送（并发 4）。PostgreSQL 上用 `FOR UPDATE SKIP LOCKED` 让多副本并发认领不重复；SQLite 单副本下平台库事务本来就互斥。
- **唤醒**：入队后经事件总线广播唤醒各副本立即拉取，并以定时轮询兜底（含总线断线重连后的补拉）。
- **重试**：重试是同一行任务推后 `next_run_at`、累加尝试次数，而不是进程内定时器，所以重启或换副本后照常继续。
- **重启与崩溃**：启动时拾取遗留的到期任务；优雅停机释放本副本持有的租约，让其他副本或下一次启动立即接手；副本崩溃时等租约过期后由其他副本重新认领。因此投递语义是**至少一次**，接收方应按 `delivery_id` 去重。
- **Webhook 被删除**时，它的待投递任务随外键级联删除，不再发送。
- Webhook 仍是**旁路通知**：申请、审批、执行的结果在站内收件箱和审计里有完整记录，投递失败不影响任何状态。

## 6. URL 与签名密钥按密钥对待

- 两者都用 `DOWEL_SECRET` 加密存储（与数据库连接串同一套 AES-256-GCM），任何响应、审计、日志、投递记录里都不出现：响应只有 `urlMasked`（协议 + 主机）和 `hasSecret`。
- 修改时 URL 不给就保留；密钥“字符串 = 换新 / null = 清除 / 不给 = 不变”；界面编辑时不回显。审计只记组、名称、格式、事件和“改没改 URL / 密钥”。
- 投递失败的原因去掉 URL 的路径和查询参数（包括其中较长的片段——对方的错误响应可能把请求地址原样回显）再脱敏。
- 消息内容只含项目、环境、版本、人名、状态这类信息，渲染前所有字符串再脱敏一次兜底。

## 7. 签名

- 通用 JSON：`X-Dowel-Signature: sha256=HMAC-SHA256(secret, "<X-Dowel-Timestamp>.<body>")`。时间戳进签名，接收方可以拒绝过旧的请求防重放（用户文档给了校验示例）。
- 钉钉、飞书按各自文档的加签规则；企业微信、Slack 的机器人没有签名机制，密钥就在 URL 里。

## 被否决的方案

- **复用 `connectionAllowlist`**：要么为了 Webhook 打开内网就等于为数据库放宽了，要么空列表“不限制”让 Webhook 能打到任何内网地址。
- **只在保存时解析校验**：挡不住 DNS 重绑定与之后的 DNS 记录变更。
- **经 HTTP 代理发送**：连接时检查失去意义；需要时以后再评估“代理 + 代理侧限制”的方案。
- **跟随重定向**：接收端可把带签名的请求转向任意地址（包括内网）。
- **对所有失败无差别重试**：配置错误重试也一样失败，只会刷屏。
- **进程内队列、重启丢失**（P5b 最初实现）：重启或副本退出时，未发出的投递和排着的重试会丢失，多副本下也无法交接，已由第 5 节的平台库持久化队列取代。
