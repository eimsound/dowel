# 规范化与验证：按需影子库规范化、严格发布流水线、“已验证”即同版本可执行

- **状态**：已生效（Implemented）
- **领域 / 范围**：工作副本表达式的影子库规范化（触发时机、黄金基线、待规范化判定、手动入口）；发布流水线；闭环验证与读回核对；按数据库完整版本号把关执行；写入层规范化
- **合并自**：原 ADR 0016（2026-11-27，看板 #3）、原 ADR 0017（2026-11-27，Issue #132，PR #162、#194），并按原 ADR 0019（Issue #161）、PR #205（`forProjectTarget` 拿到首个可用影子库即返回）、PR #209（迁移预览验证与发布对齐）调和；相关 Issue：#123、#133、#134、#136、#145、#146、#153、#159
- **重审触发条件**：版本一致的要求在实际运维中过严（可评估按环境放宽到大版本系列，现在不做开关）；同一项目的多个数据库版本对同一对象回显不同写法（见下方待实现的修订）；需要放宽执行读回校验或恢复时读回核对中的任何一道（须同时重审 [02-version-chain-and-recovery.md](02-version-chain-and-recovery.md) 第 5 节的黄金基线路径）

> **待实现的修订**：[09-per-version-readback-truth.md](09-per-version-readback-truth.md)（已拍板待实现，Issue #201）将把外部影子库方言的读回核对从“读回必须等于版本模型”改为“闭环一致即通过，并按数据库完整版本号记录读回差异”，执行、漂移、标记改用叠加了差异的有效模型比较。在它的实现 PR 合入之前，本文描述的就是当前 `main` 的行为：四种方言的读回核对都是严格零差异。

## 原则

- **版本模型里只存数据库的写法。** 出现别的写法一律视为缺陷：在写入与发布时规范化或拦下并指出差异；不在比较时容忍，也不在流程里自动绕过，以免遮蔽缺陷。
- **“已验证”与执行读回用同一把尺子。** 已验证意味着：在同版本的数据库上执行，读回校验一定通过。
- **编辑期间零影子库 I/O。** 影子库只在用户需要结果时才连。
- **不考虑旧数据兼容。** Dowel 尚未公开发布，没有被实际使用过的数据；不做存量扫描、迁移或自救功能。

## 1. 按需规范化：编辑期零影子库调用，关键出口 `flush`

派生数据（[04-ir-design.md](../04-ir-design.md) 2.6）指 CHECK、默认值、生成列、表达式索引与部分索引条件、分区键与分区边界的引擎规范形式，以及依赖改名后的不透明对象 DDL。规范化在影子库里从黄金基线重放到当前模型，读回规范形式并带版本检查写回工作副本。

- **编辑期间不触发**：提交编辑、添加环境、接入后都不调度规范化，没有后台防抖。
- **关键出口按需 `flush`**：发布；迁移预览、DDL 导出、验证（Web 与 MCP 同一组出口）；版本与画布的差异；画布历史详情；拉取预览、接入预览；MCP 读模型类工具。出口返回的 `seq` 是 flush 之后的，恰好就是后续确认请求要带的 `workingSeq`，并直接使用 flush 判定过的那份模型，不再二次读取工作副本。
- **确认阶段不再 flush**：恢复画布历史、应用版本到画布、作废 / 取消作废时同步工作副本、拉取确认、接入确认。它们的 `workingSeq` 来自已经 flush 过的预览；若在确认时 flush，写回会推进 `seq`，用户自己跟自己冲突（`409 working_changed`）。
- **单机与 HA 统一**：按分支串行的本地队列 + 分支级派生锁（PG 多副本是阻塞版的分布式锁，超时返回 `503 normalize_busy`）；队列里尚未开始的同分支 flush 合并成一次。
- **零成本稳态**：锁内先用纯函数判定有没有待规范化对象（第 3 节），没有就 **0 影子库 I/O** 返回 `clean`。
- **跳过不报错**：没有影子库、连不上、canonicalize 失败时 `flush` 安静返回 `skipped`，不改基线。对迁移预览、DDL 导出等出口，这意味着继续使用当前写法；**发布不在此列**，见第 6 节。
- **单影子库选择**：规范化只用一个影子库。按数据库版本组升序（最低已知版本组优先，未知版本组最后），组内按“显式影子库 > 非生产环境的同实例影子库 > 允许同实例的生产环境”依次尝试，**拿到第一个可用影子库立即返回**，不再为其余版本组建连或预检（PR #205）。模型页状态栏显示的影子库来源与这一选择对齐。

## 2. 黄金基线不变量

黄金基线（`branches.baseline`）是“已知为规范形式”的模型，待规范化判定相对它进行。基线**只**在两种情况下推进：

1. **canonical 替换**：导入 SQL、拉取、接入领先版本、接手，用调用方传入的模型写基线。接手与接入领先版本直接用链头版本模型作基线（#123），其安全性依赖两道严格读回：执行读回校验与恢复时闭环验证的读回核对（第 7 节）。
2. **一次成功的 canonicalize**：基线 = 本次规范化的模型 + 规范形式。

除此之外：

- 没有待规范化对象时不写基线；canonicalize 失败（连接 / SQL / 表达式错误）时不写基线。
- **已验证版本的应用 / 作废 / 取消作废**用 `ifClean`：在派生锁内判定该模型相对当前基线没有待规范化对象时才推进基线，否则只替换房间，由之后的出口 flush 或手动规范化补齐。理由：验证记录按数据库完整版本号区分，在别的版本上验证通过不保证是当前影子库的规范形式；SQL Server 生成列的推导类型规划器不比较、“已验证”不约束它；以及推进基线前的防御性确认。
- **非 canonical 替换**（恢复画布历史、应用未验证版本）同样排在本地队列与派生锁里（在途规范化先排空，不会被旧结果覆盖），只替换房间、不碰基线。

## 3. 待规范化判定

纯函数、只看当前模型与基线，稳态 0 影子库 I/O：

- **表的列上下文**：表沿分区关系解析到根父表（分区子表没有自己的列；覆盖多级分区与 attach / detach，#134），按列名（MySQL / SQL Server / SQLite 忽略大小写）对齐两边的列；两边都有的列名对应列的类型 / 类型引用（含枚举完整限定名）/ 排序规则（大小写不敏感方言再加列名原文）不同即算变了。表达式按列名引用列，所以列名对调、删列后新建同名列也算（#133）；只在一边出现的列名（新增、删除、改名到新名字）不算。
- **不透明对象**：依赖或父对象的完整限定名变了；依赖集合变了；依赖的列或依赖表 / 父表的列上下文变了；DDL 文本变了；依赖的不透明对象本身待规范化（沿依赖传递，带环保护，#136）。
- **带表达式的普通对象**：表达式变了，或所在表的列上下文变了；列自己的默认值 / 生成列另按 ID 比较列自身类型。只有分区边界、没有表达式分区键的表不看自身列上下文，而看是否改挂到另一个分区父表，以及直接父表的分区键签名是否变化（opclass / collation / 策略是有意的过近似）。
- **表达式直接写了枚举名**（#146）：相对基线有枚举的名字绑定变了（改名、对调、换 schema、删除 / 新建），且对象表达式里按词出现了其中某个枚举两边的名字。PG 按 OID 存表达式，读回时类型名跟着影子库的绑定走；稳态没有绑定变化，不做任何文本扫描。
- **SQL Server 持久化计算列**（#145、#161）：列自己的显式 `notNull` 变了、列自己的推断非空 `ext.mssql.inferredNotNull` 相对基线变了，或所在表按列名对齐的列 `notNull` 变了，即待规范化。规范化只写回推断值、从不改写显式 `notNull`（[08-dialect-fidelity.md](08-dialect-fidelity.md) 第 2 节）。其他方言与非持久化计算列不看可空性。

## 4. canonicalize 自愈

基线自己在影子库里建不出来（旧版本遗留 / 升级后不兼容）且没有依赖改名的不透明对象时，直接从空库建出当前模型（与增量迁移等价）；有改名依赖时如实报错。基础设施故障统一映射为“影子库不可用”。

## 5. 手动规范化与状态栏

- **状态查询**（查看者即可）：返回当前 `seq`、待规范化对象数与清单（有截断）、基线状态与影子库配置状态（内存 / 已配置 / 无）；0 影子库 I/O，不拿派生锁。
- **手动规范化**（编辑者以上，可指定环境）：外部影子库方言受连接限速；预连接失败或静态模型校验不通过时精确退回限速额度。未指定环境时，影子库在派生锁内按第 1 节的规则解析；基线等于当前模型时直接返回 `clean`，不连影子库、退回额度。否则 canonicalize、写回（画布历史里是一条 `derive` 提交）、推进基线。错误：影子库不可用、canonicalize 失败（脱敏）、`409 working_changed`、`503 normalize_busy`、`503 shutting_down`；规范化期间项目被删除返回 `404`（同项目不存在）。不写审计（派生写回已在画布历史里）。
- **状态栏**（模型页底部，不进顶栏）：“表达式已规范化”或“N 处待规范化”，查看者也能看到；编辑者另有“规范化”按钮，没有可用影子库或未同步时不可用并说明原因。关键出口、环境与 schema 范围变更后都使状态查询失效：零改写的 flush 只推进基线、`seq` 不变，不主动重查会一直停在“N 处待规范化”。

## 6. 发布是一条严格流水线：规范化 → 影子库闭环验证 → 冻结

任何一步不通过就不发布，不存在“发布为未验证”：

1. **规范化**：`flush` 被跳过且仍有待规范化对象时，在验证之前就拒绝（`normalize_pending`，列出待处理对象）；跳过原因是没有 / 连不上影子库时按影子库不可用拒绝。
2. **验证**：没有可用影子库或影子库暂时连不上时拒绝（`shadow_unavailable`，稍后重试）；SQLite 永远有内存影子库，不受影响。验证失败（`verify_failed`）或读回核对发现写法不一致（`readback_mismatch`）时拒绝。
3. **门禁**：只有与项目某个环境的数据库完整版本号一致的影子库才算验证依据。至少一条通过、且没有任何可用影子库验证失败，才发布；没有一个通过的影子库与项目环境版本一致时拒绝（`no_matching_shadow`）。尚未覆盖到的环境在发布结果里列出，不阻止发布。
4. **冻结**：使用规范化步骤判定过的那一份模型冻结版本与脚本，版本一定带有至少一条通过的验证记录。

**读回核对拒绝时不自动修复**：用户重试；仍被拒就按报告把模型改成数据库的写法。出现这种拒绝说明规范化有缺陷，服务端记日志以便定位。

## 7. 闭环验证增加读回核对，所有入口统一

- **闭环验证**在影子库里按模型建一遍、再按冻结脚本跑一遍，比较两次读回的结构；在此之上，用执行读回校验的**同一个比较**核对“升级后读回的结构 对 本版本模型”与“回滚后读回的结构 对 上一个版本模型”，范围按冻结的 scope。不一致即验证失败，报告列出对象、属性、模型里的值、数据库读回的值；回滚方向的差异标明属于上一个版本的模型。
- **四种方言都严格比较**：执行读回校验与读回核对都不容忍任何表达式写法差异（MySQL 原先对字符集前导、反引号、字符串转义、外层括号与空白的纯格式容忍已于 #162 移除）。规划器不为 PostgreSQL、SQLite 增加别名或大小写容忍；MySQL、SQL Server 现有的类型规范化比较保留——那是引擎回显类型的方式决定的，不是为了容错。
- **统一的入口**：发布、重新验证、接手、接入领先环境、向导基线、迁移预览的验证（Web `POST /api/projects/:pid/verify` 与 MCP `verify_migration`）共用同一套验证（含读回核对）。迁移预览的验证冻结与发布完全相同的升级 / 回滚脚本并走同一套按完整版本号分组的验证（PR #209）：不指定环境时验证项目环境的每一个不同完整版本号；指定环境时只用该环境的影子库，但覆盖情况仍按全部环境计算；返回与发布拒绝相同的错误码、`verifiedOn` 与未覆盖环境，`no_matching_shadow` 时 `ok` 为 `false`，只读 `ok` 的调用方不会误当作可发布。
- **唯一“没验证就存在”的版本**：向导从已有数据库导入时，基线验证不通过或没有影子库都不阻止项目创建，基线标为未验证——它的模型是从数据库读出来的，不是手写的。
- **其余“未验证”**只会出现在人工修改过脚本、尚未重新验证的版本上。
- “标记为已执行”不要求版本已验证，它在目标库上做结构核对（[02-version-chain-and-recovery.md](02-version-chain-and-recovery.md) 第 3 节）。

## 8. 验证结果按数据库完整版本号记录，执行按目标库版本把关

- **记录**：每条验证结果记下影子库的数据库完整版本号（PostgreSQL 两段，如 17.4；MySQL 三段，如 8.4.3；SQL Server 为构建号；SQLite 的影子库与目标库是同一个内置库，视为恒等）。多次验证的结果合并；脚本被人工修改后清空。
- **执行与回滚**：目标库的完整版本号必须有通过的验证记录，否则拒绝（`unverified`）；预演做同样的检查；紧急执行与 CI 令牌不绕过。首次执行时作为基线写入、不运行脚本的第一个版本之外，每个要执行的迁移都按这条检查。
- 原先“最低目标版本组必须有影子库”的规则已删除：每个环境由自己的数据库版本把关。

## 9. 写入模型时换成数据库的写法，这是唯一的一层

- 列类型、SQLite 内置排序规则在所有写入入口共用的位置规范化（Web、MCP 宏、粘贴、WebSocket）；只处理内置类型，用户自定义、带引号区分大小写的类型名不折叠。各方言“什么算不改语义的写法统一”见 [08-dialect-fidelity.md](08-dialect-fidelity.md)。
- **PostgreSQL `serial` 类写法不是真正的类型**：写入时展开成数据库实际建出的结构（整数列、非空、归属于该列并随表名列名派生命名的序列、指向该序列的默认值），模型里不存 `serial`。界面在“整数类型、默认值指向一个序列、该序列归属于此列”同时成立时把类型显示为 `serial (integer)`（`bigserial`、`smallserial` 同理），只是显示、不另存标记，从数据库导入的同类列也这样显示。之后改类型只改类型，默认值与序列不动；取消自增的做法是清空默认值。

## 10. 生命周期边界

- **停机**：停机后手动规范化拒绝（`503 shutting_down`），`flush` 返回 `skipped`；停机等待在途任务排空。
- **项目删除**：删除后在途规范化不回写内存或库里的基线，也不报成功——`flush` 返回 `skipped`，需要模型而读不到时报“项目不存在”（HTTP 404、MCP `project_not_found`），绝不编造空模型；`forget` 必须先于踢房间、关影子库，并跨副本广播；事件晚到或丢失时由失败路径上的存在性复查兜底，稳态（成功路径）不加查询。并发实现细节与反模式见 [pitfalls：rooms-derive-shadows](../../skills/pitfalls/references/rooms-derive-shadows.md)。

## 影响

- 画布里的表达式在规范化前显示用户原文，需要用户（或出口）触发；迁移 / DDL 第一次打开可能稍慢。迁移、DDL、发布、验证这些真正要求规范形式的地方都会先 flush，结果的正确性不受影响。
- 没有连接任何数据库的 PostgreSQL、MySQL、SQL Server 项目不能发布版本，仍可建模、预览迁移、导出 DDL。
- 生产环境需要版本一致的影子库：打开“允许同实例影子库”，或配置一个版本相同的独立影子库。目标库升级小版本后、以及先升级预发后升级生产的那段时间里，尚未在新版本上验证的版本不能执行或回滚到该环境，紧急回滚也不例外。同实例影子库随实例一起升级，重新验证一次即可。
- 给项目新增一个不同数据库版本的环境后，已有版本要重新验证才能执行到它。
- 此前依赖 MySQL 纯格式容忍才能执行的版本会报 `readback_mismatch`（不考虑旧数据，不做兼容）。

## 被否决的方案

- **保留编辑期后台防抖规范化，只修补自冲突与基线投毒**：画布里的表达式能“自己变成”规范形式，但编辑期影子库负载（同实例影子库时落在目标实例上）、HA 锁争用与画布历史里大量 `derive` 提交噪音依旧，行为也难以预期（何时变、为什么没变）。
- **手动“全量重查”入口**（不看黄金基线、从空库重新规范化全部对象）：用户无从判断什么时候该点；没有旧数据需要补救；发布时的读回核对会直接拒绝并报告写法不一致，不需要靠用户手动兜底。
- **在 IR 里给每个对象记“已规范化”标记**：消除不了三处根本耦合（规范形式只有引擎能给出、写回会推进 `seq`、导出要求规范形式），还要改 IR 的 `FORMAT` 与目标库历史的存储格式，并破坏 [04-ir-design.md](../04-ir-design.md) D7。
- **继续允许没有影子库时发布，重新验证时把版本模型回填成规范形式**：要给“版本发布后不可变”（[02-version-chain-and-recovery.md](02-version-chain-and-recovery.md) 第 1 节）开例外，并牵连接手与黄金基线的判断；收紧以后再放开容易，反过来很难。
- **发布时自动修复**（把差异涉及的对象重新规范化后重试）：用户无感，但要在发布流程里加一段改写与重试逻辑，并把规范化的缺陷悄悄绕过去。
- **接手与接入暂不启用读回核对**：只为照顾旧数据；统一核对让“已验证”在所有入口含义一致。
- **只按大版本系列把关**（PostgreSQL 17、MySQL 8.4）：小版本升级与分批升级期间不会被卡住，但小版本之间回显万一有差异，要拖到执行时才发现。
- **发布时要求覆盖项目里所有环境的数据库版本**：保证发布出去的版本能执行到当时的每个环境，但任何一个环境的影子库没跟上，整个项目都不能发布。
- **规划器把类型别名、大小写当成等价**：语义上成立，但会让“某个写入入口漏了规范化”这类缺陷不再暴露。
- **`serial` 写入时拒绝并提示改用 identity，或自动换成 identity**：实现更小，但前者让习惯写法多一步，后者替用户做了一个不完全等价的选择。
- **规范化时为每个版本组都建连影子库**：规范化只需要一份基准写法，多版本组并发建连只增加开销（PR #205）。
