# Webhook 出站：另设允许列表、默认只放行公网、连接时检查、不跟随重定向、有限重试、进程内队列

2026-11-20 决定（P5b，E8）：组管理员可以给组配置 Webhook（通用 JSON、钉钉、飞书、企业微信、Slack），执行申请、审批结果、执行结束时由服务端发 HTTP 请求出去。这意味着**服务端会替用户去访问一个用户给的 URL**，和数据库连接一样是 SSRF 面；同时 Webhook 地址里常常带着令牌（钉钉的 `access_token`、企业微信的 `key`、Slack 的整段路径），本身就是密钥。实现见 `apps/server/src/webhooks.ts`、`routes/webhooks.ts`，用户文档 `docs/webhooks.md`。

**另设一份允许列表 `webhookAllowlist`，不复用数据库的 `connectionAllowlist`。** 两者的语义相反：数据库通常在内网，`connectionAllowlist` 是“只能连到这些地址”，空表示不限制（自托管的默认）；Webhook 的接收端通常在公网（钉钉、飞书、Slack），需要防的恰恰是被指向内网（云元数据 `169.254.169.254`、内网管理接口、本机端口）。所以 Webhook 的规则是**默认只允许公网地址**：拒绝回环、私有（10/8、172.16/12、192.168/16）、链路本地（169.254/16、fe80::/10）、CGNAT（100.64/10）、唯一本地（fc00::/7）、0.0.0.0/8 与未指定地址、组播、保留 / 文档地址，IPv6 里嵌着 IPv4 的写法（IPv4-mapped、NAT64、6to4）按里面的 IPv4 再判断一次；`webhookAllowlist` 里的 CIDR / IP / 主机名**额外放行**（内网的自建接收服务）。复用一份列表的话，要么为了 Webhook 打开内网就等于为数据库放宽了，要么空列表“不限制”让 Webhook 能打到任何内网地址，都不对。主机名项按名字匹配、不检查解析结果——实例管理员写进去就是明确信任它的 DNS。

**检查在真正连接时做。** 保存时解析一次主机名只能给用户及时的反馈，挡不住 DNS 重绑定（保存时解析到公网、发送时解析到内网），也挡不住保存之后 DNS 记录被改。所以每次发送都给 `node:http` / `node:https` 的 `request` 传自定义 `lookup`：它调系统解析，对**每一个**解析结果做上面的判断，有一个不通过就整个拒绝（不挑一个能用的——混着内网地址的记录本身就可疑），通过后才把地址交给 Node 去连。Node 开了 `autoSelectFamily` 时会以 `{ all: true }` 调用 lookup、要地址数组，否则要单个地址，两种回调形式都支持。URL 主机是 IP 字面量时 Node 不调用 lookup，发请求前单独检查。每次请求 `agent: false`，不复用连接池里的连接，保证 lookup 一定执行。不支持经 HTTP 代理发送：经过代理时连接的是代理，连接时的检查就失去意义（需要时以后再加“代理 + 代理侧限制”的方案）。

**不跟随重定向。** 3xx 一律算失败（“不跟随重定向，请填写最终的地址”），不重试。跟随重定向等于让接收端把请求转向任意地址（包括内网），而且重定向目标收到的是带签名、带内容的请求；真正的 Webhook 服务不需要重定向。

**重试策略。** 只有可能自行恢复的失败才重试：网络错误、超时、429、5xx；最多重试 3 次（共 4 次尝试），指数退避 2 秒、8 秒、32 秒（`retryBaseMs × 4ⁿ`，测试里调短）。4xx（地址或令牌错了）、出站限制拒绝、3xx、钉钉 / 飞书 / 企业微信在 HTTP 200 里返回的业务错误码（签名不对、关键词不匹配、频率超限之外的配置错误居多）不重试——重试也一样失败，只会刷屏。每次尝试都写一行投递记录（同一个事件的多次尝试共用 `delivery_id`，接收方可以据此去重），每个 Webhook 只保留最近 50 条（写入后清理），足够排查又不会让表无限增长。一次尝试总时限 5 秒（连接 + 发送 + 读响应），响应体最多读 4 KB。

**进程内队列，重启丢失。** 投递排在进程内的队列里异步发送（并发 4），`emit` 不阻塞调用方、不抛错；等待中的重试是 `unref` 的定时器。没有用平台库做持久队列：Dowel 目前是单进程部署（执行锁、漂移检查也是这个前提），通知是“尽力而为”的旁路——申请、审批、执行的结果都在站内收件箱和审计里有完整记录，Webhook 丢一条不影响任何状态；持久队列要处理多进程抢任务、重启后补发过期消息（一小时前的“请审批”再发出来反而误导）。代价写进文档：**服务重启时，还没发出去的投递和排着的重试会丢失**。以后多进程部署时再改成平台库里的待发表 + 认领。

**URL 和签名密钥按密钥对待。** 两者都用 `DOWEL_SECRET` 加密存储（和数据库连接串同一套 AES-256-GCM），任何响应、审计、日志里都不出现：响应只有 `urlMasked`（协议 + 主机，例如 `https://oapi.dingtalk.com/…`）和 `hasSecret`；修改时 URL 不给就保留、密钥“字符串 = 换新 / null = 清除 / 不给 = 不变”，界面编辑时不回显；审计只记组、名称、格式、事件和“改没改 URL / 密钥”。投递失败的原因会去掉 URL 的路径和查询参数（包括其中较长的片段——对方的错误响应可能把请求地址原样回显）再过 `scrubSecrets`。消息内容由调用方构造（只有项目、环境、版本、人名、状态这类信息），渲染前所有字符串再脱敏一次兜底。

**签名。** 通用 JSON 用 `X-Dowel-Signature: sha256=HMAC-SHA256(secret, "<X-Dowel-Timestamp>.<body>")`：把时间戳放进签名，接收方可以拒绝过旧的请求防重放（文档里给了校验示例）。钉钉、飞书按各自文档的加签规则；企业微信、Slack 的机器人没有签名机制，密钥就在 URL 里。
