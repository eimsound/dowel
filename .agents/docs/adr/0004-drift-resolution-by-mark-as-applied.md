# 漂移的处理：导入、发布、标记为已执行，不设“收编版本”

2026-11-20 决定：环境发生漂移（线上结构不等于它当前版本的模型）时，Dowel 只提供两个出口。一是保留线上的修改：用线上结构**覆盖**工作副本（导入），用户检查、修改后按普通流程**发布**新版本（冻结真实的 up / down，影子库验证），再把漂移的环境**标记为已执行**到这个版本；其他环境把它当普通版本执行。二是放弃线上的修改：Dowel 生成修复脚本 `plan(线上结构, 当前版本的模型)`，**只显示、不代为执行**，用户自己执行后重新检查漂移。

**标记为已执行**是一个通用的特权操作：环境可以被标记到链上任意版本（更新或更早都行），唯一的硬条件是在项目锁里读出的线上结构等于该版本的模型；不执行任何 SQL，在目标库历史里写一条 `direction = 'mark'` 的记录，向前标记时给目标版本和中间跳过的版本写 `executed_at`。读回失败后手工修好、含非事务步骤的迁移半途失败后手工补完、手工回退了发布，都走这个出口；第一次执行时的“写入基线”是它的特例。

先讨论过一个专门的“漂移收编”流程：读出线上结构合并到当前模型，自动发布一个带特殊标记的版本并直接记为已执行，同时加一串前置条件（环境必须在链头、没有半途失败、工作副本没有未发布的修改）。放弃它是因为拆成三个已有的动作以后：不需要特殊的版本类型和发布路径；用户能在发布前修正导入的结果（例如把按名字识别成“删一列、加一列”的热修改回改名，保住对象 ID，冻结出 `RENAME`）；安全不靠事先的条件，而靠最后一步标记时的结构核对，任何一步做错都会在标记时被拒绝并给出差异。

ADR 0002 要保护的是“碰目标库的 SQL 只能是发布时冻结、验证过的那一份”和“环境处在版本 V 时结构等于 V 的模型”，不是“每个环境都把每份脚本跑一遍”，所以标记不与它冲突；同一个理由排除了修复脚本由 Dowel 代为执行（它是临时 plan 出来的、没验证过的 SQL）。也排除了“执行时发现线上已等于目标就自动只写记录”：只含数据步骤的版本在结构上和父版本相同，会被悄悄跳过；而线上能等于目标本身就意味着已经漂移，自动跳过等于悄悄把漂移合法化。

已知限制：漂移环境落后于链头时（例如 prod 停在 v5 做了热修，链头已到 v7），线上结构不等于任何可发布的版本，只能先按修复脚本改回 v5 再往前执行；“带着漂移往前执行”不做。
