# 版本链与恢复：冻结迁移链、目标库存完整版本、链尾作废、漂移两个出口、恢复时严格验证

- **状态**：已生效（Implemented）
- **领域 / 范围**：版本链的形态与不可变性、目标库迁移历史、链尾版本作废与反悔、漂移处理与“标记为已执行”、接手 / 接入领先环境
- **合并自**：原 ADR 0002（2026-11-18）、0003（2026-11-19）、0004（2026-11-20）、0012（2026-11-21，P6.5）、0013（2026-11-24，取代 Q10 / Q24 与原 M3-B）；相关 Issue / PR：#123、#132、#159
- **重审触发条件**：需要“带着漂移往前执行”；需要模型分支 / 发布前设计评审；首个公开版本发布后要改目标库历史的读语义（届时必须递增 `format_version`）

> **待实现的修订**：[09-per-version-readback-truth.md](09-per-version-readback-truth.md)（已拍板待实现，Issue #201）将让目标库 `dowel.versions` 额外记录写入时的数据库完整版本号与本库读回差异，并让接手 / 接入按每个数据库完整版本号验证。在它的实现 PR 合入之前，本文描述的就是当前 `main` 的行为。

## 1. 迁移在发布时冻结，环境沿版本链逐个执行

发布版本时，从上一个版本生成升级和回滚脚本，验证通过后冻结（发布流水线见 [07-normalization-and-verification.md](07-normalization-and-verification.md) 第 6 节）；之后各个环境沿版本链逐个执行这些冻结的脚本，不在执行时从“环境当前版本”临时规划到目标版本。临时规划 `plan()` 只用于预览和对比任意两个版本。

本节要保护的不变式是：**碰目标库的 SQL 只能是发布时冻结、验证过的那一份**，以及**环境处在版本 V 时结构等于 V 的模型**。它不要求“每个环境都把每份脚本跑一遍”——这是第 3 节“标记为已执行”不与它冲突的原因。

## 2. 目标库里存每个版本的完整内容，丢了平台数据也能接手

Dowel 在目标库里写迁移历史时，不只记“执行到第几版 + 校验和”（Flyway、Alembic、Django 的做法），还存每个版本的完整模型（含对象 ID、名字锁定）和冻结的升级 / 回滚脚本。

- 历史固定放在目标库的独立 schema `dowel` 里（不提供改名；同一个库里的多个项目按项目区分，共用这个 schema）；没有建 schema 的权限时直接报错，不退回到业务 schema；不支持 schema 的数据库用同库里 `dowel_` 前缀的表。
- 历史表只追加（四种方言都有只追加触发器），`versions` 表按 `(project_id, number)` 唯一。
- 代价：生产库里多出 Dowel 自己的数据（只有结构，没有业务数据；PG 会压缩大字段，估计上百个版本也只有几 MB，尚未实测），每次执行多写一行。

## 3. 漂移只有两个出口；“标记为已执行”是通用的特权操作

环境发生漂移（线上结构不等于它当前版本的模型）时，只提供两个出口，生产与非生产行为相同：

1. **保留线上的修改**：用线上结构**覆盖**工作副本（导入），用户检查、修改后按普通流程**发布**新版本（冻结真实的 up / down，影子库验证），再把漂移的环境**标记为已执行**到这个版本；其他环境把它当普通版本执行。
2. **放弃线上的修改**：Dowel 生成修复脚本 `plan(线上结构, 当前版本的模型)`，**只显示、不代为执行**；用户自己执行后重新检查漂移。

**标记为已执行（`mark`）**：

- 可以把环境标记到活跃主链上的任意版本（更新或更早都行）。唯一的硬条件是在目标库项目锁里读出的线上结构等于该版本的模型；不执行任何 SQL，在目标库历史里写一条 `direction = 'mark'` 的记录，向前标记时给目标版本和中间跳过的版本写 `executed_at`。
- 不能标记到已作废版本（第 4 节）。停留在已作废版本上的环境，只要结构一致，可以**跨岔路零 SQL** 标记回活跃主链上的版本；此时“中间跳过的版本”沿 `parent_id` 从最近公共祖先取到目标版本的活跃链段，不卷入无关的已作废版本。
- 不要求目标版本已验证：它在目标库上做的就是结构核对。
- 适用场景：读回失败后手工修好、含非事务步骤的迁移半途失败后手工补完、手工回退了发布、一个空历史的库已经手工建成某个版本的结构等。

**首次执行时的隐式基线**：一个还没有 Dowel 历史的目标库，第一次执行时如果结构已等于链上第一个版本，执行器不运行第一个版本的脚本，只把它作为基线随后续迁移一起写入历史；其后每个要执行的迁移照常检查验证记录（[07-normalization-and-verification.md](07-normalization-and-verification.md) 第 8 节），不为基线另设豁免。如果结构已等于第一个版本、却没有后续迁移可执行，执行器拒绝并引导用户改用“标记为已执行”。不再有单独的“写入基线”入口（#159 移除）。

**已知限制**：漂移环境落后于链头时（例如 prod 停在 v5 做了热修，链头已到 v7），线上结构不等于任何可发布的版本，只能先按修复脚本改回 v5 再往前执行；“带着漂移往前执行”不做。

## 4. 不做模型分支，改用链尾版本作废与画布复制粘贴

Dowel 保持单主干工作副本，不做 Git 风格的模型分支与重放合并引擎。并行改表、发错版本回滚与对象复用，由**链尾版本作废 + 公共祖先切换**与**同方言画布 / 历史 / 跨画布复制粘贴**解决。以后若仍需发布前设计评审，围绕“工作副本 vs 链头 diff”独立评估，不再依赖模型分支。

### 4.1 链尾版本作废（Retire）与公共祖先切换

- **范围**：一次可以作废活跃主链最末尾的一个或多个连续**非首**版本，不区分是否曾在生产环境执行；作废不连目标库，由后续执行预演与审批显式标注 `down` 回滚段兜底。
- **软作废、号段只增**：版本号只增不重用（作废 `v5` 后，基于 `v4` 发布的新版本为 `v6`、`parent = v4`）。作废默认把工作副本回退到该段的父版本（可勾选保留当前工作副本），作为新提交记入画布历史，不丢数据。
- **权限**：被作废段都从未在任何环境执行过时，项目编辑者可作废；任一版本执行过，须项目管理员；所有作废写审计日志。
- **执行与 CI**：Web 端支持基于最近公共祖先的一键混合切换（`down → up`，如 `v5 → v4 → v6`），预演页与执行申请单显式标出回滚段，并同时满足回滚与执行策略；CI 令牌不自动 `down`（返回明确错误码，交人工在 Web 端确认，见 [05-ci-tokens-and-api.md](05-ci-tokens-and-api.md) 第 3 节）。
- **约束**：禁止再执行（`up`）或标记（`mark`）到已作废版本，停在其上的环境只能切回活跃主链或向祖先回滚；关联的未执行申请自动失效；存在执行中的版本时拒绝作废。

### 4.2 反悔与不可回滚时的救回

- **未发新版前一键取消作废**：当且仅当尚未发布任何更新版本（待恢复段恰好是从当前活跃链头连续衔接到全局最大编号的已作废链尾）时，按同级权限一键取消作废、恢复为活跃主链。此前已失效的执行申请不复活；可选是否把工作副本同步切回恢复后的链头；写审计。这样既保持“根到最大编号即活跃主链”的接手不变式，也能原地无损恢复误作废。
- **已发新版后**：旧岔路永久锁定、不可取消作废。版本页为任意版本（含已作废版本）提供一键“应用到画布”（复用画布历史的差异确认与新提交机制）后重新发布；无法承受 `down` 丢数据的环境用第 3 节的跨岔路 `mark` 零停机切回活跃主链。

### 4.3 目标库与接手兼容

- 四种方言的目标库 `dowel.versions` / `dowel.history` 表结构与 `format_version = 1` 保持不变，不新增作废列或 `direction` 枚举。
- 目标库历史链校验与多环境接手合并的分叉判定为：版本号唯一递增 + 合法父链树 + **根到最大编号的唯一路径即活跃主链**（其余岔路自动识别为已作废）；只有同号不同 `version_id` 或多根时判 `history_fork`。
- **不递增 `format_version` 的依据**：允许目标库共存已作废岔路，相对原来的严格线性校验是不兼容的读语义变化；之所以不递增，是因为 Dowel 尚未发布首个公开版本（与 [02-consensus.md](../02-consensus.md) 11.5“发版之前不写任何升级路径，当前格式为 1”一致），不存在旧发行版读取这类历史。首个公开版本发布后，再有此类破坏性变更须递增 `format_version`。
- **自动识别的前提**：“根到最大编号即活跃主链”只在更高编号的新版本已实际写入至少一个参与接手的目标库后成立。若已执行的 `v5` 被作废后、更高编号版本尚未落地任何参与接手的目标库前平台库就丢失了，接手会把 `v5` 恢复为活跃链头；接手后用户可再次作废。

### 4.4 同方言画布 / 画布历史 / 跨画布复制粘贴

- 覆盖当前画布、画布历史、同方言跨项目；支持“单 / 多张表”与“表内列 / 约束 / 索引”两级粒度。
- 粘贴一律生成全新 UUIDv7；同名自动加后缀，绝不静默覆盖；指向未选中的外部既有表的外键按 `(schema, 表, 列)` 自动重连（找不到则跳过并提示）；经正常同步层 mutator 提交。既有老表的零星并发改动由人工补改。

## 5. 接手与接入领先环境强制影子库验证

所有从外部目标库恢复进入平台的冻结版本——新建项目**接手**整条历史链，或已有项目**接入**严格领先于平台链的目标库——都必须在写入平台前经本实例影子库闭环验证通过。验证与发布共用同一套（含读回核对，范围按冻结的 scope），验证结果按影子库的数据库完整版本号记录；恢复进来的版本要执行到某个环境，同样要求有与该目标库完整版本号一致的通过记录（[07-normalization-and-verification.md](07-normalization-and-verification.md) 第 7、8 节）。缺少可用影子库或任一版本验证失败时直接拒绝，并指明具体版本与原因。平台内因此不存在“未验证的恢复版本”，也不需要“批量重新验证”功能。

- **接手向导**：允许为每个环境配置独立影子库连接串，或勾选允许同实例影子库。
- **接入领先环境与工作副本**：目标库历史是平台链的严格延伸（无分叉）且领先版本全部验证通过后，补齐平台版本链并**覆盖工作副本到新链头**。当前工作副本不是链上版本（有未发布草稿）时，必须先展示覆盖前后的差异并经用户确认；回看或找回被覆盖的草稿，通过模型页基于 `room_snapshots` + `room_commits` 的“画布修改历史”（查看单次变更、当时的模型、与当前画布的差异，一键恢复）完成。
- **接手 / 接入直接用链头版本模型作为黄金基线**（#123，见 [07-normalization-and-verification.md](07-normalization-and-verification.md) 第 2 节）：其安全性依赖两道严格读回——执行读回校验与恢复时闭环验证的读回核对。今后放宽其中任何一道，都要重新审视这条路径。
- **不做“撤销认领”**：认领交还统一由原实例的实例管理员主动反向认领，避免单方面把认领权退回给版本链已落后的旧实例。

## 被否决的方案

- **执行时从环境当前版本临时规划到目标版本**：规划器能在任意两个版本之间直接生成迁移，步骤也更少；但 staging 与 prod 实际执行的 SQL 可能不同（比如中间 Dowel 升级了），评审和验证过的脚本不是最终执行的那份，人工修改脚本、插入数据迁移步骤也没地方放。
- **目标库只记版本号 + 校验和**：新实例接手时只能重新读库结构，对象 ID 全部重新生成，下一次改名会被当成先删后加，名字锁定与历史脚本也丢了——这正是 Dowel 区别于按名字比较的工具的地方。
- **专门的“漂移收编”流程**（读出线上结构合并到当前模型，自动发布带特殊标记的版本并直接记为已执行，加一串前置条件）：拆成导入、发布、标记三个已有动作后，不需要特殊版本类型和发布路径；用户能在发布前修正导入结果（例如把按名字识别成“删一列、加一列”的热修改回改名，保住对象 ID，冻结出 `RENAME`）；安全不靠事先的条件，而靠最后一步标记时的结构核对，任何一步做错都会在标记时被拒绝并给出差异。
- **修复脚本由 Dowel 代为执行**：它是临时 plan 出来、没验证过的 SQL，违反第 1 节的不变式。
- **执行时发现线上已等于目标就自动只写记录**：只含数据步骤的版本在结构上和父版本相同，会被悄悄跳过；而线上能等于目标本身就意味着已经漂移，自动跳过等于悄悄把漂移合法化。
- **接手不强制验证，恢复后逐个或批量重新验证**（P4c 原实现）：无影子库或老版本失效时也能先接手，但打破“平台内所有待执行冻结版本都经本实例影子库验证”的不变式，恢复后体验割裂。
- **接入领先环境时保留脏工作副本、只弹警告**：用户容易忘记对齐画布，下一次发布时意外把新链头新增的对象删掉。
- **完整模型分支 + 语义冲突重放合并引擎**：能原生支持多人并行深度修改老表（保留改名意图）与独立分支评审，但正常工程实践以新增表与零星加列 / 加索引为主，随 mutator 与多方言演进维护重放合并与多分支状态机的成本远超收益。
- **物理删除已执行的链尾并重用版本号**：违背目标库留存完整历史以支持接手的原则（第 2 节），打破历史表的只追加触发器与 `versions` 的 `(project_id, number)` 唯一约束，并在多环境接手和沟通中造成同号歧义。
- **目标库新增 `retired_at` 列或 `direction = 'retire'`**：能覆盖 4.3 所述“已执行版本被作废、更高编号版本尚未落地任何目标库时平台库丢失”的窗口（该窗口在无新版落地前没有时间上限），但这种失真只在平台库彻底丢失且无后续版本写入目标库时才发生，且接手后再次作废即可恢复意图；为它让作废动作联网写所有目标库、或改动四方言 DDL 与历史格式版本，得不偿失。
- **无条件支持任意旧岔路取消作废**：已基于父版本发布新版本后再复活旧岔路，会制造双活跃头、连环恢复顺序混乱与工作副本错位。
- **允许作废从未执行过的首个版本**：能原地救回首个版本就坏掉的旧项目，但破坏“版本链单根”的前提；不考虑旧数据后没有必要。
