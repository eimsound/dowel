# 方言保真：按引擎真实语义建模，不用规范化抹平语义差异

- **状态**：已生效（Implemented）
- **领域 / 范围**：各方言的类型与可空性在模型中的表示；目前覆盖 SQLite 列类型（rowid 别名、STRICT、无类型列）与 SQL Server 持久化计算列的显式 / 推断非空
- **合并自**：原 ADR 0018（2026-11-27，Issue #140、#141 方案 ③）、原 ADR 0019（2026-11-28，Issue #161，来源 PR #157）
- **重审触发条件**：发现新的“写法不同但被当作相同”或“系统目录分不出两种声明”的方言语义；SQL Server 提供能区分显式与推断非空的系统目录信息

## 原则

按每种方言**真实的数据库语义**建模，不用规范化去抹平差异。规范化只允许改变不影响语义的写法（与 [07-normalization-and-verification.md](07-normalization-and-verification.md)“版本模型里只存数据库的写法”一致）。比较时不加任何容忍。

## 1. SQLite：列类型按声明原样保留

**背景**：原先把 `int` / `bigint` / `bool` / `boolean` 等折叠成 `INTEGER`、`varchar` / `clob` 折成 `TEXT`、`double` / `float` 折成 `REAL`、`decimal` 折成 `NUMERIC`，空类型在不同位置分别是 `''`、`TEXT`、`ANY`。这些写法在 SQLite 里并不等价：

- **rowid 别名**：只有声明类型恰为 `INTEGER` 的单列主键才是 rowid 别名。`INT` / `BIGINT PRIMARY KEY` 不是：非 STRICT 表里能存 `NULL` 和非整数值，也不能加 `AUTOINCREMENT`。折叠后任何一次 12 步重建都会静默把主键变成 rowid 别名，存量有非整数值时拷贝数据直接 `datatype mismatch`（#140）。
- **亲和性**：`BOOLEAN` 是 NUMERIC 亲和性而不是 INTEGER；非 STRICT 表里不写类型的列是 BLOB 亲和性（值原样保存），`ANY` 是 NUMERIC 亲和性，`TEXT` 是 TEXT 亲和性——三者不是同一列。
- **三套口径**：模型、规范化、读回各给一种空类型，规划器必然要重建，执行读回必然 `readback_mismatch`（#141）。

**决定**：

1. **类型规范化只做不改语义的写法统一**：去首尾空白、压缩连续空白、整体大写；整段是一个带引号的普通类型名时去掉引号（与引擎读回一致）。不再有任何别名折叠（`bigint` 存为 `BIGINT`、`boolean` 存为 `BOOLEAN`、`varchar(255)` 存为 `VARCHAR(255)`）。函数幂等，模型写入与引擎读回走同一个函数。
2. **rowid 别名由声明类型决定**：`INTEGER` 单列主键是 rowid 别名并可用 `AUTOINCREMENT`；`INT` / `BIGINT` 等单列主键按原类型保留，建表与 12 步重建都输出原类型。IR 不另设 rowid 标记。`AUTOINCREMENT` 的写入校验与模型校验仍要求类型为 `INTEGER`。
3. **STRICT 白名单按真实规则**：`INT`、`INTEGER`、`REAL`、`TEXT`、`BLOB`、`ANY`（不区分大小写）；`BIGINT`、`BOOLEAN` 等别名不再因折叠被放行。
4. **非 STRICT 表保留无类型列**：`type: ''` 是合法的 SQLite 列定义，模型、规范化、快照读回、规划器与建表 / 重建 DDL（省略类型）统一为 `''`；所有写入入口都可以写入（宏需显式传空字符串，省略仍报缺少类型）。
5. **STRICT 表继续拒绝无类型列**：写入、模型校验、给含无类型列的表开启 STRICT，都报错并说明 STRICT 只接受上述六种类型。其他方言的空类型规则不变（PG 枚举列 `typeRef` + `''` 仍表示非数组枚举）。

**边界**：只改 SQLite，其他方言的类型规范化不变。带引号且不是整段普通类型名的写法不做特殊处理，差异由验证的读回核对暴露。

## 2. SQL Server：持久化计算列的显式 NOT NULL 与引擎推断的非空分开存

**背景**：SQL Server 按表达式推断持久化计算列是否可空（`cp AS ([code]) PERSISTED` 在 `code` 非空时读回不可空）。原先模型只有一个 `notNull`，规范化把推断结果写回 `notNull`，规划器又把它渲染成 `PERSISTED NOT NULL`；被引用列改回可空后，迁移仍带着用户从没写过的 `NOT NULL`，目标库插不进 NULL 行。实测（SQL Server 2022）系统目录对“推断非空”与“显式 `PERSISTED NOT NULL`”完全一样，也没有对应的约束对象，分不出两者。

**决定**：

1. **两个字段**：`notNull` 只表示用户显式声明的 `PERSISTED NOT NULL`，生成 DDL 只看它；`ext.mssql.inferredNotNull` 表示引擎从表达式推断为非空，**只由影子库规范化写回**，从不渲染进 DDL，写入入口忽略调用方传入的值。普通列、非持久化计算列不用这个字段。
2. **有效可空性** = `notNull || inferredNotNull`。规划器按它比较（显式与推断互换、有效值不变时不生成迁移）；执行读回校验复用规划器，同样按它严格比较；主键校验也按有效可空性。
3. **推断值与影子库构建路径无关**：读回可空时推断必为 false；读回非空时，只有该列在本次构建中确定以非显式方式从零新建时才直接取读回值，其余情形（显式声明，或所在表已在基线中、增量迁移后物理列可能保留基线的显式 `NOT NULL`）在影子库同表临时加一个同表达式的**非持久化**计算列，读它的可空性再删掉（实测持久化与非持久化计算列的推断结果一致）。显式 `notNull` 永不被改写。
4. **导入与拉取（影子库探测拆分）**：系统目录分不出显式与推断，读结构时先一律记成推断，再拆分：
   - **主键成员**：一律记成显式非空，不探测（见第 7 条）。
   - **其余读回非空的持久化计算列**：在影子库里按模型建库（这些列与主键成员都按显式 `NOT NULL` 建，主键与引用它们的约束才建得出来），再用第 3 条的临时列探测表达式本身的推断——推断为可空记成显式，推断为非空记成推断。模型里没有这样的列时不连影子库。
   - **没有可用的影子库**（没配置、生产不允许同实例、连不上、建不出模型）：不拦下导入 / 拉取，这些列全部记成显式，并在结果里列出受影响的列；影子库可用后用户可自行取消勾选。
   - 覆盖范围：向导“从已有数据库”（冻结基线之前拆分，与基线验证共用同一个影子库）；“保留线上的修改”只拆分不能从工作副本沿用的列。漂移检查、标记核对、执行读回只比较不写模型，不需要拆分；接手、接入领先版本用版本模型；从 SQL 导入时影子库导入已经探测。
5. **待规范化判定**：列自己的推断值相对基线变了也算待规范化；列自己的显式 `notNull` 变了仍算（旧规则写回的存量基线没有推断值，借此补算）。稳态仍是 0 影子库 I/O（[07-normalization-and-verification.md](07-normalization-and-verification.md) 第 3 节）。
6. **界面**：“非空”复选框只绑显式 `notNull`；只由推断得出非空时不勾选，显示只读提示；列表按有效值显示，推断的另行区分。
7. **主键例外**：建主键（以及导入 / 拉取时的主键成员）视为对主键列显式声明非空。在只由推断得出非空的计算列上建主键，会把它设为显式 `notNull: true`；之后被引用列改成可空，主键列仍保持非空，不会因推断变化而失去主键的前提。导入的基线因此在影子库里总能建出来。

**影响**：

- 旧规则写回过 `notNull: true` 的列按显式处理，DDL 与以前相同；用户取消勾选后触发一次规范化补上推断值，有效值不变时不生成迁移。
- 从已有数据库导入 / 拉取会多一次影子库访问（只在有读回非空、非主键的持久化计算列时）；没有影子库时按显式记录，最坏情况只是多一个用户可以取消的 `NOT NULL`。
- `ext.mssql` 只被 SQL Server 方言读取；粘贴不跨方言，同方言粘贴的列不带推断值，由下一次规范化算出。

## 被否决的方案

- **SQLite 继续折叠类型别名，比较时视为等价**：语义上不等价（rowid 别名、亲和性），折叠会在重建时静默改变主键语义。
- **SQL Server 只用一个字段，读回比较时把推断值当等价**：规划器仍会把写回的推断值渲染成 `NOT NULL`，问题原样存在；而且是比较时容忍。
- **规范化不写回推断值**：模型可空、读回非空，读回校验报不一致，推断非空的列永远执行不了。
- **导入时用 `sys.dm_exec_describe_first_result_set` 在目标库上只读推断表达式**：不需要影子库，但它推断的是查询结果集的可空性，不是计算列自己的推断路径，两者一致只是实测结论；不接受这种不一致的风险，任何路径（包括兜底）都不使用它。
- **导入时一律记成推断**：“显式声明在可空表达式上”的列（主键常见）会在下一次规范化时被写回为可空，迁移把它重建成可空，作主键时整个分支无法规范化。
- **没有影子库时拦下导入 / 拉取**：结果最准确，但生产默认不允许同实例影子库，会让“从生产库新建项目”不可用。
