# 审批按提交时的流程快照走、资格按审批时判断；审批不给执行权；申请人不能自批

2026-11-20 决定（P5b，E4 / E5）。审批流程的数据结构和“只能追加”的合并规则见 [ADR 0005](0005-execution-policy-layers.md)；这里定的是运行规则。实现：`apps/server/src/requests.ts`、`routes/requests.ts`，用户文档 `docs/approvals.md`。

**流程快照，变严即失效。** 申请提交时把当前生效的审批流程（各层环节拼接的结果；没有环节时记为“默认流程”）快照进申请。之后审批按快照的环节和人数走。策略中途变化时，在锁内重新算当前生效流程：如果快照**包含**当前流程（ADR 0005 的子序列偏序：当前流程不比快照严），申请继续按快照走——变宽不会让已经提交的申请少走环节；如果当前流程**变严**（多了环节、换了环节、人数变了，即快照不再包含它），申请失效，要按新流程重新提交。考虑过两种简单方案：“完全按快照走”会让上级事后追加的环节对已提交的申请不起作用（上级收紧的意图被绕过）；“策略一变就失效”会让与审批无关的改动（比如改超时）也打断进行中的审批。现在的规则对收紧是保守的，对无关改动和放宽不打扰，判断用的就是 ADR 0005 已经有的偏序，不用新概念。默认流程的快照只有当前也没有配置环节时才成立。

**资格按审批时的成员关系。** 审批人范围（组管理员、项目管理员、执行者、指定组成员 / 组管理员、指定用户、默认流程的“有执行权限的人”）在审批的那一刻、在执行策略锁里重新读成员关系、授权和项目当前所属的组再判断。提交之后被移出组、撤掉授权的人不能再批（快照里存的是范围，不是名单）。审批人还必须能看到这个项目（P1 的可见性规则），看不到的人既不通知也不能批——否则通知里会泄露项目的存在。

**审批不给执行权。** 不管流程怎么配置，真正执行的人（“通过并执行”的最后一个审批人，或全部通过后点“执行”的人）都要满足环境生效的“谁能执行”（或是执行者）。路线图原文是“全部通过后由申请人或有执行权的人点执行”，我们把它收窄为“有执行权的人（申请人自己有执行权时也可以）”。理由：ADR 0005 把“追加环节”算作收紧、下级可以随意追加；如果审批能代替执行权，一个项目管理员就可以在组层设了“仅限执行者”的环境上追加一个“指定用户 = 我的同事”的环节，让没有执行权的开发提交、同事批准、开发自己执行——追加环节反而成了放宽，ADR 0005 的单调性就不成立了。现在的规则下，审批流程只会多加限制，“谁能执行”决定谁能碰目标库，两者正交；默认流程（“无权者提交，有权者通过并执行”）也自然落在这条规则里：默认环节的审批人就是有执行权的人。代价：没有执行权的申请人在全部通过后要等有执行权的人来执行（会收到“待你执行”的通知）。

**「最后一个审批人即执行者」** 的含义是凑够最后一个环节的那一次通过必须同时执行（“通过并执行”，同一个事务里先通过、再转为执行中），因此这一步要求执行权；单独“通过”会被拒绝。没设标记时，全部通过后任何有执行权的人都可以执行。执行失败而绑定仍然成立时（例如锁等待超时，事务整体回滚），任何有执行权的人都可以重试。

**申请人不能审批自己的申请。** 四眼原则：申请人往往本身就在审批人范围里（项目管理员申请，审批人是项目管理员；默认流程里有执行权的人也可以提交申请），允许自批就等于一个人完成了全部流程。系统不限制同一个人批多个环节，但每个环节单独确认（请求里带环节号，必须等于当前环节，一次只推进一个环节），配置页提示范围可能重叠的环节。

**放宽策略本身不走审批（P5a 遗留的决定）。** 保持 P5a 的规则：放宽是特权操作，要这一层的管理员，并且满足这一层改动前生效的“谁能执行”；所有策略修改都在执行策略锁里、严格审计。不走审批的理由：审批绑定的是“某个环境从版本 A 执行到版本 B”这件事，策略修改没有对应的绑定对象；让放宽也走审批要回答“用哪一层、改之前还是改之后的流程审批策略本身”，会形成递归；而“不是执行者的管理员撤掉仅限执行者”这个风险已经由 P5a 的规则堵住。放宽对已提交申请的影响见上面的快照规则（变宽不影响已提交的申请）。

**紧急执行不绕过前置环境。** 只有实例管理员，绕过审批流程，必填原因、二次确认、审计，通知该环境审批流程里所有现在有资格的审批人。漂移、完整性、认领、已验证和前置环境检查都照常做（先预演，不通过就拒绝）。前置环境保护的是“没在上游验证过的版本不能上生产”，紧急情况最常见的是回滚，而回滚本来就豁免前置环境；真的要跳过前置环境的向前执行，实例管理员可以先改环境的前置环境设置——那是一次有审计的放宽，不需要再开一条更宽的通道。紧急执行记成一条 `emergency = true` 的申请（状态直接是“执行中”），复用申请的详情页、时间线和通知；**结果**（成功、失败、执行器判为状态已变）同样通知审批人并发 Webhook。**紧急执行的记录不走申请的流程**（第一轮审查补上）：它失败之后不能经申请的“执行 / 重试”重试——那等于让任何有执行权的人在不经审批的情况下再执行一次——也不能撤回；要再来一次就重新发起紧急执行（实例管理员，重新填原因、重新预演）或者提交执行申请。

**锁。** 审批、驳回、撤回、转为执行中、执行结束、定时检查都在执行策略锁（ADR 0005 的 `withPolicyLock`）里，锁内重新读申请、策略、成员关系和环境状态。真正的执行在锁外（拿环境锁和目标库项目锁，不能在全局锁里连外部库）；“执行中”这个状态保证同一个申请不会执行两次，绑定的最终核对在目标库锁里做（见 ADR 0007）。执行要用到的一切（项目、环境行、生效策略、前置环境检查、生产环境名）都在转成“执行中”的同一个锁内事务里准备好；转成“执行中”之后任何没能开始执行的失败都走同一个结束处理转成执行失败，申请不会停在“执行中”（第一轮审查）。
