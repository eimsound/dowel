# 执行策略按四层逐层取更严，审批流程只能追加，放宽是特权操作

2026-11-20 决定（P5a；2026-11-21 修订：已移除「前置环境」功能，不同环境彼此独立）：执行策略（谁能执行、审批流程、允许令牌执行、语句超时、锁等待超时）在实例 → 组 → 项目 → 环境四层配置，实例 / 组 / 项目层各有生产、非生产两套，环境层只有它自己一套（按生产标记合并上级的那一套）。**未设置 = 继承，合并 = 逐层取更严**，每个字段都有明确的严格程度：谁能执行“仅限执行者 > 项目管理员 > 项目编辑者”，允许令牌“不允许 > 允许”，两个超时“越短越严，0 = 不限最宽”。标量字段的合并就是在这些全序上取最大值，所以合并结果一定不弱于任何一层的显式设置；写入时再拒绝比上级下限更宽的值（422），界面把上级的下限显示为锁定。

**审批流程没有自然的全序**，用“子序列”偏序：F ⪯ G 当且仅当 F 的环节按原顺序全部出现在 G 里。每层存的是**本层追加的环节**，生效流程是各层环节按层序拼接，上级的生效流程因此总是下级生效流程的前缀，下级在结构上就删不掉、改不了上级的环节，不需要写入校验。「最后一个审批人即执行者」不参与比较（它决定谁按执行按钮，不是要几个人同意），拼接后只有最后一个环节上的标记生效。考虑过“下级整个替换流程，校验必须以上级流程为前缀”，放弃的原因是上级之后改了流程，下级存的旧流程就不再合法，需要级联修复；追加式存储没有这个问题。

**超时越短越严**：超时保护的是目标库上的业务——DDL 在等锁时，后面所有访问这张表的语句都排在它后面，越早放弃越安全。默认锁等待 5 秒（足以等过普通短事务，对业务是可以容忍的停顿，超时可直接重试，断点续跑不变），语句不限（大表上的建索引、改类型本来就慢，中途被杀既浪费又可能留下要清理的东西）。审查后补充三条：① 策略里“不限”的项**不设置**，恢复用 `RESET` 而不是设成 0——库端（`ALTER DATABASE / ROLE … SET`）已有的超时照常生效，Dowel 只能收紧、不能替库放宽，读回校验和写历史也跑在库端原来的设置上；② `CREATE / DROP INDEX CONCURRENTLY`、`REINDEX … CONCURRENTLY`（含 PG 14 起的 `REINDEX (CONCURRENTLY …)` 括号写法、含重试前清理遗留无效索引；判断先去掉注释和字符串，见 `@dowel/core` 的 `isConcurrentDdlSql`）**不设 `lock_timeout`**；`ALTER TABLE … DETACH PARTITION … CONCURRENTLY` **不豁免**——它的第二阶段要对分区拿 ACCESS EXCLUSIVE，排队时一样挡业务（第三轮审查改正）。它的第一个事务提交（分区标成 detach pending）之后，等旧事务结束和第二阶段拿锁都可能超过 `lock_timeout`（前者更常见），超时后分区停在 detach pending，原语句重跑会报 already pending detach；所以续跑这一步时执行器先查 `pg_inherits.inhdetachpending`，是就改为执行 `ALTER TABLE 父表 DETACH PARTITION 分区 FINALIZE`（同样受锁等待超时约束、可以反复重试），迁移不会卡死（第四轮审查补上）。只有执行器解析不出这条语句（没写 schema 等）时才需要人工 FINALIZE：它们只拿 SHARE UPDATE EXCLUSIVE，不阻塞读写，等的是旧事务结束，不会把业务堵在后面——`lock_timeout` 要防的正是后者；如果照设，有长事务的生产库上默认 5 秒会让它反复失败并留下 INVALID 索引，清理那一步也同样失败；③ 语句超时对它们照常生效。

**默认值不是下限**：上级都没设置时，下级可以设得比默认更宽（和 H6 一致：项目管理员能把生产环境设成“项目编辑者”）。要禁止，就在上级显式设置。否则 P4b 的现有行为会被改变，也会让默认值变成无法撤销的约束。

**改策略：收紧不是特权操作，放宽是。** 放宽（任一字段变宽、审批流程不再包含原流程）削弱了环境保护，按 GLOSSARY 的定义就是特权操作：除了这一层的管理身份，操作者还要满足这一层改动之前生效的“谁能执行”。否则一个不是执行者的组管理员 / 项目管理员可以先撤掉“仅限执行者”再自己执行，“仅限执行者”就形同虚设。代价是设成“仅限执行者”之后，放宽要找执行者或实例管理员（配置页有提示）。改生产标记换了一套上级设置时，变宽的字段固定成原来的生效值，不能借改标记放宽；**项目转组**换掉组层时同样处理（审查后补上：原来转组会悄悄放宽）——选“固定”而不是“把转组当成放宽、要求满足原生效的谁能执行”，理由是和改生产标记同一条规则、转组本身已经要求两边组管理员，而且固定之后生效策略完全不变，之后真要放宽再按放宽的规则在环境层改；新建的环境才按新组合并。组范围的授权（含执行者）跟着范围走，转组后对这个项目失效。

**写入是原子的**（审查后）：所有策略写入（四层配置、改生产标记、转组时的固定）都在一把“执行策略锁”的事务里读当前值、校验、写入、写审计——PG 用事务级 advisory lock 全局串行（量很小，一把锁也覆盖跨层组合），SQLite 的平台库事务本来就互斥。考虑过按版本号 compare-and-swap（冲突返回 409）：要给每层加版本列、界面要处理 409 重试，而串行化之后后到的请求直接按最新状态判断（放宽就 403、不合法就 422），对用户更直接。环境层只有一条写入路径（`applyEnvPolicy`），`PATCH …/environments/:eid` 和 `PUT …/exec-policy` 共用。**锁内用到的一切都在锁内重新读**（第二轮审查）：环境行（含生产标记）、四层配置、项目当前所属的组、调用者的组成员关系 / 授权 / 项目角色；锁外读到的只用来做不写任何东西的预检。否则等锁期间别人转了组或改了生产标记，锁内会拿旧的组层校验、拿旧的生产标记决定要不要检查“取消生产标记”。

**执行者在任何档位都能执行**（档位决定的是项目角色能不能执行），执行者授权自带项目的只读可见性，不带模型编辑权限。“仅限执行者”的生产环境只认**授权时授予者是实例管理员**的执行者授权（`grants.by_instance_admin`，授权时记下、之后不变）：这样策略之后才收紧成“仅限执行者”时，原来由项目管理员授予的执行者自动不算，不用在收紧时检查或清理已有授权。

**存储**：`exec_policies(scope_kind, scope_id, policy json)` 每个范围一行，字段不出现 = 继承；H6 的 `environments.exec_policy` 搬进环境层的 `whoCanExecute` 后删除这一列（只留一个事实来源）。~~原 `environments.prerequisite_id` 前置环境列于 2026-11-21 决策移除。~~合并、比较、校验都是 `@dowel/api` 的纯函数，服务端和界面共用；库里的策略解析不了时拒绝（500），不当作“没设置”，免得被改坏的“仅限执行者”变成默认档位。以后加字段时：标量字段要先定义全序再加进 `SCALAR_FIELDS`，非全序的字段要给出可证明单调的合并方式（像审批流程这样），否则“只能收紧”的随机测试会失败。
