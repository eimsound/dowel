# 执行治理：四层策略单调收紧、审批按快照走且不给执行权、申请绑定以目标库为准

- **状态**：已生效（Implemented）
- **领域 / 范围**：执行策略（谁能执行、审批流程、令牌执行、超时、申请有效期）的四层合并与修改规则；审批运行规则与紧急执行；执行申请的绑定与失效
- **合并自**：原 ADR 0005（2026-11-20，P5a）、0006（2026-11-20，P5b，E4 / E5）、0007（2026-11-20，P5b，E3）；用户文档 `docs/{zh,en}/execution-policy.md`、`approvals.md`
- **重审触发条件**：新增一个执行策略字段（必须先给出全序或可证明单调的合并方式）；需要让 CI 令牌受 `whoCanExecute` / 审批约束（见 [05-ci-tokens-and-api.md](05-ci-tokens-and-api.md) 第 10 节）；策略写入量增长到全局串行锁成为瓶颈

## 1. 执行策略按四层逐层取更严

执行策略在**实例 → 组 → 项目 → 环境**四层配置。实例 / 组 / 项目层各有生产、非生产两套，环境层只有自己一套（按生产标记合并上级的那一套）。不同环境彼此独立。

### 1.1 标量字段：未设置即继承，合并即取更严

每个标量字段都定义了严格程度的全序，合并就是在全序上取最大值，所以合并结果一定不弱于任何一层的显式设置：

- 谁能执行：仅限执行者 > 项目管理员 > 项目编辑者；
- 允许令牌执行：不允许 > 允许；
- 语句超时、锁等待超时：越短越严，“不限”最宽；
- 申请有效期（`requestTtlHours`）：越短越严，没有“不限”（1～720 小时，默认 24）。批准绑定的是提交时的状态，拖得越久，审批人看到的与执行时的实际差得越远。

写入时拒绝比上级下限更宽的值（422），界面把上级的下限显示为锁定。

**默认值不是下限**：上级都没设置时，下级可以设得比默认更宽（例如项目管理员能把生产环境设成“项目编辑者”）。要禁止就在上级显式设置；否则默认值会变成无法撤销的约束。

### 1.2 审批流程：只能追加的子序列偏序

审批流程没有自然的全序，用“子序列”偏序：F ⪯ G 当且仅当 F 的环节按原顺序全部出现在 G 里。每层只存**本层追加的环节**，生效流程是各层环节按层序拼接；上级的生效流程因此总是下级生效流程的前缀，下级在结构上就删不掉、改不了上级的环节，不需要写入校验。

“最后一个审批人即执行者”不参与比较（它决定谁按执行按钮，不是要几个人同意），拼接后只有最后一个环节上的标记生效。

### 1.3 超时越短越严，以及 `lock_timeout` 的豁免

超时保护的是目标库上的业务：DDL 在等锁时，后面所有访问这张表的语句都排在它后面，越早放弃越安全。默认锁等待 5 秒（足以等过普通短事务，超时可直接重试，断点续跑不变），语句不限（大表建索引、改类型本来就慢，中途被杀既浪费又可能留下要清理的东西）。

- **“不限”即不设置**：恢复用 `RESET` 而不是设成 0。库端（`ALTER DATABASE / ROLE … SET`）已有的超时照常生效，Dowel 只能收紧、不能替库放宽；读回校验和写历史也跑在库端原来的设置上。
- **`CONCURRENTLY` 索引操作不设 `lock_timeout`**：`CREATE / DROP INDEX CONCURRENTLY`、`REINDEX … CONCURRENTLY`（含 PG 14 起的括号写法，含重试前清理遗留的无效索引；识别时先去掉注释和字符串）。它们只拿 SHARE UPDATE EXCLUSIVE，不阻塞读写，等的是旧事务结束，不会把业务堵在后面——而这正是 `lock_timeout` 要防的；照设的话，有长事务的生产库上默认 5 秒会让它们反复失败并留下 INVALID 索引，清理那一步也同样失败。语句超时对它们照常生效。
- **`ALTER TABLE … DETACH PARTITION … CONCURRENTLY` 不豁免**：它的第二阶段要对分区拿 ACCESS EXCLUSIVE，排队时一样挡业务。第一个事务提交（分区标成 detach pending）之后，等旧事务结束或第二阶段拿锁都可能超过 `lock_timeout`，超时后分区停在 detach pending、原语句重跑会报 already pending detach。因此续跑这一步时执行器先查 `pg_inherits.inhdetachpending`，是就改为执行 `ALTER TABLE 父表 DETACH PARTITION 分区 FINALIZE`（同样受锁等待超时约束、可反复重试），迁移不会卡死。只有执行器解析不出这条语句（例如没写 schema）时才需要人工 FINALIZE。

### 1.4 收紧不是特权操作，放宽是

放宽（任一字段变宽，或审批流程不再包含原流程）削弱环境保护，按 GLOSSARY 的定义是特权操作：除了这一层的管理身份，操作者还要满足这一层**改动之前**生效的“谁能执行”。否则一个不是执行者的组管理员 / 项目管理员可以先撤掉“仅限执行者”再自己执行。代价是设成“仅限执行者”之后，放宽要找执行者或实例管理员（配置页有提示）。

- **改生产标记**换了一套上级设置时，变宽的字段固定成原来的生效值，不能借改标记放宽。
- **项目转组**换掉组层时同样固定：与改生产标记同一条规则；转组本身已要求两边组管理员；固定之后生效策略完全不变，之后真要放宽再按放宽规则在环境层改。新建的环境才按新组合并。组范围的授权（含执行者）跟着范围走，转组后对这个项目失效。
- **放宽本身不走审批**：审批绑定的是“某环境从版本 A 执行到版本 B”，策略修改没有对应的绑定对象；让放宽走审批要回答“用哪一层、改之前还是改之后的流程来审批策略本身”，会形成递归；而“非执行者的管理员撤掉仅限执行者”的风险已由上面的规则堵住。放宽对已提交申请的影响见第 2.1 节。

### 1.5 写入原子、锁内重读

所有策略写入（四层配置、改生产标记、转组时的固定）都在一把全局“执行策略锁”的事务里读当前值、校验、写入、写审计：PG 用事务级 advisory lock 全局串行（写入量很小，一把锁也覆盖跨层组合），SQLite 的平台库事务本来就互斥。环境层只有一条写入路径，改环境与改环境策略两个接口共用它。

**锁内用到的一切都在锁内重新读**：环境行（含生产标记）、四层配置、项目当前所属的组、调用者的组成员关系 / 授权 / 项目角色。锁外读到的只能用于不写任何东西的预检；否则等锁期间别人转了组或改了生产标记，锁内会拿旧的组层校验。

### 1.6 执行者授权

执行者在任何档位都能执行（档位决定的是项目角色能不能执行）；执行者授权自带项目的只读可见性，不带模型编辑权限。“仅限执行者”的生产环境只认**授权时授予者是实例管理员**的执行者授权（授权时记下、之后不变）：策略之后才收紧成“仅限执行者”时，原来由项目管理员授予的执行者自动不算，不用在收紧时检查或清理已有授权。

### 1.7 存储与扩展

- 每个范围一行策略 JSON，字段不出现即继承；环境的“谁能执行”只有这一个事实来源。
- 合并、比较、校验是 `@dowel/api` 的纯函数，服务端和界面共用。
- 库里的策略解析不了时拒绝（500），不当作“没设置”，免得被改坏的“仅限执行者”变成默认档位。
- 以后加字段：标量字段先定义全序；非全序字段要给出可证明单调的合并方式（像审批流程这样），否则“只能收紧”的随机测试会失败。

## 2. 审批运行规则

### 2.1 流程快照，变严即失效

申请提交时把当前生效的审批流程（各层环节拼接的结果；没有环节时记为“默认流程”）快照进申请，之后按快照的环节和人数走。策略中途变化时在锁内重新算当前生效流程：

- 快照**包含**当前流程（按第 1.2 节的子序列偏序，当前流程不比快照严）→ 继续按快照走，变宽不会让已提交的申请少走环节；
- 当前流程**变严**（多了环节、换了环节、人数变了，即快照不再包含它）→ 申请失效，按新流程重新提交。

默认流程的快照只有当前也没有配置环节时才成立。

### 2.2 资格按审批时的成员关系

审批人范围（组管理员、项目管理员、执行者、指定组成员 / 组管理员、指定用户、默认流程的“有执行权限的人”）在审批那一刻、在执行策略锁里重新读成员关系、授权和项目当前所属的组再判断。快照里存的是范围不是名单，提交后被移出组、撤掉授权的人不能再批。审批人还必须能看到这个项目；看不到的人既不通知也不能批，否则通知会泄露项目的存在。

### 2.3 审批不给执行权

不管流程怎么配置，真正执行的人（“通过并执行”的最后一个审批人，或全部通过后点“执行”的人）都要满足环境生效的“谁能执行”（或是执行者）；申请人自己有执行权时也可以执行。

理由：第 1.2 节把“追加环节”算作收紧，下级可以随意追加。如果审批能代替执行权，项目管理员就可以在组层设了“仅限执行者”的环境上追加一个“指定用户 = 我的同事”的环节，让没有执行权的开发提交、同事批准、开发自己执行——追加环节反而成了放宽，单调性就不成立了。现在审批流程只会多加限制，“谁能执行”决定谁能碰目标库，两者正交；默认流程（无权者提交，有权者通过并执行）也自然落在这条规则里。代价：没有执行权的申请人在全部通过后要等有执行权的人来执行（会收到“待你执行”的通知）。

### 2.4 “最后一个审批人即执行者”

凑够最后一个环节的那一次通过必须同时执行（同一个事务里先通过、再转为执行中），因此这一步要求执行权，单独“通过”会被拒绝。没设标记时，全部通过后任何有执行权的人都可以执行。执行失败而绑定仍然成立时（例如锁等待超时、事务整体回滚），任何有执行权的人都可以重试。

### 2.5 申请人不能审批自己的申请

四眼原则：申请人往往本身就在审批人范围里，允许自批就等于一个人完成全部流程。系统不限制同一个人批多个环节，但每个环节单独确认（请求带环节号，必须等于当前环节，一次只推进一个环节），配置页提示范围可能重叠的环节。

### 2.6 紧急执行

- 只有实例管理员可以发起，绕过审批流程；必填原因、二次确认、审计，并通知该环境审批流程里所有当前有资格的审批人。
- 漂移、完整性、认领和验证记录检查照常做（先预演，不通过就拒绝）。
- 记成一条 `emergency = true` 的申请（状态直接是“执行中”），复用申请的详情页、时间线和通知；结果（成功、失败、状态已变）同样通知审批人并发 Webhook。
- **紧急执行的记录不走申请流程**：失败后不能经申请的“执行 / 重试”再来（那等于让任何有执行权的人不经审批再执行一次），也不能撤回；要再来一次就重新发起紧急执行（重新填原因、重新预演）或提交执行申请。

### 2.7 锁

审批、驳回、撤回、转为执行中、执行结束、定时检查都在执行策略锁里，锁内重新读申请、策略、成员关系和环境状态。真正的执行在锁外（拿环境锁和目标库项目锁，不能在全局锁里连外部库）；“执行中”状态保证同一个申请不会执行两次，绑定的最终核对在目标库锁里做（第 3.4 节）。执行要用到的一切都在转成“执行中”的同一个锁内事务里准备好；转成“执行中”之后任何没能开始执行的失败都转成执行失败，申请不会停在“执行中”。

## 3. 执行申请的绑定与失效

### 3.1 绑定什么

提交前先跑一次预演（与直接执行前完全相同的检查），预演的计划就是申请绑定的内容：起始版本（提交时环境的当前版本，可以为空）、目标版本和方向、要执行的迁移列表（版本、方向、顺序）和每个版本的校验和；另外记下提交时的生产标记、连接串指纹和审批流程快照。审批人看到的就是这些，批准的也只是这些。

- **绑定预演用的那一份校验和**：预演在锁外，写入申请在锁内。锁内读到的校验和与预演时不同（预演之后脚本被改了）就 409、让用户重新预演，而不是绑定锁内新读到、没预演过的那份。
- **连接串指纹是带密钥的 HMAC**：连接串里有密码，无盐 SHA-256 可以离线撞出来；改用从 `DOWEL_SECRET` 按用途派生密钥的 HMAC-SHA256。`DOWEL_SECRET` 换了、解不开连接串时用密文的摘要（不泄露任何东西，之后再改连接串密文一定会变）。

### 3.2 失效条件

有效期过了 → 过期。环境当前版本 ≠ 起始版本、检测到漂移、生产标记变了、连接串变了、目标版本或绑定的任一版本不存在、任一版本的校验和变了、生效审批流程变严 → 失效。每个失效都带给人看的原因（例如“环境的当前版本变了：提交时是 v1，现在是 v2”）。

### 3.3 为什么失效而不是重新绑定

环境状态变了以后，原来的批准对应的是另一组迁移（起点不同，要执行的迁移就不同），自动换绑等于替审批人批准了他们没看过的东西。重新提交的成本是再走一遍审批，这正是审批要的效果。

### 3.4 三处判定，最终以目标库历史为准

1. **审批 / 驳回 / 执行前**：在执行策略锁里重新读环境、版本、策略后判定；失效就在同一个事务里把申请转为终态，请求返回 409。
2. **定时检查与按范围的快速检查**：定时检查（每 30 秒，覆盖全部未结束的普通申请；失败 / 中断的紧急执行记录是终态，不再检查）与“按范围的快速检查”（执行 / 标记结束、漂移检查、读历史同步、改脚本、改环境、改策略、转组时显式带上受影响的范围，合并成一轮，进行中又来的会再跑一轮、不会丢）把失效 / 过期的申请转为终态并通知申请人。这只为及时通知，正确性不依赖它。检查分两步：先在锁外只读地找出绑定已不成立的申请（多数时候一个都没有，不拿全局锁），再在锁内重读、重判、条件更新；详情页打开时的检查同样如此。
3. **执行时**：执行器在**目标库的项目锁**里、写任何东西之前，按目标库自己的历史核对当前版本、算出的迁移列表和校验和；不一致就报 `request_stale`，什么都不写，申请转为失效。

**为什么必须有第 3 处**：前两处用的是平台库里的缓存（环境当前版本、漂移结果），缓存可能落后于目标库——别的实例执行过、有人绕过 Dowel 写了历史、上一次同步失败。目标库历史才是事实来源（[02-version-chain-and-recovery.md](02-version-chain-and-recovery.md) 第 2 节），所以最终判定放在执行器里、目标库锁内。它也覆盖并发：审批和直接执行同时发生时，两者都要拿环境锁和目标库项目锁，后执行的那个看到的当前版本已经变了——直接执行变成空操作或按新起点执行，申请则 `request_stale` 失效，目标库只会被执行一次。库已经在目标版本（别人先执行到了）也算不一致：不能把“什么都没做”当作申请执行成功。

### 3.5 执行失败后的状态

执行失败（脚本报错、锁等待超时……）记为“执行失败”，不是终态：绑定仍然成立时（事务整体回滚，或非事务步骤停在断点、当前版本没变）可以重试，断点续跑语义不变；执行了一部分、当前版本已经变了的，下一次检查转为失效。

### 3.6 中断恢复

执行中的申请记下所属副本。启动与巡检时，只把**所属副本已不存活**（HA 下按副本心跳租约判断；单机或没有副本记录时退回“最后更新早于本进程启动时间”）且仍是“执行中”的申请条件更新为执行失败（`interrupted`，结果未知，提示到环境页查看执行历史），绝不误判其他存活副本正在跑的迁移。被记为中断的申请不会被巡检改写成失效或过期；之后如果仍收到真实执行结果，结束处理接受并用真实结果覆盖。结果最终以目标库历史为准。

## 被否决的方案

- **下级整个替换审批流程，校验必须以上级流程为前缀**：上级之后改了流程，下级存的旧流程就不再合法，需要级联修复；追加式存储没有这个问题。
- **策略写入按版本号 compare-and-swap（冲突返回 409）**：要给每层加版本列、界面要处理 409 重试；串行化之后后到的请求直接按最新状态判断（放宽就 403、不合法就 422），对用户更直接。
- **转组时把换组层当作放宽，要求满足原生效的“谁能执行”**：与改生产标记的规则不一致，且转组已要求两边组管理员；固定原值更简单、生效策略不变。
- **审批完全按快照走**：上级事后追加的环节对已提交申请不起作用，收紧意图被绕过。
- **策略一变就让申请失效**：与审批无关的改动（比如改超时）也会打断进行中的审批。
- **全部通过后由申请人点执行（路线图原文）**：审批会变成执行权的替代，追加环节反而能放宽，破坏第 1 节的单调性。
- **申请绑定失效后自动重新绑定**：等于替审批人批准没看过的迁移。
- **连接串指纹用无盐 SHA-256**：可被离线撞库。
- **只靠平台库缓存判定申请失效**：缓存可能落后于目标库，并发时会重复执行。
