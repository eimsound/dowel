# 已达成的共识

本文记录已经确定的决策。尚未确定的问题见 [03-open-questions.md](03-open-questions.md)，决策依据的数据见 [01-research.md](01-research.md)。

## 1. 定位

**开源、可自托管、支持多人实时协作的数据库 schema 建模平台，迁移的生成、验证和交付都是工程级的。**

|                        | drawDB / ChartDB | StackRender | Bytebase / Atlas | **Dowel**           |
| ---------------------- | ---------------- | ----------- | ---------------- | ------------------- |
| 可视化建模             | ✅               | ✅          | 弱 / 无          | ✅                  |
| 开源可自托管的实时协作 | ❌ 只在付费云版  | ❌          | —                | ✅                  |
| 改名识别               | —                | ?           | ❌ 按名字比较    | ✅ 按 ID 比较       |
| 用真实引擎验证迁移     | ❌               | ❌          | 部分             | ✅ 在目标实例上验证 |
| 锁和重写整表的风险分析 | ❌               | ❌          | 靠人工规则       | ✅ 引擎实测         |
| 分支和评审流程         | ❌               | ❌          | 审批流           | ✅ 以模型为中心     |

数据库支持优先级：**第一批 PostgreSQL、SQLite；第二批 MySQL、SQL Server。**（**2026-11-22 更新**：上述四方言及 PG 15–19 多版本与分区表编辑均已合入 `main`）。

### 1.1 项目性质与开发方式（2026-11-17 确定）

- **实验性开源项目**：不做商业化，不运营 SaaS，不设时间表。
- **开发全部由 Claude 完成**；用户负责方向和产品取舍。

由此确定的开发原则：

1. **每项功能都要有能自动验证的验收标准**（随机测试、闭环验证、端到端测试）。没有人工测试兜底，测试就是唯一的质量保证。
2. **先做能完全自动验证的部分，再做需要人看的部分**：先做核心引擎，再做服务端，最后做界面（见第 9 节 M1 的内部顺序）。
3. **文档就是跨会话的记忆**：规划、决策、实验结果都写进 `.agents/docs/`，每次工作先读本文档，再按需读同目录的其他文档，结束时更新。
4. **小步推进**：每一步都能单独跑通测试，不留半成品。

**决策方式**：有明显可行方案的技术问题，由 Claude 直接决定，写进本文档并附理由，用户可随时推翻；方案模糊、或影响产品形态的问题，才问用户。

1. **IR 是唯一数据源。** 画布、SQL 视图、迁移都从 IR 派生；协作同步的内容只有 IR，不同时存一份可编辑的 SQL 文本。
2. **对象有稳定 ID。** 改名是修改属性，不是先删后加。diff 按 ID 匹配。
3. **一个项目只绑定一种方言。** 换方言是“一次性转换出新项目”，不承诺同一个模型自动对应多种数据库。
4. **正确性由真实引擎判断。** 导入、表达式归一化、语义校验、迁移验证、风险分析都交给影子库，不再引入外部 SQL AST 解析器。
5. **浏览器保持轻量。** 浏览器只运行纯 TS 核心，不默认加载 PGlite 或大型 WASM。
6. **版本差异先预防、再验证。** 生成 SQL 时查版本能力表，执行时在同版本实例上验证。

## 3. 架构

```
┌──────────────── 浏览器（轻） ────────────────┐
│ React：画布 / 表格编辑 / SQL 视图 / 评审页      │
│ 本地 IR 副本 + 待确认的修改队列                │
│ @dowel/core：diff → 操作列表 → 迁移 SQL 预览   │
│              + 版本能力表 + 静态规则检查       │
└───────────────────────┬──────────────────────┘
                        │ WebSocket（修改 / 广播 / 在线状态） / HTTP
┌───────────────────────▼──────────────────────────────────────────┐
│ 服务端（Node 26 + Hono，同一个进程、同一个端口）                    │
│ ├ 协作：按顺序处理每个修改，校验通过才生效，持久化到平台 PG        │
│ ├ API：项目、环境、版本、分支、评审、权限                          │
│ ├ 任务队列：pg-boss（基于 PG，不需要 Redis）                       │
│ └ 验证执行器：服务端能连到数据库时在这里执行                       │
└───────────────────────┬──────────────────────────────────────────┘
                        │ 只由用户侧主动向外连接
┌───────────────────────▼──────────────────────────────────────────┐
│ CLI / 代理（跑在用户网络里，内含 @dowel/core 和验证执行器）         │
│ pull（读结构） / drift（漂移检测） / plan / apply / lint / 执行检查 │
└──────────────────────────────────────────────────────────────────┘
```

- **自托管**：服务端一般能直连数据库，验证执行器在服务端运行。
- **SaaS**（暂不做，见 1.1）：连不到用户内网，读结构、检查、执行迁移都交给 CLI 代理；平台不保存生产库凭据。架构上保留“代理只向外连接”的设计，以后需要时再做。

## 4. 核心模块

### 4.1 IR

- 每个对象有稳定 ID。
- 两层结构：通用核心字段 + 各方言扩展字段（PG 的 RLS、EXCLUDE、分区；MSSQL 的 identity、带名字的默认值约束等）。
- 表达式字段（默认值、CHECK、生成列、索引条件）以 SQL 片段存储，规范形式以引擎读出来的为准。
- 画布布局（位置在 `branches.layout`、**板块（Section）**在 `branches.sections`，术语定义见 [GLOSSARY.md](../../GLOSSARY.md)）单独存放在布局层，绝不进入 IR，不影响 SQL、迁移、diff 或版本快照；板块定义（名称、颜色、成员）在项目内团队共享，每张表最多归属 1 个板块且不支持嵌套、与 schema 正交（兼容 PG/MSSQL 多 schema 与 MySQL/SQLite 单 schema）；展开/折叠及邻域聚焦视图状态仅保存在各自浏览器本地（2026-11-22 确定，见 Q17）。
- **约束、索引、序列的名字全部写进 IR。** 按引擎规则自动推导的名字（如 `users_email_key`）在表或列改名时**跟着改**，迁移里生成对应的 `RENAME`；用户可以锁定单个对象的名字（例如业务代码里写了 `ON CONFLICT ON CONSTRAINT users_email_key`），锁定后不跟着改。（2026-11-17 确定，依据见 [01-research.md](01-research.md) 第 5 节，设计见 [04-ir-design.md](04-ir-design.md) 1.4）
- 项目下挂多个**环境**（dev、staging、prod-a……），每个记录方言大版本；**项目目标版本 = 所有环境中最低的那个**（类似 browserslist）。

### 4.2 协作、版本、分支、评审

- **实时协作采用“服务器说了算、按顺序处理”**（2026-11-17 确定，取代原先的 Yjs / CRDT 方案，调研见 [01-research.md](01-research.md) 第 8 节）：
  - 每个修改是一次具名操作（如“改列名”“改 CHECK 表达式”），客户端先在本地乐观执行，同时发给服务器。
  - 服务器按到达顺序逐个处理，**对照最新状态校验**；不通过就拒绝，客户端撤回这条修改、刷新到最新数据，并提示原因（例如“`email` 已被张三改名为 `mail`”）。
  - 操作的执行逻辑写在 `@dowel/core` 里，客户端和服务器共用同一份代码。
  - 服务器保存操作日志，供历史、审计、分支合并使用。
  - 在线状态、多人光标、挂在对象上的评论照常支持。
  - **同步层自己写**（2026-11-17 确定，不用 Zero 等现成组件）：与 API 同一个进程、同一个端口；设计参考 Zero / Replicache 的 mutator 模型和 Logux 的 undo 协议。
- **版本**：IR 的不可变快照，迁移永远在两个版本之间生成。
- **分支**：从某个版本分出的独立工作副本。
- **评审**：可视化 diff + 迁移 SQL + 验证结果 + 风险报告，评论、批准、合并。
- **分支合并时检测语义冲突，交给人处理，不自动解决。**

### 4.3 核心引擎 `@dowel/core`、`@dowel/engines` 与跨方言抽象（纯 TS，浏览器 / 服务端共用）

```
IR(v1), IR(v2)
  → diff：按 ID 匹配 → 操作列表（AddColumn / RenameColumn / AlterType / AddFK …）
  → 编排：按依赖排序，拆成适合在线执行的步骤
       （NOT VALID + VALIDATE；CONCURRENTLY 单独拆出事务；SQLite 12 步重建表；MSSQL 带名 DEFAULT 约束顺序）
  → DialectSpec / 各方言翻译层：查版本能力表 → 生成 up / down SQL（via DialectRegistry）
  → 静态规则检查：不可逆操作、数据丢失风险、目标版本不支持的写法
```

多方言三层抽象已落地：

- **`@dowel/core`（`DialectSpec` + `DialectCapabilities`）**：纯函数、无 I/O，前后端共用，统一封装引用/词法/类型规范化、推导命名、模型校验、规划器、非事务与高危语句检测；
- **`@dowel/engines`（`EngineAdapter` + `HistoryStore`）**：统一封装连接适配、固定会话参数、快照读取与指纹、风险实测、目标库迁移历史读写与项目互斥锁；
- **`apps/server/src/targets/`（`TargetDriver`）**：按方言分派目标探测、拉取结构与影子库准备/清理生命周期。

各方言要单独处理的坑：

- **PG（15–19）**：DDL 支持事务；`CONCURRENTLY` 不能在事务里（失败清理遗留 `INVALID` 索引、`DETACH PARTITION ... CONCURRENTLY` 超时转 `FINALIZE`）；多环境取最低大版本作目标版本（`NULLS NOT DISTINCT` 15+、分区表 `IDENTITY`/排他约束 17+、`VIRTUAL` 生成列与显式命名 `NOT NULL` 与 `uuidv7()` 18+、`REPACK` 19+）。
- **SQLite（`node:sqlite`）**：大部分 ALTER 不支持，按官方 12 步流程重建表，在事务外切换 `PRAGMA foreign_keys = OFF/ON` 并在提交前跑 `PRAGMA foreign_key_check`；目标库经 `DOWEL_SQLITE_ROOTS` 白名单与逐段软链消解保护（禁指 `DOWEL_DB`），引擎开启 `enableDefensive` 与 authorizer。
- **MySQL（8.4 / 9.7）**：DDL 会自动提交，每一步记断点并在崩溃重跑时结合 `information_schema` 与幂等 errno 探测跳过已提交单步；`ALGORITHM=INSTANT / INPLACE / COPY` 渐进试跑风险；多环境按主次版本分组验证（9.0+ `VECTOR` 检查）。
- **MSSQL（2019 / 2022 / 2025）**：删列或改默认值前先删带名 `DEFAULT` 约束（`DF_<table>_<col>`）；改名用 `EXEC sp_rename`；独占行 `GO [count]` 切批；`CLUSTERED` 约束/索引互斥；2025（17+）原生 `json` 与 `vector(n)` 能力检查；TLS 默认严格校验。

### 4.4 影子库

确定顺序：

1. 环境里显式配置的影子库实例（用户可指定其他实例）。
2. **默认：目标库所在实例上的 `{原库名}_dowel`**（PG / MySQL / MSSQL 均采用 `{原库名}_dowel`，超长按各自标识符上限截断并拼接 8 位短哈希）。
3. ~~兜底：项目还没连接任何数据库时，PG 用 PGlite~~。**2026-11-18 用户决定：不用 PGlite 兜底**——PG / MySQL / MSSQL 影子库只能是真实数据库实例，**不可用就报错**。

**SQLite 例外：一律用内存库**（Node 26 内置 `node:sqlite` `:memory:`，免环境配置即可导入 SQL 与闭环验证）。

同实例影子库的好处：版本、扩展、排序规则、参数和目标完全一致，版本矩阵问题自然消失，不需要单独维护验证集群。

配套保护措施：

| 风险             | 措施                                                                                                                                                                               |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 检查拖累生产实例 | `production` 环境默认禁用同实例影子库，需明确同意或改配其他实例；同一影子库串行互斥                                                                                                |
| 锁表空间耗尽     | 限制等待与语句超时（PG `lock_timeout` / `statement_timeout`、MySQL `lock_wait_timeout` / `max_execution_time`、MSSQL `SET LOCK_TIMEOUT` / 请求取消、SQLite `PRAGMA busy_timeout`） |
| 误清空业务库     | 专用标记核对后才清空：PG 用库级 `COMMENT`、MySQL 用 `__dowel_shadow_mark` 哨兵表、MSSQL 用 `dowel_shadow` 数据库扩展属性（并拒绝 `master`/`tempdb`/`model`/`msdb`）                |
| 权限与残留       | 专用账号拥有 `_dowel` 库；对目标库只读系统目录；无建库权限时提示手动建库语句；每次检查前清空影子库（PG 用 `DROP SCHEMA CASCADE`、MySQL / MSSQL 按依赖拓扑清理对象并保留标记）      |
| 并发生命周期竞争 | PG 使用维护库 advisory lock、MySQL 使用 `GET_LOCK`、MSSQL 使用 `sys.sp_getapplock`，遇并发建库错误码自动回退复用                                                                   |

**托管库适配边界（2026-11-23 已完成 Tier 1 收口并关闭 Q7）**：不做云厂商专有适配（如 Supabase 系统 schema 白名单、Neon branch API 等）与云账号实测矩阵（跨公网 10–50 倍 RTT 对串行影子库往返体验极差、放宽清空策略会破坏非空库保护安全边界，且生产已禁用同实例影子库）；已完成 Tier 1 收口：补充托管库影子库与最小权限 SQL 配置指南、友好识别 PG Transaction Pooler（`-pooler.` / `6543` 等）与缺 `CREATEDB`/非 owner `42501`（含 `resetShadow` 清空阶段）并给出精确可执行 SQL 与友好诊断提示，同时补齐本地 Docker 非超管/无 `CREATEDB`/非 owner/预打标未移交所有权受限权限自动化测试。

### 4.5 验证执行器

不同引擎接同一套检查流程，可以内嵌在服务端或 CLI 代理里：

| 检查           | 做法                                                                     |
| -------------- | ------------------------------------------------------------------------ |
| 语义校验       | 在影子库建出 IR 对应的结构，捕获引擎报错                                 |
| 闭环验证       | 建旧版本 → 执行 up → 读结构 → 必须等于新版本；执行 down → 必须等于旧版本 |
| 样本数据试跑   | 插入种子数据或脱敏样本后执行迁移                                         |
| 风险分析（PG） | `pg_locks`、`relfilenode`、`pg_stat_xact_user_tables`                    |
| 多环境验证     | 项目涉及几个环境（大版本），就在各自的影子库上跑一遍                     |

检查结果由服务器写回并广播给所有协作者，只算一次。

### 4.6 导入与解析

| 方言       | 导入（主路径）                                   | 浏览器 SQL 视图                       |
| ---------- | ------------------------------------------------ | ------------------------------------- |
| PostgreSQL | 在真实影子库执行，读系统目录                     | 只读（实时由 IR 派生 DDL 预览与复制） |
| SQLite     | 在内存库（`node:sqlite` `:memory:`）执行并读结构 | 只读（实时由 IR 派生 DDL 预览与复制） |
| MySQL      | 在真实影子库执行，读 `information_schema`        | 只读（实时由 IR 派生 DDL 预览与复制） |
| MSSQL      | 在真实影子库执行，读系统目录（`sys.*`）          | 只读（实时由 IR 派生 DDL 预览与复制） |

- **2026-11-22 明确不做模型页全库 SQL 可编辑（Q3）**：模型页 SQL 视图长期保持只读（用于实时 DDL 预览与复制）；版本详情页仅支持手改冻结迁移步骤并走影子库闭环验证。
- **不引入外部 SQL AST 解析器**：四方言（PG / SQLite / MySQL / MSSQL）统一通过真实影子库（SQLite 为内存库）执行并读系统目录导入，合法性一律以真实引擎执行结果为准。原 `pgsql-parser` / `@polyglot-sql/sdk` / `node-sql-parser` 与统一接口 `SqlFrontend` 规划随之作废。
- **仅保留自研词法级语句切分器**：负责处理 PG `$$`、MySQL `DELIMITER`、MSSQL 独占行 `GO [count]` 切批与常见导出噪声过滤，并将引擎报错映射回原脚本位置。

### 4.7 环境、漂移、交付

- 漂移检测：~~CLI 代理~~服务端读线上结构（2026-11-19，见第 11 节），与环境当前版本比较；两边都是引擎输出的规范形式，不误报。**2026-11-20**：漂移的处理见 11.5 和 [ADR 0004](adr/0004-drift-resolution-by-mark-as-applied.md)。
- 迁移历史：在用户库里建历史表，记录版本和校验和。**2026-11-19 细化**：固定放在 `dowel` schema，并存每个版本的完整模型和冻结脚本，见 11.5。
- 交付：纯 SQL（up / down）与托管执行 / CI HTTP API（2026-11-22 明确不做第三方迁移目录格式导出与 GitHub App 提交 PR）。
- `apply` 默认先 plan 再确认，生产环境强制先通过评审。**2026-11-19 改**：是否需要审批、谁能执行由执行策略决定，见 11.3。

## 5. 技术栈

### 5.1 总体

| 部分          | 选择                                                                                                                                                      | 理由                                                                                                                                                                                                                                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 语言          | TypeScript 7（strict）                                                                                                                                    | 核心代码在浏览器、服务端、CLI 共用；协作生态在 JS；CLI 分发简单（MSSQL 驱动 tedious 是纯 JS）                                                                                                                                                                                                                     |

## 11. 产品化：账户、权限与交付（2026-11-19 确定）

2026-11-18～19 与用户逐项讨论后确定，取代本文中与之冲突的旧结论（已在原处标注）。术语以仓库根目录的 [GLOSSARY.md](../../GLOSSARY.md) 为准；难以逆转的决定见 [adr/](adr/)。

### 11.1 账户与登录

- **一个实例只服务一家公司**（[ADR 0001](adr/0001-single-company-groups.md)）。实例管理员能看到一切、拥有全部权限。
- 登录：**用户名 + 密码**，加实例级配置的**通用 OIDC**（Google、GitLab 作为预设模板）。不做 GitHub 登录（不是标准 OIDC）、LDAP、SAML；**永远不做**组级的“必须用某个 OIDC 登录”。实例管理员可以关闭密码登录，保留环境变量作应急入口。
- 用户名：小写字母、数字、`-`，1～39 位，全实例唯一，可修改。邮箱选填；非空时在全实例按大小写不敏感唯一（不可作为登录用户名，且不用于 OIDC 自动关联现有账户；OIDC 首次开户撞邮箱时清空新账号邮箱）。
- 支持可选实例级 SMTP 发信（配置存于 `instance_settings`，密码由 `DOWEL_SECRET` 加密）：首期仅用于登录页「忘记密码」发送 1 小时 `/reset/:token` 重置链接与管理后台创建邀请时邮件发送 `/invite/:token` 链接。未启用 SMTP 时，管理后台仍可生成邀请链接与重置密码 / 临时密码；管理后台「用户」页对每个用户只提供单一「重置密码」动作（直接设或随机生成一次性临时密码、吊销现有会话、强制下次登录改密），同时后端保留 `POST /api/admin/users/:id/reset-link` 与 `/reset/:token`。注册**仅邀请**：只有实例管理员能建用户或生成邀请链接（组管理员不能）。
- 首次启动自动创建初始 `admin`（可设 `DOWEL_ADMIN_USERNAME`）：提供 `DOWEL_ADMIN_PASSWORD_FILE` 或 `DOWEL_ADMIN_PASSWORD`（互斥）则直接启用；否则以 `0600` 写入 `initial-admin-password` 并在登录后强制 `/change-password` 改密与自动删文件。
- OIDC 首次登录按“提供方 + subject”识别；用户名被占用时让本人改；已有用户只能登录后自己去关联；未被邀请者被拒绝，除非管理员给该提供方开了“信任，允许自动开户”。

### 11.2 组、项目与授权

- **组**：一层、不嵌套；用户可属于多个组；默认所有用户都能建组（实例设置可改为仅实例管理员）。组的名字、描述、管理员、成员对所有人可见；**组的项目只对有权限的人可见**，无权限访问返回“不存在”。
- 项目属于一个组，URL `/project/:owner/:project`。默认所有组成员能在本组建项目，建项目者成为项目管理员。组的**默认权限**默认为编辑者，组管理员可为单个项目另设。项目可转组（两边的组管理员或实例管理员操作，原 URL 跳转）；有项目的组不能删。
- **项目角色**：查看者 / 编辑者 / 项目管理员，只管模型，不管目标库。
- **授权** = 角色 × 范围（环境 / 项目 / 组的全部项目 / 实例）× 对象（用户 / 组）。组管理员、项目管理员都能授权；例外：执行策略为“仅限执行者”时，生产环境的执行者只能由实例管理员授予。

### 11.3 执行策略与审批

- **执行策略**按环境生效，分四层配置（实例 → 组 → 项目 → 环境），生产 / 非生产各一套；**下级只能收紧**，上级设定在下级显示为锁定。
- 谁能执行：项目编辑者 / 项目管理员 / 仅限执行者。默认非生产 = 项目编辑者，生产 = 项目管理员（小公司开箱即用）。
- **特权操作**（受执行策略约束）：执行 / 回滚、处理漂移、改连接串和影子库、删除环境、取消“生产”标记、写入基线 / 接手。模型的编辑和发布不受约束。
- **审批流程**：默认一个环节、一人批——有权限者直接“执行”，无权限者提交**执行申请**，有权限者“通过并执行”。可配多个环节（每环节：审批人范围 + 人数；可设“最后一个审批人即执行者”）；驳回即结束。系统不限制同一人批多个环节（配置页提示重叠），但每个环节单独确认。批准绑定“起止版本 + 各迁移校验和”，环境状态一变即失效，默认 24 小时过期。实例管理员平时也走审批，另有“紧急执行”（必填原因、审计、通知审批人）。
- ~~**前置环境**~~（2026-11-21 移除）：不同环境彼此独立，不在 Dowel 内硬绑环境间先后关系，也不以平台缓存作为前置真值。
- 通知：站内收件箱 + 组级 Webhook（预设钉钉、飞书、企业微信、Slack 格式）。
- 运行规则（2026-11-20，P5b；2026-11-21 修订）：审批按提交时的流程快照走、资格按审批时判断、流程变严即失效；**审批不给执行权**（执行的人始终要满足“谁能执行”）；申请人不能自批；放宽策略不走审批（ADR 0006）。申请绑定与失效判定见 ADR 0007，Webhook 出站限制见 ADR 0008。

### 11.4 CI

- **CI 令牌属于项目**（创建者离职不影响），必须过期（默认 90 天，最长 1 年），只能读和执行。
- 谁能创建在实例 / 组 / 项目三层配置，可指定角色或某个组的管理员 / 成员（如 DBA 组、流水线组）；被允许者自动能只读查看范围内的项目。
- 令牌能在哪些环境执行，只看环境上的“允许令牌执行”开关（默认非生产开、生产关，逐层只能收紧）；**令牌执行不走审批**，每次执行都审计并通知。
- CI 必须**显式指定目标版本**；出错立即失败并返回错误码，只有执行锁等待（默认 30 秒）；中途失败停在最后一个成功的版本。
- **CI 接口按职责拆清、零过期缓存（2026-11-21，[ADR 0009](adr/0009-ci-tokens-and-api.md)）**：项目/环境列表只返回平台配置不连目标库；单环境状态实时读目标库 `dowel.history` 返回当前版本、未完成状态与待执行列表；漂移检测拆为独立 `POST .../environments/:env/drift` 实时读结构快照比对。
- 参考了 Atlas（审批前移、目标版本显式、批准绑定起点状态）、Bytebase、Flyway。
- **不做 CLI、个人令牌、隔离网络里的执行代理、GitHub OIDC 短令牌交换**：服务端能直连目标库（用户的实际情况），CI 直接调 HTTP API（文档给 `curl` 示例，另保留纯 `bash + curl` 的 `actions/execute/` 兼容内网自建 Actions / 通用 shell 调用）。将来出现“服务端连不到目标库”时再做代理。

### 11.5 版本、迁移与目标库

- **发布时冻结迁移，环境沿版本链逐个执行**（[ADR 0002](adr/0002-frozen-migration-chain.md)）。每个发布的版本都可以上生产，没有“正式”标记；临时 `plan()` 只用于预览和对比。
- 一个环境只对应一个目标库，不同环境彼此独立。
- **目标库里的迁移历史**（[ADR 0003](adr/0003-version-content-in-target-db.md)）：固定放在 `dowel` schema（同一个库里的多个项目共用，按项目区分；没有建 schema 的权限直接报错；不支持 schema 的数据库用同库 `dowel_` 前缀表）；存每个版本的完整模型（含对象 ID）和冻结脚本，丢了平台数据也能接手。每个实例有唯一标识，另一个实例接手同一个库须由其管理员确认“认领”，之后旧实例的执行被拒绝。不做单方面“撤销认领”，交还由原实例管理员主动反向认领。
- 导入只导结构；可勾选 schema（默认全选），不特别处理其他迁移工具的历史表。导入时只在 Dowel 里发布 v0 基线、**不写目标库**；第一次执行到该库时才建 `dowel` schema 并写基线（空库则执行 v0 完整建库；结构不符报漂移）。
- **漂移的处理**（2026-11-20，[ADR 0004](adr/0004-drift-resolution-by-mark-as-applied.md)）：只有两个出口，生产和非生产行为相同，按钮不分主次。
  - **保留线上的修改**：从漂移环境**导入**到工作副本（**覆盖**，对象 ID 按名字沿用工作副本里的）→ 用户检查、修改（例如把“删一列加一列”改回改名）→ 普通**发布**（真实的 up / down，影子库验证）→ 把漂移环境**标记为已执行**到新版本；其他环境照常执行它。没有“收编版本”这种特殊版本。导入前给差异预览，并在三种情况下警告（不拦截）：环境落后于链头（会撤销中间版本的修改）、环境有半途失败的迁移、工作副本有未发布的修改（会被覆盖）。导入是模型编辑，项目编辑者即可，和检查漂移共用连接限速，记审计（来源环境、线上结构指纹）。
  - **放弃线上的修改**：漂移详情里显示**修复脚本** `plan(线上结构, 当前版本的模型)`，可复制，附风险提示；**Dowel 不代为执行**，用户自己执行后“重新检查漂移”。模型表达不了的差异（`unresolvable`）明确列为“需要手工处理”。
  - **标记为已执行**（代码值 `mark`）：不执行 SQL，把环境记为已到达链上**任意**版本 X（更新或更早都行）。硬条件只有一个：在项目锁里读出的线上结构等于 X 的模型。目标库历史写一条 `direction = 'mark'`（from = 当前版本，to = X；`mark` 直接写进 `dowel.history` 建表语句的 direction 约束）；向前标记给 X 和中间跳过的版本写 `executed_at`，向后不写。确认框列出被跳过的版本和脚本，要求勾选“这些脚本的效果已经手工完成，或者不需要”（数据步骤会被跳过）。界面按前后关系显示“标记为已执行到 v6 / 标记为已回滚到 v4”，按钮和历史里的“标记”都带 tooltip。读回失败后手工修好、半途失败后手工补完、手工回退了发布，都走它；第一次执行的“写入基线”是它的特例。
  - **不做**：执行时“线上已等于目标就自动只写记录”（会跳过只含数据步骤的版本，也会悄悄把漂移合法化）；修复脚本由 Dowel 代为执行；导入时三方合并差异；环境落后于链头时“带着漂移往前执行”（已知限制：只能先按修复脚本改回当前版本）。
  - **权限与审计**：标记是特权操作，动作 `environment.mark`（取代 P4b 预留的 `environment.resolve_drift`），按环境的执行档位约束，生产环境要输入环境名；审计记 from、to、跳过的版本、线上结构指纹，成功和失败各一条。CI 令牌不能标记。审批（P5）的批准绑定“起止版本 + 线上结构指纹”，结构一变即失效。
  - **目标库历史的格式版本**（2026-11-20）：`meta.format_version` 只在**破坏性变更**（旧版 Dowel 照旧读写会出错）时 +1，加列之类的兼容变更不动它，靠建表语句的 `if not exists` / 幂等的 `add column if not exists` 处理。读的一方**从第一个发布版起**就检查：库里的值比代码新或不是整数 → `format_too_new`，拒绝执行和读历史（这个检查事后补不上，所以即使现在没有任何升级也保留）。发版之前不写任何升级路径，当前格式为 1。
  - **接手与接入强制影子库验证（2026-11-21，[ADR 0012](adr/0012-strict-verify-on-restore.md)）**：接手不处理漂移，但必须全链在影子库验证通过才允许接手（向导允许配置影子库），不再产生未验证的恢复版本；接入已有历史环境支持目标库严格领先于平台链（无分叉延伸），领先版本同样须经影子库验证通过后补进平台链并覆盖工作副本，若当前工作副本有未发布修改则先展示覆盖前后差异由用户确认，回看/恢复原草稿依赖在线文档式「画布修改历史」。

### 11.6 界面

- 采用“窄图标栏 + 随页面变化的侧面板”（静态稿 `.agents/docs/ui/mockups/shell.html` 方案 d）：图标栏放组头像、组级入口、当前项目的页面、收件箱；侧面板在模型页是对象树，在环境页是环境列表。模型页的属性面板默认按需显示，可固定为常驻。实现前先更新 DESIGN.md。

### 11.7 高可用（HA，2026-11-21 确定，[ADR 0011](adr/0011-ha-postgres-only.md)）

- 多副本部署仅依赖外部平台 PostgreSQL（单机 SQLite 保留用于单副本），**不引入 Redis**。
- 实时协作房间采用无状态多活：WebSocket 写操作通过平台 PG 分支行锁串行提交，经 `LISTEN/NOTIFY` 跨副本广播轻量通知（`seq` / 踢人 / 角色变更 / 收件箱推送），负载均衡无需粘性路由。
- Webhook 队列迁入平台 PG 表（`FOR UPDATE SKIP LOCKED`），定时巡检（审批过期、漂移检查）与首次启动管理员引导（`bootstrapAdmin` / PG advisory lock）适配多副本。
- 限流器（登录、连库探测、CI 令牌失败、CI 令牌速率）保持进程内内存计数，全部限流维度（上限与窗口）开放环境变量配置，并在部署配置与文档注明「HA 多副本下总配额约为设定值 × 副本数」。
