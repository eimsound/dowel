## 一、IR 与协作

### Q1 IR 的具体格式

✅ **已确定（2026-11-17）**：按 [04-ir-design.md](04-ir-design.md) 第 1 节。

- **要紧之处**：IR 是唯一数据源，定了之后改动成本很高。
- **要决定的**：
  - ID 方案：UUIDv7 / ULID / nanoid。倾向 UUIDv7（有序、标准）。
  - 通用核心字段与方言扩展字段的边界，以及扩展字段如何做类型约束（按方言的 zod 判别联合？）。
  - 表达式片段如何存：原文 + 引擎规范形式两份？只存规范形式会让用户看到的写法和自己输入的不一样。
  - 影子库能执行、但 IR 不认识的对象（如第三方扩展的类型），如何作为“不透明对象”保留并参与 diff。
  - IR 格式自身的版本号与升级方式。
  - 落盘格式（给 CLI 和 Git 工作流用）：JSON / YAML / 自定义 DSL？要求对 Git diff 友好、稳定排序。
- **下一步**：写出 `packages/core` 的类型草稿，用一个真实的中型 PG schema（约 50 张表）验证表达力。

### Q2 协作同步的数据如何映射 IR

✅ **已确定（2026-11-17）**：按 [04-ir-design.md](04-ir-design.md) 第 2 节（服务器按顺序处理，原型已验证）。

> **2026-11-17**：协作方案已从 Yjs 改为“服务器按顺序处理、可拒绝”（见 [02-consensus.md](02-consensus.md) 4.2），下面基于 Yjs 的原问题作废。**新方案**见 [04-ir-design.md](04-ir-design.md) 第 2 节，原型和随机测试结果见 [01-research.md](01-research.md) 第 9 节。

- **要紧之处**：决定并发编辑的粒度、撤销 / 重做的行为、文档大小和性能。
- **要决定的**：
  - 每个对象一个 `Y.Map`，还是整张表一个？粒度太粗会导致并发修改同一张表的不同列时互相覆盖。
  - 列的顺序如何表达（`Y.Array` 还是带排序键的 `Y.Map`）。列顺序在 PG 里只能靠重建表来改，要不要允许调整？
  - `Y.UndoManager` 的范围：只撤销自己的操作。
  - 画布布局放在同一个文档还是单独的文档。
  - 检查结果写回文档的位置，以及如何避免触发不必要的重新检查。

### Q3 SQL 视图编辑后如何保住对象 ID

❌ **明确不做（2026-11-22）**：模型页全库 SQL 视图长期保持只读（用于实时 DDL 预览与复制），不做直接编辑并反解析回 IR 的方案（四方言下维护 AST 解析器、DDL source-map 与反向 mutator 编译器成本远超收益，且极易破坏稳定对象 ID；冻结迁移脚本手改已在版本详情页支持，修改模型统一通过画布/属性表单或 SQL 导入）。以下为历史问题记录。

- **要紧之处**：用户在 SQL 视图里把 `name` 改成 `full_name`，解析出来的新 IR 里没有 ID，会被识别成先删后加，正好违背核心原则 2。
- **可选方案**：
  1. 按位置和相似度做启发式匹配（同一张表内，类型和约束相同、名字变了 → 认为是改名），由用户在界面上确认。
  2. 在生成的 SQL 视图里嵌入隐藏标记（如 `-- @id:...` 注释），解析时读回。
  3. 用 CodeMirror 的变更信息追踪编辑发生在哪个对象的文本范围内。
- **倾向**：3 为主、1 兜底、需要时让用户确认；不采用 2（污染用户看到的 SQL）。
- **下一步**：做一个原型验证 3 的可行性。
- **2026-11-17 补充**：改为服务器排序后，SQL 视图不再支持多人同时打字。编辑 SQL 视图等同于打开一个草稿：保存时解析 → 与打开时的 IR 做 diff → 生成一组修改，`reads` 取打开时的版本，期间别人改过的对象会被拒绝（[04-ir-design.md](04-ir-design.md) 2.3）。保住 ID 的问题仍然存在。

### Q4 M1 覆盖哪些 PG 对象

✅ **已确定（2026-11-17）**：按 [04-ir-design.md](04-ir-design.md) 第 4 节。

- **要决定的**：表、列、主键、唯一、外键、CHECK、索引（含部分索引、表达式索引）、枚举、序列、identity、生成列、注释——这些肯定要做。以下是否在 M1 范围内：视图、物化视图、函数、触发器、RLS 策略、分区表、继承、扩展、域类型、复合类型、多 schema。
- **倾向**：M1 做到分区表和多 schema；视图、函数、触发器、RLS 先作为不透明对象保留（能导入、能原样输出，但不能可视化编辑）。

### Q5 迁移里如何容纳人工步骤和数据迁移

✅ **已确定（2026-11-17）**：按 [04-ir-design.md](04-ir-design.md) 第 5 节。

- **要紧之处**：真实迁移常常要在两步 DDL 之间回填数据（如拆列、改类型），expand / contract 还需要在两个阶段之间部署应用代码。
- **要决定的**：
  - 操作列表里允许插入用户写的 SQL 步骤吗？验证时如何处理（照样在影子库里执行）？
  - expand / contract 如何表示：一次评审生成两个迁移，还是一个迁移带“暂停点”？
  - 生成的迁移被用户手动修改后，如何检测“修改后的结果仍然等于目标版本”（用闭环验证即可）。

### Q6 闭环验证的“结构相等”如何定义

✅ **已确定（2026-11-17）**：按 [04-ir-design.md](04-ir-design.md) 第 3 节。

- **要决定的**：比较时忽略哪些差异（约束和索引的自动生成名、列的物理顺序、OID、统计信息、所有者、权限）；不同大版本读出的形式不同（如 PG 18 的 NOT NULL 约束）如何统一。

## 二、影子库与验证

### Q7 影子库的权限、生命周期、并发

✅ **已确定并收口（2026-11-23）**：

- **已落地基础能力（2026-11-18）**：有 `CREATEDB` 权限时自动建 `{原库名}_dowel`，否则提示用户手动建；影子库长期保留、每次检查前清空；同一影子库用锁串行排队（PG advisory lock / MySQL `GET_LOCK` / MSSQL `sp_getapplock`）；“生产环境”由用户手动标记，新环境默认标为生产且默认禁用同实例影子库。
- **明确不做**：不做云厂商专有适配（如 Supabase 系统 schema 白名单、Neon branch API 等）与云账号实测矩阵。原因：公网直连托管库存在 10–50 倍 RTT，对串行多往返的影子库验证体验极差；为云厂商特例放宽清空策略会破坏“非空库保护”安全边界；且生产环境已禁用同实例影子库，本身就推荐指向自托管或近端验证实例。
- **Tier 1 收口已落地（2026-11-23）**：
  1. 在 `docs/modeling.md`、`docs/deployment.md` 与 `docs/dialects.md` 补充托管数据库影子库拓扑、禁用 PG Transaction Pooler 说明与四方言/三外部方言最小权限 SQL 配置指南；
  2. 在 `apps/server/src/targets/pg.ts`、`apps/server/src/targets.ts` 与 `apps/server/src/shadow.ts` 增加 PG Transaction Pooler URL/错误识别诊断、缺 `CREATEDB` / 非 owner `42501` 精确可执行 SQL 提示，以及 `resetShadow` `42501` 权限归类保护（严禁 `WITH (FORCE)` 且全路径凭据脱敏）；
  3. 在 `apps/server/test/shadow-pg.test.ts` 与 `apps/server/test/shadow-ops.test.ts` 补齐纯单元测试及本地 Docker PG 非超管 / 无 `CREATEDB` / 非 owner / 预打标未移交所有权受限权限自动化测试。

以下为历史问题记录。

- **要决定的**：
  - 默认 `{原库名}_dowel` 由谁创建：Dowel 自动建（需要 `CREATEDB`），还是要求用户手动建？
  - 长期保留还是每次用完删掉？倾向长期保留、每次检查前清空。
  - 同一实例上多个项目、多个检查如何排队：一个 `_dowel` 库加 advisory lock，还是每个项目一个库？
  - 判定“生产环境”的依据：用户手动标记，还是根据连接信息推断？倾向手动标记，默认值为“生产”。
  - 托管数据库（RDS、Cloud SQL、Supabase、Neon、Azure SQL 等）上的实际限制，需要逐个确认。
- **下一步**：在 RDS PostgreSQL、Supabase、Neon 上各试一次建库、建账号、`BEGIN…ROLLBACK` 检查。

### Q8 风险分析如何估算耗时

✅ **已确定（2026-11-17）**：按倾向，只给数量级（秒 / 分钟 / 小时）和锁类型，依据 `reltuples`、`pg_relation_size`、索引数量估算；不做合成数据实测。

- **现状**：引擎能告诉我们“拿什么锁、是否重写整表、是否全表扫描”，但不知道要多久。
- **要决定的**：根据目标库的 `reltuples`、`pg_relation_size` 和索引数量估算耗时，用什么模型？要不要让用户在影子库里用合成数据做一次真实测量？
- **倾向**：先给出数量级（秒 / 分钟 / 小时）和锁类型，不追求精确。

### Q9 版本能力表如何维护

✅ **已确定（2026-11-17）**：按倾向，每个能力一条声明 + 一条在多版本矩阵上运行的验证用例，CI 检查两者一致。

- **倾向**：每个能力一条声明 + 一条在 Testcontainers 多版本矩阵上跑的验证用例，CI 里自动检查能力表和真实行为是否一致。

### Q15 polyglot 的缺陷如何处理

❌ **作废（2026-11-22）**：明确不做模型页全库 SQL 编辑（Q3）后，四方言全仓均通过真实影子库执行 + 读系统目录导入，不再引入 `@polyglot-sql/sdk` / `pgsql-parser` / `node-sql-parser` 等外部 SQL AST 解析器，此问题不复存在。以下为历史记录。

- **已知缺陷**：MSSQL 建表时带名字的默认值约束丢名字；`EXEC sp_rename` 解析失败；SQLite 的 `STRICT`、`WITHOUT ROWID` 解析失败（SQLite 本来就不走 polyglot）；错误 SQL 会被当成合法的接受。
- **要决定的**：给上游提 PR，还是在适配层里绕过（比如有影子库时以影子库读回的名字为准）？如果需要在浏览器里使用，是否从源码按方言裁剪编译以减小体积？
- **倾向**：给上游提 PR；有影子库时以影子库为准。

## 四、产品与工程

### Q22 不可信 SQL 的执行隔离与 PGlite 资源管理

❌ **作废（2026-11-18）**：用户决定影子库不用 PGlite 兜底，用户的 SQL 只在用户自己的实例上执行，这个问题不复存在。以下为历史记录。

> **2026-11-17**：不做 SaaS，“一个用户拖垮所有人”的多租户风险不存在了。但自托管下 PGlite 仍跑在服务进程里，一个检查卡死或占满内存会拖垮整个服务，所以仍然要“子进程 + 超时强杀 + 内存上限”。

- **要紧之处**：用户的 DDL（包括函数、触发器、默认值表达式）会在影子库里执行。连的是用户自己的实例时，风险由用户承担；但 PGlite 兜底跑在**我们的服务进程里**，SaaS 上一个用户写个死循环函数或超大的 `generate_series`，就能拖垮所有人。实验数据：第一个 PGlite 实例让进程内存涨到约 720MB，之后每个约 +240MB，且是单连接（[01-research.md](01-research.md) 2.5）。
- **要决定的**：PGlite 跑在 worker 线程还是子进程（子进程才能可靠限制内存、超时后直接杀掉）；实例池大小、按项目复用还是按检查新建；排队策略；SaaS 上是否干脆不提供 PGlite 兜底，要求连真实实例。
- **倾向**：子进程 + 内存上限 + 超时强杀；实例池按 LRU 复用；SaaS 上 PGlite 兜底单独限额。

### Q23 样本数据从哪里来

✅ **已确定（2026-11-17）**：M1 做按 IR 自动生成的合成数据（刻意包含空值、重复、超长值）和用户提供的种子 SQL；生产库抽样脱敏随 CLI 一起做，只在用户网络内进行。

- **要紧之处**：“带样本数据试跑迁移”是核心卖点之一（加 NOT NULL 时有空值、加 UNIQUE 时有重复值，都靠数据才能发现），但数据来源没规划。
- **可选来源**：
  1. 按 IR 自动生成符合约束的合成数据，并刻意制造边界值（空值、重复、超长字符串）；
  2. 用户提供的种子 SQL；
  3. 从生产库抽样并脱敏——只能在 CLI 代理里本地完成，数据不离开用户网络（与 Q11 的数据边界一致）。
- **倾向**：M1 做 1 和 2；3 放到 M3，随 CLI 代理一起做。

### Q24 分支合并：重放操作还是三方对比
