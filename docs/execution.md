# 执行迁移、回滚与漂移

Dowel 把“发布的版本”变成“真正改动你的数据库”的那一步叫**执行**。本页说明执行的行为、失败后怎么恢复、`dowel` 历史表长什么样、目标库账号需要什么权限，以及什么是漂移。

> 审批、执行申请、CI 令牌还没有，后续版本提供。接手现有库、认领、预演、处理漂移（保留 / 放弃线上的修改、标记为已执行）见本页下面各节和 [快速开始](getting-started.md)。

## 基本概念

- **发布 = 冻结迁移。** 发布版本时，Dowel 从上一个版本生成升级（up）和回滚（down）脚本，在影子库里验证通过后冻结。之后每个环境**沿版本链逐个执行这些冻结的脚本**，不会在执行时临时规划。所以 staging 上验证过的脚本，就是 prod 上执行的那一份。
- **环境**对应一个目标库。每个环境有“当前版本”：目标库的 `dowel` 历史里最后一次成功的执行到了哪个版本。
- **执行**把环境从当前版本沿链升到目标版本；**回滚**沿 down 链降到较早的版本。两者都在环境详情页操作，生产环境要输入环境名确认。

## 目标库账号需要的权限

执行迁移用环境里配置的那个账号（连接串里的账号），它需要：

| 用途                                   | 需要的权限                                                                                                                                                                        |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 执行你的迁移脚本                       | 脚本里每条 DDL 本身需要的权限（对相关 schema 的 `USAGE` / `CREATE`、表的所有者等）。Dowel 不会替你提权，也不会用别的账号                                                          |
| 第一次执行时建 `dowel` schema 和历史表 | 库级 `CREATE` 权限（Dowel 自己建 `dowel` schema）；或者让 DBA 事先执行 `CREATE SCHEMA dowel AUTHORIZATION "<账号>"`，Dowel 就只需要在里面建表                                     |
| 读写 `dowel` schema                    | 对 `dowel` schema 的 `USAGE` 和 `CREATE`，以及表上的读写                                                                                                                          |
| 读结构（漂移检查、执行后读回校验）     | `CONNECT` + 系统目录（默认就能读）；库里已有 `dowel` 历史时，还要对 `dowel` schema 有 `USAGE` 和表的 `SELECT`（要读当前版本）。满足这些的只读账号**能做漂移检查**，但**不能执行** |

没有建 schema 的权限时，Dowel **直接报错并给出需要 DBA 执行的语句**，不会退回到业务 schema 里建历史表。`dowel` schema 的名字固定，不能改。

## 目标库里的 `dowel` 历史

历史固定放在目标库的 `dowel` schema 里。同一个库里的多个项目共用它，表里都带 `project_id`。它只含结构、脚本和执行记录，**没有业务数据**。`dowel` schema 不会被导入，也不参与漂移比较。

| 表         | 内容                                                                                                                                                                                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `meta`     | 键值：`format_version`（历史格式的版本，当前是 1）。库里的格式比当前 Dowel 新、或者不是整数时，Dowel 拒绝执行（连读历史也拒绝）并提示升级 Dowel。格式版本只在**破坏性变更**（旧版 Dowel 照旧读写会出错）时才 +1，兼容的变更（比如加列）不动它                   |
| `projects` | 每个项目一行：项目 ID、名字、**当前认领它的 Dowel 实例的唯一标识**（`instance_id`）、认领时间 `claimed_at`、认领者 `claimed_by`、上一个实例 `previous_instance_id`。不是本实例认领的项目，本实例不能执行（见“认领”）                                            |
| `versions` | 每个执行过的版本一行：序号 `number`、名字、`parent_id`、冻结的升级 / 回滚脚本（`up_steps` / `down_steps`，`jsonb`）、`checksum`、**完整的模型**（含对象 ID）、冻结时的 schema 范围 `scope`、结构指纹、发布者和时间                                              |
| `claims`   | 认领事件，**只追加**（触发器禁止修改和删除）：哪个实例、从哪个实例手里、谁确认的、什么时候                                                                                                                                                                      |
| `history`  | 每次执行一行：`from_version` → `to_version`、方向（`baseline` / `up` / `down` / `mark`；`mark` 是“标记为已执行”，没有执行任何 SQL，见“漂移”）、状态（`running` / `done` / `failed`）、断点 `step_index`、错误信息、执行者、来源（`web` / `ci`）、实例、起止时间 |

要点：

- **`history` 只追加**：触发器禁止删除，只允许改仍在 `running` 的行，且标识字段不能变，已结束（`done` / `failed`）的行不能再改。这是防止误改的保护，不是安全边界——表的所有者和超级用户仍然能删触发器。
- **当前版本** = 最后一条 `done` 的记录的 `to_version`（执行、回滚、基线、标记都一样）；失败和进行中的记录不改变它。
- **`checksum`** 是升级 + 回滚脚本规范化 JSON 的 sha256。每次执行前，Dowel 会按脚本**内容重算**每个版本的校验和，与记录比对；对不上就拒绝（见下面的“完整性检查”）。
- **模型和脚本都存在目标库里**，所以即使平台数据丢了，也能靠它接手这个库（见 [快速开始](getting-started.md) 的“接手现有项目”和“灾难恢复”）。

## 第一次执行到某个库

目标库里还没有这个项目的历史时，Dowel 先看库里的结构：

| 库里的结构                                                                           | Dowel 做什么                                                                                                      |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| **等于链上第一个版本的模型**（通常是“从这个库导入”的项目，第一个版本是 `v0 · 基线`） | **只写入基线**：建 `dowel` schema、记下这个版本和一条 `baseline` 记录，**不执行任何 SQL**。之后正常执行后面的版本 |
| **空库**（范围内没有任何对象）                                                       | 执行第一个版本的 up，完整建库                                                                                     |
| 其他                                                                                 | 报**漂移**，拒绝执行，并列出“库的结构 → 基线”的差异。**这时 Dowel 不会在你的库里建任何东西**                      |

“空库”指全新的 PostgreSQL 库：只有 `public` schema（PostgreSQL 给它加的默认注释 `standard public schema` 不算差异）。项目设置了 schema 范围时，只看范围内的 schema。

也可以在环境详情页单独点“写基线”：只写历史、不执行，之后再决定什么时候执行。

## 执行

一次执行按下面的顺序检查，**任何一步不通过都会拒绝，且什么都不会改**：

1. **拿项目锁**。同一个项目在同一个库上同时只能有一个执行：另一次执行会等锁，**默认等 30 秒**，超时失败。等到锁之后会重新读取状态——如果前一次已经把环境执行到了目标版本，这一次就什么都不做。
2. **完整性检查**。平台里的版本链和目标库 `dowel` 历史里的版本链都必须完整：序号连续、`parent` 衔接、**每个版本的冻结脚本按内容重算的校验和等于记录值**。两边还要互相一致（目标库历史里的版本都在平台的链上、校验和相同）。有人改了目标库历史里的校验和或脚本，会在这里被发现。这一步最先看**认领**：目标库里记着的“当前认领这个项目的实例”不是本实例，就直接拒绝（`foreign_instance`），见下面“认领”。
3. **漂移检查**。读目标库的当前结构，与环境当前版本的模型比较，不一致就拒绝（见下面的“漂移”）。读结构用的 schema 范围是**环境当前版本冻结时记录的范围**（第一次执行用第一个版本的），不是项目现在的设置——项目的范围之后改了，旧版本的比较结果不会变。
4. **验证检查**。要执行的每个迁移都必须已经**在影子库里验证通过**（版本页上的“已验证”）。执行前不会重新验证；未验证的版本被拒绝，提示先去“重新验证”。人工改过脚本的版本改完就回到未验证。
5. **实例级语句检查**。迁移里不能有 `CREATE / DROP / ALTER DATABASE`、`TABLESPACE`、`ROLE | USER | GROUP`、`ALTER SYSTEM`，有就拒绝。
6. **逐个迁移执行**，每个迁移执行完都**读回目标库的结构，必须等于目标版本的模型**，否则这个迁移当作失败。

### 事务与非事务步骤

- **没有非事务步骤的迁移是一个事务**：它的历史记录、全部脚本步骤、读回校验和版本记录都在同一个事务里，要么全部提交，要么全部回滚。读回的结构不对时，事务回滚，库保持原样。
- 含**不能放进事务的步骤**（`CREATE INDEX CONCURRENTLY`、`VACUUM`、`REINDEX DATABASE / SYSTEM`、不带表名的 `CLUSTER`、`ALTER TYPE … ADD VALUE` 等）的迁移不是原子的：Dowel 按“一段事务步骤 / 一个非事务步骤”依次执行，**每做完一段就记一个断点**（`history.step_index`），最后一段里做读回校验并结束记录。版本页和环境页会标出这类迁移。
- 执行时用的是与影子库验证时相同的固定会话设置（时区、日期格式、`search_path` 等），所以脚本在目标库上的行为与验证时一致；执行结束后这些设置会被重置，不会留在连接上。

### 回滚

回滚沿 **down 链**逐个执行：从当前版本开始，依次执行当前版本的回滚脚本、再前一个版本的回滚脚本……直到目标版本。规则与执行完全相同（完整性、漂移、验证、实例级语句、读回校验）。第一个版本（基线）没有回滚脚本，不能回滚到它之前。

回滚不会让版本变得“没执行过”：目标库历史里仍然记着它，所以**任何环境上执行过的版本都不能再编辑脚本**（版本页返回 409）。“执行过”是**永久**的：Dowel 在版本自己身上记下第一次执行的时间，只写一次、不会清除——换了环境的连接串、目标库被清空、目标库里的历史被人手工删掉、环境被删除，都不会让它重新变得可以编辑。（只有目标库一点没改动的失败才不算执行过——事务整体回滚、建 `dowel` 历史时权限不足等；Dowel 在第一次对目标库做会留下痕迹的写入之前记下这件事，所以不管失败是什么类型的错误，判断都一样。执行进行中的版本脚本也不能改；Dowel 进程崩溃留下的“进行中”标记，会在下一次读取目标库历史或执行时清掉。事务型迁移是在 `COMMIT` 成功之后才算动过目标库——`COMMIT` 本身失败（比如 DEFERRABLE 约束到提交时才检查）时，库里没有任何变化，版本仍然可以编辑。）

**本进程正在对环境执行时，不能改环境的连接配置（连接串、影子库、是否允许同实例影子库），也不能删除环境**（409，“环境正在执行，稍后再改”；被拒绝的请求不会对任何数据库产生副作用）。如果环境上还留着没收尾的“进行中”标记（Dowel 进程崩溃留下的）而本进程没有在执行，修改**不会被挡住**，按保守方向处理：这些版本当作执行过（永久，不能再编辑），标记删掉，然后照常改连接串或删环境。**这样处理，最坏的结果是一个其实没碰过目标库的版本不能再编辑了，而不会让碰过库的版本又能编辑。**执行开始时，如果等锁期间环境的连接串被改了，执行用的是新连接串；环境被删了就拒绝执行。Dowel 目前只支持**单进程部署**，这些保护和对残留标记的清理都依赖这一点。

## 预演（dry run）

执行、回滚、写基线的**确认对话框一打开就会先预演**，把结果显示出来，你确认之后才真正执行。预演做完全部“执行前检查”，但**什么都不写**：

- 检查：项目锁（能不能拿到）、完整性、认领、漂移、要执行的迁移是否已验证、实例级语句、目标库里的 `dowel` 历史能不能写（账号有没有建 schema / 建表的权限，历史格式是不是比当前 Dowel 新）。
- 列出：要执行（或回滚）的迁移和每一步 SQL；哪些步骤**不在事务里**（含这类步骤的迁移不是原子的）；发布 / 重新验证时存下来的**风险摘要**（只有升级脚本有；回滚脚本没有锁和重写分析）；上一次停在中途时**会从哪个迁移的哪一步接着跑**；目标库还没有历史时，是只写基线还是在空库上建库，以及**会新建 `dowel` schema**。
- **不写目标库**：不建 `dowel` schema（预演之后一个还没有历史的库仍然没有 `dowel` schema）、不写执行记录。**也不写平台库的登记**（不登记“这个版本即将在这个环境执行”、不改环境的当前版本和缓存）。
- 检查没通过**也是正常返回**：对话框显示原因（漂移的差异、未验证、被别的实例认领、锁被占用……），和真正执行时的错误是同一套文案。预演只等项目锁几秒，正在执行时直接报告“锁被占用”，不会排队。
- **权限和真正的执行一样**（预演要连目标库、会暴露将要执行的脚本）；**生产环境预演不需要输入环境名**，因为什么都不会写。

## 认领

目标库的 `dowel.projects` 里记着**当前认领这个项目的 Dowel 实例**。执行只允许认领它的那个实例：

- 第一次执行到某个库时，执行它的实例登记为认领者。
- **另一个实例**（或者平台库丢失重建后 `instance_id` 变了的同一个实例）要接手这个库的历史，必须由**它的实例管理员**确认“**认领**”。认领写 `dowel.projects`（认领者、`claimed_by`、`claimed_at`、上一个实例 `previous_instance_id`），并在只追加的 `dowel.claims` 里记一条事件。`history` 里的执行记录原样保留，不会被改写。
- **后果**（确认对话框里会说明）：认领之后，**原实例再执行这个库会被拒绝**（`foreign_instance`，在所有其他检查之前）；**只读的漂移检查和读历史不受影响**，原实例仍然能看。要换回来，原实例的实例管理员再认领一次即可（没有单独的“撤销”）。
- 认领的入口：接手现有项目时（向导里，确认后一并认领）、给已有项目接入已有历史时（见 [快速开始](getting-started.md)）、以及**环境详情页**：目标库的项目由别的实例认领时，页面显示认领情况（谁认领的、什么时候、上一个是谁），实例管理员看得到“认领”按钮。其他人只能看到认领情况。
- 认领前 Dowel 先确认历史是完整的、并且与平台的版本链对得上（校验和、模型）；历史被改坏就拒绝认领。认领要取目标库的项目锁：原实例正在执行时不能认领。
- 认领是对目标库的写入，所以**只有实例管理员**能做；它和执行档位无关。

## 失败与恢复

- **步骤因为执行策略的超时被取消**（等锁超过锁等待超时、语句超过语句超时）：错误代码是 `step_timeout`，原因里写明是哪一种超时和设定的秒数，和脚本本身的错误区分开。处理方式和下面的“步骤报错”完全一样：事务型迁移整体回滚、稍后重试；含非事务步骤的迁移从断点续跑。见 [执行策略](execution-policy.md#超时语句超时与锁等待超时)。
- **某个迁移的步骤报错**：停在**最后一个成功的版本**。事务型迁移整体回滚，库里没有留下半个迁移；历史里多一条 `failed` 记录（带错误信息）。修好原因（比如清掉重复数据）后**直接重试**即可。没有任何环境执行成功过、且事务整体回滚的版本，**脚本还可以修改**。
- **含非事务步骤的迁移失败**：已提交的部分**不会回滚**，库处于“半途”状态。历史里这次执行是 `failed`，`step_index` 记着最后做完的一步。第一个非事务步骤执行**之前**，Dowel 先把断点记成 `-1`（“已经开始动目标库，但还没完成任何一步”）：如果它第一步就失败了（比如 `CREATE UNIQUE INDEX CONCURRENTLY` 因为重复数据失败，留下了无效索引），库同样算“半途”，同样从断点续跑，不会被判成漂移。**重试时 Dowel 从断点接着跑**，不会重复执行已经完成的步骤。半途状态下：
  - 漂移检查会跳过（结构既不是旧版本也不是新版本，没法比）；
  - **必须先把这次迁移跑完**，不能改做别的（比如直接回滚会被拒绝，并提示先继续）；
  - 例外：如果你在目标库上**手工把剩下的步骤补完了**（或者决定放弃它、手工改成了别的版本的样子），可以用“**标记为已执行**”让历史追上现实（见“漂移”）——标记在半途状态下也可用，标记之后这个状态就结束了。
- **`CREATE INDEX CONCURRENTLY` 失败**（比如唯一冲突）会在 PostgreSQL 里留下一个**无效（INVALID）索引**。重试前 Dowel 会自动把它删掉再重建，不需要你手工处理。删除是**精确匹配**的：从语句里解析出索引名和它所在表的 `schema.table`，只删这张表上、同名、状态为 INVALID 的索引——别的 schema 里的同名表、同名索引不会动。语句里的表没写 schema，或者 Dowel 解析不了语句时**不会删除**任何东西，失败信息里会提示你手工 `DROP INDEX CONCURRENTLY` 后重试。
- **进程中途被杀**：事务型迁移的事务会被数据库回滚；含非事务步骤的迁移留下 `running` 记录，下一次执行同样从断点续跑。项目锁是数据库会话级的，进程退出后自动释放。
- **任何意外错误**（读结构失败、schema 范围有问题、连接断开……）：Dowel 先把一条 `failed` 记录写进历史（文本脱敏；写记录本身失败，比如连接已经断了，只记日志、仍然抛出原错误），再把错误报给你。失败记录总是在事务之外写的——事务型迁移回滚后另起一个事务写，不会跟着回滚消失，也不会让这次执行一直停在 `running`。
- **读回校验失败**（执行完的结构与目标版本的模型不一致）：说明脚本和模型对不上（比如人工改过脚本）。事务型迁移整体回滚、记 `failed`；需要修脚本并重新验证。
- **需要人工修正的状态**：含非事务步骤的迁移，**所有步骤都做完了**，读回的结构却不等于目标版本（最后一步是非事务步骤时尤其会这样：它已经提交，没法回滚）。这说明脚本本身的结果就不对，**接着跑解决不了**。这时这次执行记为 `failed`，错误文本以 `[readback_mismatch]` 开头，**不算“停在中途”**，不会续跑，也不会无限重复同样的读回。库停在半途状态，Dowel 的做法是：
  - 漂移检查和执行 / 回滚都把它报成**漂移**，附上与当前版本模型的差异，并说明“这个差异是上一次执行留下的、需要手工修正”；环境页顶部有红色提示条；
  - 你要手工把目标库改回当前版本的样子（差异列表里的 SQL 就是需要做的事），漂移消失后才能再执行；
  - 想继续这个版本，先修脚本（版本没有任何环境“执行过”之前才能改，而这个版本已经动过目标库，所以通常要发布一个新版本来替代它）；或者手工把库改成目标版本的样子后，用“**标记为已执行**”把环境记到那个版本。
  - **手工修好之后**：把目标库改回**当前版本**的样子（读回失败的那次执行的起点）后，漂移检查返回“无漂移”，红色提示条消失（提示条只在漂移检查的结果仍是“漂移”并且差异是上一次执行留下的时才显示；执行因读回失败的那一刻，漂移状态就会同时刷新成“漂移”，不需要再手动检查一次）。环境的当前版本仍是历史里最后一次成功的版本，**不会**因此认为已经到了目标版本，也不会补写一条记录；历史里那条读回失败的记录还在（历史只追加），只是不再有意义。之后再执行，会从头重新执行那个迁移。如果手工把库改成了**目标版本**的样子，漂移检查是拿它和当前版本比较，所以仍会报漂移；这时用“**标记为已执行**”：Dowel 核对线上结构等于目标版本的模型后，写一条 `mark` 记录，环境就记到了目标版本（见“漂移”）。**Dowel 有意不在“结构恰好等于目标版本”时自动补写一条完成记录**——只含数据步骤的版本在结构上和父版本相同，会被悄悄跳过；线上能等于目标本身就意味着已经漂移，自动跳过等于悄悄把漂移合法化。标记是你明确做的一个动作，并且有核对和审计。
- 所有错误文本在返回给浏览器、写进审计和写进目标库历史之前都会**脱敏**（连接串里的密码会被遮掉）。

## 漂移

**漂移**指目标库的实际结构与 Dowel 记录的环境当前版本不一致——通常是有人绕过 Dowel 直接在库上 `ALTER` 了东西。执行和回滚在漂移时会被拒绝，因为在一个已经变了样的库上继续执行，结果没法预期。

- **怎么比**：Dowel 读目标库结构，先比**结构指纹**（每次执行时读回结构记下的值，比较时去掉了列的物理顺序等不稳定字段），一样就没有漂移；不一样再把线上结构导入成模型，与当前版本的模型比较，得到差异列表。差异用“**线上结构 → 当前版本模型**”表示：每一项是要让线上结构回到当前版本需要做的一步（类型、对象、SQL）。差异最多显示 100 项，同时显示总数。
- **什么时候检查**：每次执行 / 回滚前都会检查；环境页有“**检查漂移**”按钮手动检查；服务端还有**定时检查**，默认每小时一次，用环境变量 `DOWEL_DRIFT_INTERVAL_MINUTES` 调整（分钟，`0` 关闭）。
- **结果缓存**在平台库的环境上（最近检查时间、状态、差异摘要）。**图标栏的“环境”入口和项目概览页**在有漂移的环境上显示警告。
- 检查时目标库**正在执行**、或上一次执行**停在中途**时会跳过。检查本身失败记为“检查失败”，不算漂移，**文案说明真实原因**：连不上目标库、目标库返回错误（权限等）、目标库历史与平台版本链对不上（完整性）、schema 范围有问题（跨范围引用）、读不了 `dowel` 历史，其他意外错误只在服务器日志里留详情。
- **怎么处理漂移**：有两条路，生产和非生产行为相同，两个按钮不分主次，都在环境页的漂移详情里。见下面“保留线上的修改”和“放弃线上的修改”。

### 保留线上的修改：导入 → 发布 → 标记为已执行

线上的改动是对的、要留下来时：

1. **导入**（“保留线上的修改”按钮，也就是环境页的“从此库导入结构”）：读出这个环境的线上结构，**按名字沿用工作副本里的对象 ID**，然后**覆盖**工作副本。这是普通的模型编辑，**项目编辑者就能做**；和“检查漂移”共用连接限速；审计里记来源环境和线上结构指纹。**确认覆盖时绑定预览时的线上结构指纹**：确认请求带着预览拿到的指纹，服务端重新读线上结构，指纹不一致（预览之后又有人改了库）就拒绝并给出新的差异（409），对话框显示“线上结构在预览之后变了”，让你重新确认。覆盖前对话框先给**差异预览**（覆盖会带来的变化），并在这些情况下**警告（不拦截）**：环境落后于链头（导入的是它现在的结构，覆盖会撤销中间版本的修改；环境从来没有执行过、链上却已经有版本时也一样）、环境有半途失败的迁移或上一次执行的读回校验失败（两种分开说明）、工作副本有未发布的修改（会被覆盖）。**确认覆盖同时绑定预览时的工作副本版本**：预览之后别人又改了模型（工作副本变了），服务端拒绝并给出新的预览（409），对话框提示“工作副本在预览之后变了”，让你重新确认，不会悄悄盖掉别人刚改的内容。
2. **检查和修改**：线上结构是按名字导入的——手工做的改名会被识别成“删一列、加一列”。发布前在模型里把它改回改名（保住对象 ID），冻结出来的才是 `RENAME`。
3. **发布**：走普通的发布流程（冻结真实的 up / down，影子库验证），没有任何特殊标记。
4. **标记为已执行**：把漂移的环境标记到新版本（见下）。其他环境把它当普通版本执行。

### 放弃线上的修改：修复脚本

线上的改动不要时：漂移详情里的“**放弃线上的修改**”显示**修复脚本**——`plan(线上结构, 当前版本的模型)`，也就是上面差异列表里的那些步骤，带固定的会话设置，可以复制，并提示风险（会删掉线上的对象或其中的数据的步骤；改列类型可能重写整张表）。模型表达不了的差异（`unresolvable`）单独列为“**需要手工处理**”。风险提示**按规划器步骤的种类**统计，不靠文本里有没有 `drop`：会删掉对象或数据的步骤（删表、删列、删 schema / 序列 / 类型 / 视图等不透明对象 / 索引）、去掉约束的步骤（单独一类：不丢数据，但会放开保护）、改列类型的步骤（可能重写整表）；`DROP DEFAULT`、`DROP NOT NULL` 不算；**重建不算删除**：同一个对象先删再建（比如索引定义变了、约束重建）、枚举去掉一个值时用的临时副本（`_dowel_tmp_*`）都不计入“删除”，只在有重建时单独提示“重建 N 个对象”。

**Dowel 不代为执行修复脚本**：它是临时 plan 出来的、没验证过的 SQL，不属于发布时冻结验证过的那一份。你自己在目标库上执行，然后点“**重新检查漂移**”。漂移摘要只保存前 100 项：脚本不完整时对话框会说明，执行后重新检查，剩下的会再列出来。

### 标记为已执行

**不执行任何 SQL**，只在目标库的迁移历史里把环境记为“已经到达版本 X”。适用于线上已经手工改成这个版本的情况：热修之后发布了包含它的新版本、读回失败后手工修好、含非事务步骤的迁移半途失败后手工补完、手工回退了一次发布。第一次执行时的“写入基线”是它的特例。

- **目标版本 X 可以是链上任意版本**，比当前版本新（向前）或旧（向后）都行。按钮按方向显示“标记为已执行到 vN”或“标记为已回滚到 vN”；历史里这类记录显示“标记”。
- **核对**：Dowel 在项目锁里读出线上结构，`plan(线上结构, X 的模型)` 必须为空，否则**拒绝并列出差异**——标记只记录“已经到达这个版本”，不改库。确认框一打开就先核对（预演）。
- **写入**：一条 `direction = 'mark'` 的历史记录，from 是当前版本，to 是 X。向前标记时，X 和中间跳过的版本在平台上记为**执行过**（`executed_at`，它们的脚本从此不能再编辑），并在目标库补上这些版本的版本行；**向后标记不写 `executed_at`**，版本的可编辑性不变。
- **确认框**：向前标记会列出**被跳过的版本和它们的脚本**（这些脚本不会执行——数据步骤、需要手工做的事都不会发生），你必须勾选“这些脚本的效果已经手工完成，或者不需要”才能确认。**这个确认绑定到预演的结果**：确认请求带着预演时的计划（当前版本、目标版本、跳过的版本、线上结构指纹），服务端在项目锁里重新算一遍，对不上（预演之后有人又标记了、又改了库）就**拒绝并给出新的计划**，什么都不写；对话框刷新成新的预演结果，提示“目标库在核对之后变了，请重新确认”，已经勾选的确认也会清掉，要对着新的计划重新勾选。向前标记没有带着预演的计划、或者没有勾选确认，都会被拒绝（而且在目标库里建 `dowel` schema 之前就拒绝，没有历史的库被拒绝后仍然没有任何改动）；向后标记和标记到当前版本没有被跳过的版本，不需要这些。
- **半途状态也能标记**：上一次执行停在中途、或读回校验失败时，手工处理好之后用标记走出来。这时目标版本**也可以就是当前版本**：DBA 手工把半途的库改回了当前版本的样子，标记到当前版本（按钮显示“标记为停在 vN（放弃未完成的迁移）”）会写一条 from = to = 当前版本的 `mark` 记录，关掉那次未完成的运行；之后执行从头重跑那个迁移。没有未完成的运行时，标记到当前版本是“已经记在这个版本”，不需要标记。这种标记同样要核对线上结构，也不改变版本能不能编辑。
- **确认框以服务端的预演为准**：向前还是向后、跳过哪些版本、要不要勾选确认，都用打开确认框时服务端预演返回的计划，不用页面缓存的状态（缓存可能已经过期）；按钮文案先按缓存显示，预演返回后再按预演结果更新。有未完成的运行时，下拉里的“当前”、方向和“停在 vN”也以执行器读目标库历史得到的当前版本为准，不用平台缓存。
- **权限**：特权操作，按环境的“谁能执行”档位（`environment.mark`）；生产环境要输入环境名；将来的 CI 令牌不能标记。审计成功、失败各记一条（from、to、跳过的版本、线上结构指纹）。标记不受前置环境约束（它不跑脚本）。

### 已知限制

- **环境落后于链头时，带着漂移不能往前执行。**例如 prod 停在 v5、做了热修，而链头已经到 v7：线上结构不等于任何可发布的版本，Dowel 不会“带着漂移往前执行”。只能先按修复脚本把库改回 v5（当前版本），再往前执行。（导入时的差异预览会在这种情况下警告：覆盖会撤销中间版本的修改。）
- 导入时不做三方合并。

## 谁能执行

谁能执行由**执行策略**决定：实例 → 组 → 项目 → 环境四层配置、逐层取更严，详见 [执行策略、执行者与前置环境](execution-policy.md)。简要说：

| 档位       | 谁能执行                     |
| ---------- | ---------------------------- |
| 项目编辑者 | 项目编辑者及以上，以及执行者 |
| 项目管理员 | 项目管理员，以及执行者       |
| 仅限执行者 | 只有被授予“执行者”的用户或组 |

**默认**：非生产环境是项目编辑者，生产环境是项目管理员。实例管理员不受限制。

受它约束的**特权操作**有：执行 / 回滚、写入基线、改连接串和影子库设置、取消“生产”标记、删除环境、**标记为已执行**、**给已有项目添加环境并接入已有历史**。预演和真正的执行用同一个权限。其中改连接串、取消生产标记、删除环境、接入已有历史这些配置类操作**另外至少要项目管理员**。放宽执行策略本身也是特权操作（收紧不是）。取消“生产”标记不会悄悄放宽：变宽的项会固定在环境层。

执行策略里还可以配置**审批流程**：配置了审批环节的环境，执行和回滚都要先提交**执行申请**、审批通过后再执行（实例管理员另有紧急执行），见 [执行申请与审批](approvals.md)。没有直接执行权限的人也可以在默认流程下提交申请，由有执行权限的人“通过并执行”。

执行策略里还有**前置环境**（执行到本环境的版本不能比前置环境新）和**超时**（锁等待默认 5 秒、语句默认不限，超时的步骤报 `step_timeout`，可以重试），见同一页。

**模型的编辑和发布不受执行策略约束**，仍然按项目角色。查看者不能执行（除非被授予了执行者）。

生产环境的执行、回滚、写基线必须在确认对话框里**输入环境名**，服务端也会校验。每次执行都写进审计日志（谁、哪个环境、哪些版本、成功还是失败）。
