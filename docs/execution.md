# 执行迁移、回滚与漂移

Dowel 把“发布的版本”真正作用到目标数据库的步骤称为**执行**。本页说明执行的完整校验链、不同方言的目标库历史表与账号权限、预演、认领、失败与断点恢复，以及漂移检测与处理。

> 相关阅读：[执行策略与执行者](execution-policy.md)、[执行申请与审批](approvals.md)、[组级 Webhook](webhooks.md)、[接手现有项目与灾难恢复](takeover.md)、[CI HTTP API](api.md) 与 [多方言与版本支持](dialects.md)。

## 基本概念 {#basic-concepts}

- **发布即冻结迁移**：发布版本时，Dowel 基于上一个版本生成升级（up）与回滚（down）脚本，经影子库验证后冻结。所有环境均按链逐个执行这些冻结好的脚本，不会在执行阶段临时重新规划。
- **环境当前版本**：目标库的 Dowel 历史记录中最后一条成功结束（`status = 'done'`）的执行所到达的版本。
- **执行与回滚**：在环境详情页可将环境从当前版本升级到较新版本，或沿着 down 链回滚到较早版本；生产环境操作须输入环境名称二次确认。

## 目标库账号权限与历史表位置 {#target-privileges}

执行迁移始终使用环境配置中填写的数据库账号，Dowel 不会提权或切换账号。不同方言的历史存储方式如下：

- **PostgreSQL / SQL Server**：迁移历史固定放在目标库的 `dowel` schema（`dowel.meta`、`dowel.projects`、`dowel.versions`、`dowel.history`、`dowel.claims`）。
- **SQLite / MySQL**：因方言不支持同一数据库内的独立 schema 命名空间，历史存储在同库的 `dowel_` 前缀表（`dowel_meta`、`dowel_projects`、`dowel_versions`、`dowel_history`、`dowel_claims`）。

### 账号所需权限 {#privilege-table}

| 用途                 | PostgreSQL / SQL Server                                                                                                      | SQLite / MySQL                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 执行业务 DDL         | 脚本本身涉及的业务 schema 与对象权限                                                                                         | 目标库 / 文件读写与 DDL 权限                                   |
| 首次建历史表         | 数据库级 `CREATE`（或 `CREATE SCHEMA`）权限；也可由 DBA 预建 `dowel` schema 并把所有权或 `CREATE`/`ALTER`/`USAGE` 授给该账号 | 建表与建触发器权限（SQLite 需允许读写且未设 `query_only = 1`） |
| 读写迁移历史         | 对 `dowel` schema 的读写及触发器执行权限                                                                                     | 对 `dowel_*` 表的读写与触发器权限                              |
| 漂移检测与只读查历史 | 连接权限 + 系统目录读权限 + `dowel` schema 只读（此类只读账号可检测漂移，不能执行）                                          | 连接 / 文件读权限 + `dowel_*` 表只读权限                       |

若目标账号没有建 `dowel` schema 的权限，Dowel 会直接报错并给出让 DBA 预先执行的授权语句，绝不退回业务 schema 中建表。`dowel` schema 与 `dowel_*` 表名固定且不可更改，导入与漂移比对时永远自动跳过。

### 历史表结构 {#history-tables}

同一个数据库中的多个项目可共用这套历史表，表内通过 `project_id` 隔离：

| 表名（schema / 前缀）         | 内容                                                                                                                                                                                                           |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `meta` / `dowel_meta`         | 键值表，记录 `format_version`（当前为 `1`）。若库内格式版本高于当前 Dowel 支持版本，Dowel 一律拒绝读写并提示升级服务端                                                                                         |
| `projects` / `dowel_projects` | 每个项目一行：项目 ID、名字、当前认领实例 `instance_id`、认领时间、认领人、上一个认领实例 `previous_instance_id`                                                                                               |
| `versions` / `dowel_versions` | 每个已在该库执行过的版本一行：序号、名称、`parent_id`、冻结的 `up_steps` / `down_steps`、`checksum`、完整 `model`（含对象 ID）、冻结时的 `scope`、指纹与发布信息                                               |
| `claims` / `dowel_claims`     | 实例认领事件记录（只追加，触发器禁止更新与删除）                                                                                                                                                               |
| `history` / `dowel_history`   | 每次执行一行：`from_version` → `to_version`、方向（`baseline` / `up` / `down` / `mark`）、状态（`running` / `done` / `failed`）、断点 `step_index`、错误信息、执行者、来源（`web` / `ci`）、实例 ID 与起止时间 |

要点：

- **`history` 与 `claims` 只追加**：四方言均通过数据库触发器禁止 `DELETE`，并禁止修改已结束（`done` / `failed`）或标识字段（库所有者或超级用户可修改触发器，这是防误操作保护而非权限隔离边界）。
- **`checksum` 完整性校验**：由规范化后的升级与回滚脚本 JSON 计算 SHA-256，执行前会逐版重算比对，篡改脚本或校验和将被拦截。
- **跨实例可恢复**：由于每个版本的完整模型与对象 ID 都写在目标库中，平台库丢失时可按[接手现有项目与灾难恢复](takeover.md)完整重建。

## 首次执行到某个库 {#first-run}

当目标库里还没有当前项目的历史记录时，Dowel 先读取目标库的现状：

| 目标库现状                                                                   | 首次执行行为                                                                                                 |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 结构**完全等于链上第一个版本的模型**（例如刚从此库导入并生成了 `v0 · 基线`） | **写入基线**：创建历史表，记录第一个版本与一条 `baseline` 历史，**不执行任何业务 DDL**，随后照常执行后续版本 |
| **空库**（指定范围内无任何用户对象）                                         | 建历史表后执行第一个版本的升级脚本完整建库                                                                   |
| 其他不一致结构                                                               | 报告**漂移**并列出与基线的差异，拒绝执行，**不在目标库创建 `dowel` 历史表**                                  |

也可以在环境详情页单独点击“写入基线”先行建立历史基准。

## 执行与校验顺序 {#execution-steps}

每次执行（或回滚）都会严格按以下顺序检查，任一步不通过均立即中止且不改动目标库：

1. **获取项目锁**：同一项目在同一个目标库同时只能有一项执行在进行。并发请求会等待锁（默认 30 秒，超时报 `lock_timeout`）；PG 采用事务/会话级 advisory lock，SQL Server 采用独占单连接 Session 级 `sp_getapplock`，MySQL 采用独占连接 `GET_LOCK`，SQLite 采用按规范文件路径隔离的互斥锁。
2. **实例认领与完整性检查**：首先核对 `projects.instance_id` 是否为本实例（否则报 `foreign_instance`）；随后检验平台链与目标库版本链是否序号连续、`parent` 衔接、`checksum` 吻合。
3. **漂移检查**：读回目标库当前结构快照，与环境当前版本模型比较（使用该当前版本冻结时记录的 `scope`），不一致则拒绝执行。
4. **验证状态检查**：路径上的每个迁移必须已在影子库验证通过；人工修改过脚本且尚未重新验证的版本会被拒绝。
5. **高危语句检查**：拒绝包含实例级或篡改 `dowel` 历史对象语句的迁移。
6. **逐个迁移执行与读回校验**：按版本链顺序执行迁移，每个迁移执行完成后立即读回目标库结构，必须与目标版本模型严格相等，否则判定失败。

### 事务、非事务与隐式提交处理 {#tx-and-nontx}

- **事务型迁移**（PostgreSQL 常规 DDL、SQL Server 常规 DDL、SQLite 常规 DDL）：整步及历史更新位于同一事务内，任意报错或读回结构不符时整体回滚，目标库保持原样。
- **非事务步骤与 MySQL 隐式提交**：
  - **PostgreSQL** 的 `CREATE/DROP INDEX CONCURRENTLY`、`VACUUM`、`REINDEX DATABASE/SYSTEM`、无表名 `CLUSTER`、`ALTER TYPE … ADD VALUE`；
  - **SQLite** 的 12 步表重建块（在事务外切换 `PRAGMA foreign_keys = OFF/ON` 并内部自建 `BEGIN IMMEDIATE … PRAGMA foreign_key_check … COMMIT`）与 `VACUUM`；
  - **SQL Server** 的 `CREATE/ALTER/DROP FULLTEXT` 等不可入事务语句；
  - **MySQL** 的所有 DDL 语句（引擎会自动隐式提交）。
    上述非原子迁移均按“事务段 / 非事务单步”依次执行，每完成一步即更新 `history.step_index` 断点；MySQL 若发生“DDL 已提交但断点尚未写入前进程崩溃”，重试时还会结合 `information_schema` 与对应错误号做确定性幂等探测，确认已生效则安全跳过。
- 所有脚本在执行时均应用与影子库验证一致的固定会话参数（UTC 时区、严格模式等），结束后恢复连接原有设置。

### 回滚与版本锁定规则 {#rollback-and-lock}

- 回滚沿版本链逐个执行各版本的 `down` 脚本，检查规则与升级完全一致（`v0 · 基线` 或链的起点版本没有回滚脚本，无法回滚到它之前）。
- **永久执行标记**：一旦某个版本对目标库产生了实际写入痕迹（事务提交成功，或非事务/MySQL 迁移开始执行第一步非事务步骤），平台侧会永久记录该版本的 `executed_at`。此后即使回滚、删除环境、更换连接串或清空目标库，**该版本脚本也不再允许编辑**。
- **环境正在执行时的变更限制**：当环境处于执行锁占用中时，禁止修改连接串、影子库设置、删除环境或切换生产标记（返回 409）。若旧进程崩溃遗留了未收尾的 `running` 标记且当前已无实际执行，修改环境时会将受影响版本保守标记为已执行并清理残留标记。

## 预演（dry run） {#dry-run}

打开执行、回滚或写基线确认框时，服务端会自动先完成一次只读**预演**：

- 执行与真实执行完全相同的全部前置检查（项目锁、完整性、认领、漂移、验证状态、高危语句与历史表写权限）；
- 展示要经历的迁移、每条 SQL、哪些步骤不在事务内（含 MySQL 隐式提交标识）、发布时保存的风险摘要、中断续跑的起始位置，以及首次执行时是否会新建 `dowel` 历史表；
- **绝不向目标库或平台库写入任何状态**（不会创建 `dowel` 历史表或更改环境当前版本）；
- 检查未通过同样正常返回差异或失败原因（预演只等待锁数秒，若环境正忙直接提示锁被占用）；生产环境预演无需输入环境名。

## 认领 {#claim}

只有目标库历史中记录的**当前认领实例**才被允许向该库执行或回滚：

- 首次向新库执行时自动登记本实例为认领者；
- 若目标库目前由其他实例认领（包含平台库重建导致 `instance_id` 变更），必须由本实例的**实例管理员**在环境详情页（或向导接手时）确认**认领**；
- 认领会在 `dowel.projects` / `dowel_projects` 更新认领者并在只追加的 `claims` / `dowel_claims` 写入记录，原执行记录完整保留；
- **认领生效后，原实例向该库的执行或回滚请求一律被拒绝（`foreign_instance`）**，但其只读漂移检查与查看历史不受影响。不提供“撤销认领”，如需归还归属应由原实例管理员反向认领。

## 失败与恢复 {#failure-recovery}

- **策略超时取消（`step_timeout`）**：当等待锁或语句执行超过[执行策略](execution-policy.md#timeouts)设定的秒数时，报错明确标明超时类型与设定阈值，区别于普通 SQL 报错。事务型迁移整体回滚后直接重试；非事务/MySQL 迁移从断点继续执行。
- **中途中断与断点续跑**：含非事务步骤或 MySQL DDL 迁移在中途失败或进程崩溃后，库处于半途状态（`history.step_index` 记下最后完成步序号，若第一步非事务语句即开始，断点记为 `-1`）。半途状态下跳过漂移检查，并禁止直接回滚或跳版本操作，需继续重试跑完或手工补全后使用“标记为已执行”。
- **PostgreSQL 并发操作兜底清理**：
  - `CREATE INDEX CONCURRENTLY` 失败在目标表留下 `INVALID` 索引时，若能精确解析出含 schema 的表与索引名，重试前会自动 `DROP INDEX CONCURRENTLY IF EXISTS` 清理后再重建；未能解析时会提示手工清理。
  - `ALTER TABLE … DETACH PARTITION … CONCURRENTLY` 因锁超时停在 `detach pending` 时，重试自动转为执行 `ALTER TABLE … DETACH PARTITION … FINALIZE` 完成分离。
- **读回校验失败（`[readback_mismatch]`）**：当一个非事务迁移全部步骤跑完后，读回结构仍不等于目标版本（常见于手工修改后的脚本与模型不符），Dowel 不会无限续跑，而是将此次运行记为 `failed` 并触发漂移告警：你可以手工将库改回当前版本后重试，或手工改到目标版本后通过“标记为已执行”对齐历史。
- **错误信息脱敏**：所有返回给前端、写入审计与写入目标库历史的错误消息均自动脱敏密码与连接串凭据。

## 漂移 {#drift}

**漂移**指目标库的实际结构与该环境“当前版本”的模型不一致（通常因有人绕过 Dowel 直接修改目标库所致）。存在漂移时，执行与回滚会被拒绝。

### 检查方式与触发时机 {#drift-check}

- **比对逻辑**：先比对目标库结构快照指纹与记录指纹（忽略列物理顺序等非结构差异），不同时再将线上结构导入模型并生成差异清单（最多返回前 100 项及总差异数）。
- **检查时机**：每次执行/回滚前自动检查；环境页可随时点击“检查漂移”手动触发；服务端亦支持按 `DOWEL_DRIFT_INTERVAL_MINUTES`（默认 60 分钟，`0` 关闭）定时巡检所有环境，结果缓存于平台库并在导航栏和项目概览标出告警。
- 若环境正在执行或上次迁移停在半途，漂移检查自动跳过；网络不通、权限不足或历史不匹配则会如实标明“检查失败”及原因。

### 保留线上的修改：导入 → 发布 → 标记为已执行 {#drift-keep}

当线上的手工改动需要保留进模型时：

1. 在漂移详情页点击**保留线上的修改**（即“从此库导入结构”），读回目标库结构并按限定名沿用工作副本的对象 ID。提交确认前会展示差异预览并在工作副本有未发布改动、环境落后链头或有未完成迁移时发出警告；确认时校验线上结构指纹和工作副本版本号，防止并发覆盖（409）。
2. 检查导入模型（如手工改名会被识别为先删后加，可在画布调整还原为改名以生成 `RENAME`）。
3. 普通**发布**生成新版本并通过影子库验证。
4. 在环境页点击**标记为已执行**将该环境对齐到新版本，随后其余环境可按正常链执行该版本。

### 放弃线上的修改：修复脚本 {#drift-discard}

当需要撤销线上手工改动时，漂移详情页中的**放弃线上的修改**提供针对“线上结构 → 当前版本模型”生成的**修复脚本**（附带固定会话参数与删表、删列、删约束及类型改写风险提示；模型无法表达的差异归入“需要手工处理”）。

> **Dowel 不会代为执行修复脚本**：该脚本是针对漂移现场临时生成的未验证 SQL。由你在目标库确认并执行后，回到环境页点击“重新检查漂移”（若一次差异超过 100 项，分批执行并重检即可）。

### 标记为已执行 {#mark-as-applied}

**不执行任何 SQL**，在核对目标库实际结构**严格等于**目标链上某个版本 `X` 的模型后，在历史中写入一条 `direction = 'mark'` 记录将环境对齐到 `X`：

- 可向前标记（跳过热修已包含的版本），也可向后标记（手工回退后回指旧版本），甚至在半途失败且手工将库还原后标记回当前版本以解除半途锁定；
- 向前标记时，确认框以服务端实时预演结果为依据，列出所有被跳过的版本和脚本（提示这些脚本与数据步骤不会运行），须勾选确认且在项目锁内再次核对指纹与计划无误后才写入，并将跳过版本的 `executed_at` 标为已执行（向后标记或标记回当前版本不改写未执行版本的可编辑性）；
- 属于特权操作，受环境“谁能执行”档位控制，生产环境需输入环境名，**CI 令牌禁止调用标记操作**。

### 已知限制 {#drift-limits}

- **环境落后于链头且存在漂移时**：若 `prod` 停在 `v5` 并做了热修而链头已到 `v7`，必须先按修复脚本将 `prod` 还原到 `v5` 再升级（或将热修合并入模型后发布 `v8` 并标记）。
- 导入时不做三方自动合并。
