# 执行迁移、回滚与漂移

Dowel 把“发布的版本”变成“真正改动你的数据库”的那一步叫**执行**。本页说明执行的行为、失败后怎么恢复、`dowel` 历史表长什么样、目标库账号需要什么权限，以及什么是漂移。

> 接手现有库（重装 Dowel 后认领同一个库的历史）、审批、执行申请、CI 令牌还没有，后续版本提供。

## 基本概念

- **发布 = 冻结迁移。** 发布版本时，Dowel 从上一个版本生成升级（up）和回滚（down）脚本，在影子库里验证通过后冻结。之后每个环境**沿版本链逐个执行这些冻结的脚本**，不会在执行时临时规划。所以 staging 上验证过的脚本，就是 prod 上执行的那一份。
- **环境**对应一个目标库。每个环境有“当前版本”：目标库的 `dowel` 历史里最后一次成功的执行到了哪个版本。
- **执行**把环境从当前版本沿链升到目标版本；**回滚**沿 down 链降到较早的版本。两者都在环境详情页操作，生产环境要输入环境名确认。

## 目标库账号需要的权限

执行迁移用环境里配置的那个账号（连接串里的账号），它需要：

| 用途                                   | 需要的权限                                                                                                                                                                        |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 执行你的迁移脚本                       | 脚本里每条 DDL 本身需要的权限（对相关 schema 的 `USAGE` / `CREATE`、表的所有者等）。Dowel 不会替你提权，也不会用别的账号                                                          |
| 第一次执行时建 `dowel` schema 和历史表 | 库级 `CREATE` 权限（Dowel 自己建 `dowel` schema）；或者让 DBA 事先执行 `CREATE SCHEMA dowel AUTHORIZATION "<账号>"`，Dowel 就只需要在里面建表                                     |
| 读写 `dowel` schema                    | 对 `dowel` schema 的 `USAGE` 和 `CREATE`，以及表上的读写                                                                                                                          |
| 读结构（漂移检查、执行后读回校验）     | `CONNECT` + 系统目录（默认就能读）；库里已有 `dowel` 历史时，还要对 `dowel` schema 有 `USAGE` 和表的 `SELECT`（要读当前版本）。满足这些的只读账号**能做漂移检查**，但**不能执行** |

没有建 schema 的权限时，Dowel **直接报错并给出需要 DBA 执行的语句**，不会退回到业务 schema 里建历史表。`dowel` schema 的名字固定，不能改。

## 目标库里的 `dowel` 历史

历史固定放在目标库的 `dowel` schema 里。同一个库里的多个项目共用它，表里都带 `project_id`。它只含结构、脚本和执行记录，**没有业务数据**。`dowel` schema 不会被导入，也不参与漂移比较。

| 表         | 内容                                                                                                                                                                                              |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `meta`     | 键值：`format_version`（历史格式的版本）。库里的格式比当前 Dowel 新时，Dowel 拒绝执行并提示升级                                                                                                   |
| `projects` | 每个项目一行：项目 ID、名字、**拥有它的 Dowel 实例的唯一标识**、认领时间。另一个实例不能执行这个项目（认领流程之后提供）                                                                          |
| `versions` | 每个执行过的版本一行：序号 `number`、名字、`parent_id`、冻结的升级 / 回滚脚本（`up_steps` / `down_steps`，`jsonb`）、`checksum`、**完整的模型**（含对象 ID）、结构指纹、发布者和时间              |
| `history`  | 每次执行一行：`from_version` → `to_version`、方向（`baseline` / `up` / `down`）、状态（`running` / `done` / `failed`）、断点 `step_index`、错误信息、执行者、来源（`web` / `ci`）、实例、起止时间 |

要点：

- **`history` 只追加**：触发器禁止删除，只允许改仍在 `running` 的行，且标识字段不能变，已结束（`done` / `failed`）的行不能再改。这是防止误改的保护，不是安全边界——表的所有者和超级用户仍然能删触发器。
- **当前版本** = 最后一条 `done` 的记录的 `to_version`（执行、回滚、基线都一样）；失败和进行中的记录不改变它。
- **`checksum`** 是升级 + 回滚脚本规范化 JSON 的 sha256。每次执行前，Dowel 会按脚本**内容重算**每个版本的校验和，与记录比对；对不上就拒绝（见下面的“完整性检查”）。
- **模型和脚本都存在目标库里**，所以即使平台数据丢了，也能靠它接手这个库（接手功能后续提供）。

## 第一次执行到某个库

目标库里还没有这个项目的历史时，Dowel 先看库里的结构：

| 库里的结构                                                                           | Dowel 做什么                                                                                                      |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| **等于链上第一个版本的模型**（通常是“从这个库导入”的项目，第一个版本是 `v0 · 基线`） | **只写入基线**：建 `dowel` schema、记下这个版本和一条 `baseline` 记录，**不执行任何 SQL**。之后正常执行后面的版本 |
| **空库**（范围内没有任何对象）                                                       | 执行第一个版本的 up，完整建库                                                                                     |
| 其他                                                                                 | 报**漂移**，拒绝执行，并列出“库的结构 → 基线”的差异。**这时 Dowel 不会在你的库里建任何东西**                      |

“空库”指全新的 PostgreSQL 库：只有 `public` schema（PostgreSQL 给它加的默认注释 `standard public schema` 不算差异）。项目设置了 schema 范围时，只看范围内的 schema。

也可以在环境详情页单独点“写基线”：只写历史、不执行，之后再决定什么时候执行。

## 执行

一次执行按下面的顺序检查，**任何一步不通过都会拒绝，且什么都不会改**：

1. **拿项目锁**。同一个项目在同一个库上同时只能有一个执行：另一次执行会等锁，**默认等 30 秒**，超时失败。等到锁之后会重新读取状态——如果前一次已经把环境执行到了目标版本，这一次就什么都不做。
2. **完整性检查**。平台里的版本链和目标库 `dowel` 历史里的版本链都必须完整：序号连续、`parent` 衔接、**每个版本的冻结脚本按内容重算的校验和等于记录值**。两边还要互相一致（目标库历史里的版本都在平台的链上、校验和相同）。有人改了目标库历史里的校验和或脚本，会在这里被发现。
3. **漂移检查**。读目标库的当前结构，与环境当前版本的模型比较，不一致就拒绝（见下面的“漂移”）。读结构用的 schema 范围是**环境当前版本冻结时记录的范围**（第一次执行用第一个版本的），不是项目现在的设置——项目的范围之后改了，旧版本的比较结果不会变。
4. **验证检查**。要执行的每个迁移都必须已经**在影子库里验证通过**（版本页上的“已验证”）。执行前不会重新验证；未验证的版本被拒绝，提示先去“重新验证”。人工改过脚本的版本改完就回到未验证。
5. **实例级语句检查**。迁移里不能有 `CREATE / DROP / ALTER DATABASE`、`TABLESPACE`、`ROLE | USER | GROUP`、`ALTER SYSTEM`，有就拒绝。
6. **逐个迁移执行**，每个迁移执行完都**读回目标库的结构，必须等于目标版本的模型**，否则这个迁移当作失败。

### 事务与非事务步骤

- **没有非事务步骤的迁移是一个事务**：它的历史记录、全部脚本步骤、读回校验和版本记录都在同一个事务里，要么全部提交，要么全部回滚。读回的结构不对时，事务回滚，库保持原样。
- 含**不能放进事务的步骤**（`CREATE INDEX CONCURRENTLY`、`VACUUM`、`REINDEX DATABASE / SYSTEM`、不带表名的 `CLUSTER`、`ALTER TYPE … ADD VALUE` 等）的迁移不是原子的：Dowel 按“一段事务步骤 / 一个非事务步骤”依次执行，**每做完一段就记一个断点**（`history.step_index`），最后一段里做读回校验并结束记录。版本页和环境页会标出这类迁移。
- 执行时用的是与影子库验证时相同的固定会话设置（时区、日期格式、`search_path` 等），所以脚本在目标库上的行为与验证时一致；执行结束后这些设置会被重置，不会留在连接上。

### 回滚

回滚沿 **down 链**逐个执行：从当前版本开始，依次执行当前版本的回滚脚本、再前一个版本的回滚脚本……直到目标版本。规则与执行完全相同（完整性、漂移、验证、实例级语句、读回校验）。第一个版本（基线）没有回滚脚本，不能回滚到它之前。

回滚不会让版本变得“没执行过”：目标库历史里仍然记着它，所以**任何环境上执行过的版本都不能再编辑脚本**（版本页返回 409）。“执行过”是**永久**的：Dowel 在版本自己身上记下第一次执行的时间，只写一次、不会清除——换了环境的连接串、目标库被清空、目标库里的历史被人手工删掉、环境被删除，都不会让它重新变得可以编辑。（只有目标库一点没改动的失败才不算执行过——事务整体回滚、建 `dowel` 历史时权限不足等；Dowel 在第一次对目标库做会留下痕迹的写入之前记下这件事，所以不管失败是什么类型的错误，判断都一样。执行进行中的版本脚本也不能改；Dowel 进程崩溃留下的“进行中”标记，会在下一次读取目标库历史或执行时清掉。事务型迁移是在 `COMMIT` 成功之后才算动过目标库——`COMMIT` 本身失败（比如 DEFERRABLE 约束到提交时才检查）时，库里没有任何变化，版本仍然可以编辑。）

**本进程正在对环境执行时，不能改环境的连接配置（连接串、影子库、是否允许同实例影子库），也不能删除环境**（409，“环境正在执行，稍后再改”；被拒绝的请求不会对任何数据库产生副作用）。如果环境上还留着没收尾的“进行中”标记（Dowel 进程崩溃留下的）而本进程没有在执行，修改**不会被挡住**，按保守方向处理：这些版本当作执行过（永久，不能再编辑），标记删掉，然后照常改连接串或删环境。**这样处理，最坏的结果是一个其实没碰过目标库的版本不能再编辑了，而不会让碰过库的版本又能编辑。**执行开始时，如果等锁期间环境的连接串被改了，执行用的是新连接串；环境被删了就拒绝执行。Dowel 目前只支持**单进程部署**，这些保护和对残留标记的清理都依赖这一点。

## 失败与恢复

- **某个迁移的步骤报错**：停在**最后一个成功的版本**。事务型迁移整体回滚，库里没有留下半个迁移；历史里多一条 `failed` 记录（带错误信息）。修好原因（比如清掉重复数据）后**直接重试**即可。没有任何环境执行成功过、且事务整体回滚的版本，**脚本还可以修改**。
- **含非事务步骤的迁移失败**：已提交的部分**不会回滚**，库处于“半途”状态。历史里这次执行是 `failed`，`step_index` 记着最后做完的一步。第一个非事务步骤执行**之前**，Dowel 先把断点记成 `-1`（“已经开始动目标库，但还没完成任何一步”）：如果它第一步就失败了（比如 `CREATE UNIQUE INDEX CONCURRENTLY` 因为重复数据失败，留下了无效索引），库同样算“半途”，同样从断点续跑，不会被判成漂移。**重试时 Dowel 从断点接着跑**，不会重复执行已经完成的步骤。半途状态下：
  - 漂移检查会跳过（结构既不是旧版本也不是新版本，没法比）；
  - **必须先把这次迁移跑完**，不能改做别的（比如直接回滚会被拒绝，并提示先继续）。
- **`CREATE INDEX CONCURRENTLY` 失败**（比如唯一冲突）会在 PostgreSQL 里留下一个**无效（INVALID）索引**。重试前 Dowel 会自动把它删掉再重建，不需要你手工处理。删除是**精确匹配**的：从语句里解析出索引名和它所在表的 `schema.table`，只删这张表上、同名、状态为 INVALID 的索引——别的 schema 里的同名表、同名索引不会动。语句里的表没写 schema，或者 Dowel 解析不了语句时**不会删除**任何东西，失败信息里会提示你手工 `DROP INDEX CONCURRENTLY` 后重试。
- **进程中途被杀**：事务型迁移的事务会被数据库回滚；含非事务步骤的迁移留下 `running` 记录，下一次执行同样从断点续跑。项目锁是数据库会话级的，进程退出后自动释放。
- **任何意外错误**（读结构失败、schema 范围有问题、连接断开……）：Dowel 先把一条 `failed` 记录写进历史（文本脱敏；写记录本身失败，比如连接已经断了，只记日志、仍然抛出原错误），再把错误报给你。失败记录总是在事务之外写的——事务型迁移回滚后另起一个事务写，不会跟着回滚消失，也不会让这次执行一直停在 `running`。
- **读回校验失败**（执行完的结构与目标版本的模型不一致）：说明脚本和模型对不上（比如人工改过脚本）。事务型迁移整体回滚、记 `failed`；需要修脚本并重新验证。
- **需要人工修正的状态**：含非事务步骤的迁移，**所有步骤都做完了**，读回的结构却不等于目标版本（最后一步是非事务步骤时尤其会这样：它已经提交，没法回滚）。这说明脚本本身的结果就不对，**接着跑解决不了**。这时这次执行记为 `failed`，错误文本以 `[readback_mismatch]` 开头，**不算“停在中途”**，不会续跑，也不会无限重复同样的读回。库停在半途状态，Dowel 的做法是：
  - 漂移检查和执行 / 回滚都把它报成**漂移**，附上与当前版本模型的差异，并说明“这个差异是上一次执行留下的、需要手工修正”；环境页顶部有红色提示条；
  - 你要手工把目标库改回当前版本的样子（差异列表里的 SQL 就是需要做的事），漂移消失后才能再执行；
  - 想继续这个版本，先修脚本（版本没有任何环境“执行过”之前才能改，而这个版本已经动过目标库，所以通常要发布一个新版本来替代它）。等“处理漂移”功能上线后，可以在界面上处理这种状态。
  - **手工修好之后**：把目标库改回**当前版本**的样子（读回失败的那次执行的起点）后，漂移检查返回“无漂移”，红色提示条消失（提示条只在漂移检查的结果仍是“漂移”并且差异是上一次执行留下的时才显示；执行因读回失败的那一刻，漂移状态就会同时刷新成“漂移”，不需要再手动检查一次）。环境的当前版本仍是历史里最后一次成功的版本，**不会**因此认为已经到了目标版本，也不会补写一条记录；历史里那条读回失败的记录还在（历史只追加），只是不再有意义。之后再执行，会从头重新执行那个迁移。如果手工把库改成了**目标版本**的样子，漂移检查是拿它和当前版本比较，所以仍会报漂移——收下这个结果需要“处理漂移”功能（还没有）；现在的办法是改回当前版本，或者发布一个新版本。**Dowel 有意不在“结构恰好等于目标版本”时自动补写一条完成记录**，这个结果留给“处理漂移”。
- 所有错误文本在返回给浏览器、写进审计和写进目标库历史之前都会**脱敏**（连接串里的密码会被遮掉）。

## 漂移

**漂移**指目标库的实际结构与 Dowel 记录的环境当前版本不一致——通常是有人绕过 Dowel 直接在库上 `ALTER` 了东西。执行和回滚在漂移时会被拒绝，因为在一个已经变了样的库上继续执行，结果没法预期。

- **怎么比**：Dowel 读目标库结构，先比**结构指纹**（每次执行时读回结构记下的值，比较时去掉了列的物理顺序等不稳定字段），一样就没有漂移；不一样再把线上结构导入成模型，与当前版本的模型比较，得到差异列表。差异用“**线上结构 → 当前版本模型**”表示：每一项是要让线上结构回到当前版本需要做的一步（类型、对象、SQL）。差异最多显示 100 项，同时显示总数。
- **什么时候检查**：每次执行 / 回滚前都会检查；环境页有“**检查漂移**”按钮手动检查；服务端还有**定时检查**，默认每小时一次，用环境变量 `DOWEL_DRIFT_INTERVAL_MINUTES` 调整（分钟，`0` 关闭）。
- **结果缓存**在平台库的环境上（最近检查时间、状态、差异摘要）。**图标栏的“环境”入口和项目概览页**在有漂移的环境上显示警告。
- 检查时目标库**正在执行**、或上一次执行**停在中途**时会跳过。检查本身失败记为“检查失败”，不算漂移，**文案说明真实原因**：连不上目标库、目标库返回错误（权限等）、目标库历史与平台版本链对不上（完整性）、schema 范围有问题（跨范围引用）、读不了 `dowel` 历史，其他意外错误只在服务器日志里留详情。
- **怎么处理漂移**：把库改回当前版本的样子（差异列表里的 SQL 就是需要做的事），或者把线上的改动补进模型并发布成新版本。（“接受线上结构”还没有提供。）

## 谁能执行

每个环境有一档“**谁能执行**”，在环境详情页设置：

| 档位       | 谁能执行                                     |
| ---------- | -------------------------------------------- |
| 项目编辑者 | 项目编辑者及以上                             |
| 项目管理员 | 项目管理员及以上                             |
| 仅限执行者 | 目前（执行者授权上线之前）**只有实例管理员** |

**默认**：非生产环境是项目编辑者，生产环境是项目管理员。实例管理员不受限制。

这一档约束的**特权操作**有：执行 / 回滚、写入基线、改连接串和影子库设置、取消“生产”标记、改这一档本身、删除环境（处理漂移预留）。其中改连接串、取消生产标记、改档位、删除环境这些配置类操作**另外至少要项目管理员**：档位只会收紧、不会把原本只有管理员能做的事放宽给编辑者。取消“生产”标记时，没有显式设置过档位的环境会把当前生效的档位固定下来，不会悄悄放宽。

**模型的编辑和发布不受这一档约束**，仍然按项目角色。查看者不能执行。

生产环境的执行、回滚、写基线必须在确认对话框里**输入环境名**，服务端也会校验。每次执行都写进审计日志（谁、哪个环境、哪些版本、成功还是失败）。
