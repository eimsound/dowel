# 执行申请与审批

没有权限直接执行的人，或者环境要求审批时，执行和回滚都通过**执行申请**完成：提交申请 → 按环境的审批流程逐个环节审批 → 有执行权限的人执行。本页说明申请的规则、审批怎么走、紧急执行和收件箱。审批流程怎么配置见 [执行策略](execution-policy.md#审批流程)，Webhook 通知见 [组级 Webhook](webhooks.md)。

## 什么时候要提交申请

| 环境的审批流程           | 有执行权限的人                       | 没有执行权限的人                         |
| ------------------------ | ------------------------------------ | ---------------------------------------- |
| 默认（没有配置审批环节） | 直接“执行”                           | 提交申请，由有执行权限的人“通过并执行”   |
| 配置了审批环节           | **也要提交申请**（实例管理员也一样） | 提交申请，审批通过后由有执行权限的人执行 |

环境详情页上，需要申请时“执行”按钮会变成“提交执行申请”（回滚是“申请回滚”）。谁能提交申请：项目编辑者及以上，或者这个环境的执行者。查看者不能提交。

写入基线、标记为已执行不跑迁移脚本，不走审批（仍然受“谁能执行”约束）。

## 提交申请

确认对话框会先做一次**预演**（和直接执行前的检查完全一样：完整性、漂移、认领、已验证……）。**预演不通过不能提交**。可以写一段申请说明。

申请**绑定**提交时的状态：

- 起始版本（提交时环境的当前版本）和目标版本、方向（执行或回滚）；
- 要执行的每个迁移和它的**校验和**；
- 提交时生效的审批流程（快照）；
- 环境的连接设置和“生产”标记。

### 什么时候失效

只要环境的状态变了，申请就**失效**，要重新提交：

- 环境的当前版本变了（有人直接执行了、另一个申请先执行了、回滚了、标记为已执行了）；
- 检测到漂移；
- 链上相关版本的脚本被修改过、版本或目标版本不存在了；
- 环境的连接串或“生产”标记变了；
- 审批流程**变严**了（多了环节、换了环节、人数变了）。流程变宽的，申请按提交时的流程（更严的那份）继续走。

申请还会**过期**：默认 24 小时，可以在执行策略里设得更短（1～720 小时）。

失效和过期都有明确的原因，显示在申请详情页上，并通知申请人。服务端每 30 秒检查一次所有还没结束的申请，环境一有变化（执行、漂移检查、改脚本、改策略……）也会马上检查受影响的那些；审批和执行时还会在锁里再检查一次。**执行时执行器还会在目标库的锁里按目标库自己的历史再核对一遍**起始版本和校验和——即使平台里的缓存落后（比如别的实例执行过），也越不过失效：这时什么都不执行，申请转为失效。

## 审批

- 按环节顺序推进：一个环节凑够人数才进入下一个环节，下一个环节的审批人这时才收到通知。
- **驳回**即结束（必须写意见）。
- 同一个人可以批多个环节，但每个环节要**单独确认**：一次点击只推进一个环节。
- **申请人不能审批自己的申请**（四眼原则：申请人可能本身就在审批人范围里，比如项目管理员申请、审批人是项目管理员）。
- 审批人资格按**审批的那一刻**的成员关系判断：提交之后被移出组、撤掉授权的人不能再批；后来加入的人可以批。看不到这个项目的人不算审批人。
- 当前环节有资格的人数不够时，详情页会提示（需要调整审批流程或授权）。

### 谁来执行

**审批不给执行权限。** 不管流程怎么配置，真正执行的人都要满足这个环境的“谁能执行”（或是执行者）：

- 最后一个环节设了“**最后一个审批人即执行者**”（默认流程也是这样）：凑够最后一个环节的那个人点“**通过并执行**”，通过和执行一次完成；没有执行权限的人在这个位置上不能通过（页面会说明）。
- 没设这个标记：全部通过后，有执行权限的人点“**执行**”——申请人自己有执行权限的话也可以自己执行。没有执行权限的申请人会看到“等待有执行权限的人执行”，有执行权限的人会收到“待你执行”的通知。

生产环境执行时同样要输入环境名。执行失败的申请（例如锁等待超时）在绑定仍然成立时可以“重试执行”；执行到一半、环境当前版本已经变了的，申请会失效，要重新提交。

申请人可以在执行之前**撤回**申请。

## 紧急执行

**只有实例管理员**能紧急执行：在环境详情页点“紧急执行”（回滚是“紧急回滚”）。

- **绕过审批流程**，但**不绕过安全检查**：漂移、完整性、认领、已验证照常检查。
- **必须填写原因**，并勾选确认；生产环境还要输入环境名。
- 写审计，并**通知这个环境审批流程里的所有审批人**（站内收件箱 + 组的 Webhook）：开始时一条，结束时（成功、失败，或者环境状态在检查之后变了、没有执行）再一条。紧急执行在“执行申请”列表里也有一条记录（标明“紧急执行”），详情页能看到原因和结果。
- 紧急执行**失败之后不能在详情页重试**，也不能撤回：要再来一次请重新发起紧急执行（重新填原因、重新检查），或者提交执行申请走审批。

## 收件箱

图标栏的收件箱显示**未读数**，实时更新。收件箱里有三栏：

- **待我处理**：当前环节我能批的申请，以及已经全部通过、等我执行的申请；
- **通知**：待我审批、我的申请结果（通过、驳回、失效、过期、执行成功 / 失败）、紧急执行通知。点开或点“标为已读”标为已读，也可以全部标为已读；
- **我的申请**：我提交过的申请。

只会通知**能看到这个项目的人**；之后看不到了的项目（例如被移出了组）的通知不再显示，**也不计入未读数**；“全部标为已读”只作用于现在看得到的通知，重新看得到时它们仍是未读。

## 审计

提交、审批（每个环节每个人）、驳回、撤回、失效、过期、开始执行、执行结束、紧急执行都写审计日志；申请详情页的时间线就是这些记录。执行本身的审计（`environment.execute` / `environment.rollback`）里带着申请的 ID。

## 已知限制

- 只支持单进程部署：申请的定时检查、收件箱的实时推送、Webhook 队列都在进程内。服务重启时“正在执行”的申请会被记为执行失败（结果以目标库的执行历史为准）。
- 不发邮件通知（站内收件箱 + 组级 Webhook）。
