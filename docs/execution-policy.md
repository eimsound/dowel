# 执行策略、执行者与前置环境

执行策略决定**谁能对一个环境做特权操作**、执行前要走怎样的**审批流程**、迁移在目标库上**最多等多久**。它分四层配置，逐层取更严。本页说明每一项的含义、合并规则、怎么配置、怎么授予执行者，以及前置环境和超时。执行本身见 [执行迁移、回滚与漂移](execution.md)。

## 四层，逐层取更严

| 层   | 在哪里配置                        | 谁能改     |
| ---- | --------------------------------- | ---------- |
| 实例 | 管理后台 → 执行策略               | 实例管理员 |
| 组   | 组首页 → 执行策略                 | 组管理员   |
| 项目 | 项目设置 → 执行策略               | 项目管理员 |
| 环境 | 环境详情 → 执行策略（含前置环境） | 项目管理员 |

- 实例、组、项目三层各有**生产**和**非生产**两套；环境层只有它自己那一套，按环境的“生产”标记合并上级对应的那一套。
- **没有设置 = 继承**。四层都没设置时用默认值。
- **合并 = 逐层取更严**：上级设了的要求，下级只能收紧，不能放宽。下级页面上，上级的要求显示为“由组锁定：至少 项目管理员”这样的标记，比它宽的选项不能选；直接调接口也会被拒绝（422）。
- 每个字段旁边显示**生效值和来源**（来自实例 / 组 / 项目 / 环境，或默认值）。

## 每一项的含义、默认值和“更严”的方向

| 项                   | 可选值                               | 默认（非生产 / 生产）          | 哪个更严                                        |
| -------------------- | ------------------------------------ | ------------------------------ | ----------------------------------------------- |
| 谁能执行             | 项目编辑者 / 项目管理员 / 仅限执行者 | 项目编辑者 / 项目管理员        | 仅限执行者 > 项目管理员 > 项目编辑者            |
| 锁等待超时           | 秒数，0 = 不限                       | 5 秒 / 5 秒                    | **越短越严**，不限最宽                          |
| 语句超时             | 秒数，0 = 不限                       | 不限 / 不限                    | **越短越严**，不限最宽                          |
| 允许 CI 令牌执行     | 允许 / 不允许                        | 允许 / 不允许                  | 不允许更严（CI 令牌在后续版本接入，现在只保存） |
| 执行申请有效期       | 1～720 小时                          | 24 小时 / 24 小时              | **越短越严**                                    |
| 审批流程             | 若干个审批环节                       | 单环节：有执行权限的人直接执行 | 见下面“审批流程”                                |
| 前置环境（仅环境层） | 同项目的另一个环境                   | 不设置                         | 见下面“前置环境”                                |

**谁能执行**：

- **项目编辑者**：项目编辑者、项目管理员，以及执行者。
- **项目管理员**：项目管理员，以及执行者。
- **仅限执行者**：只有被授予“执行者”的用户或组。

实例管理员不受限制。**执行者在任何档位下都能在授权范围内执行**——执行者就是为此单独授权的。

**超时为什么越短越严**：迁移里的 DDL 往往要拿表上的强锁；它在等锁的时候，后面所有访问这张表的业务语句都排在它后面。锁等待越短，迁移越早放弃，对目标库上的业务越安全。所以上级设了 5 秒，下级只能设得更短（或一样），不能设成 30 秒或不限。

**默认值不是下限**：上级什么都没设时，下级可以设得比默认更宽，例如项目管理员可以把某个生产环境设成“项目编辑者能执行”。如果不允许这样做，在组层或实例层显式设置即可。

## 受执行策略约束的操作（特权操作）

执行 / 回滚、写入基线、标记为已执行（处理漂移）、改连接串和影子库设置、取消“生产”标记、删除环境、给已有项目添加环境并接入已有历史。预演和真正的执行权限相同。其中改连接串、取消生产标记、删除环境、接入已有历史这些**配置类操作另外至少要项目管理员**——执行者如果不是项目管理员，只能执行，不能改环境的配置。

**模型的编辑和发布不受执行策略约束**，仍然按项目角色。手动检查漂移需要项目编辑者，执行者也可以。

## 改策略本身：收紧随时可以，放宽是特权操作

- **收紧**（任一项变严、追加审批环节、设置前置环境）：这一层的管理员就能做。
- **放宽**（任一项变宽、删掉审批环节、去掉或换掉前置环境）会削弱环境的保护，算特权操作：除了这一层的管理员，还要**满足这一层改动之前生效的“谁能执行”**。放宽**不需要**走执行申请的审批（审批绑定的是迁移，不是策略）；所有修改都有审计。
- 改策略对**已经提交的执行申请**的影响：流程变严（多了环节、换了环节、人数变了）的，那些申请会失效、要按新流程重新提交；流程变宽的，已提交的申请仍按提交时的流程走完（更严的那份）。

所以一旦某层设成了“仅限执行者”，不是执行者的组管理员 / 项目管理员**不能自己撤掉它**，否则“仅限执行者”就形同虚设。要放宽，请这一层范围内的执行者或实例管理员来改。配置页上会提示这一点。

改“生产”标记也不会悄悄放宽：标记变了，环境用的上级设置就换成另一套；新的一套里比原来宽的项，会把原来的生效值固定成环境层自己的设置。同一次修改里既改生产标记又改“谁能执行”时，按**改动后**的生产标记对应的上级检查。

**项目转组也不会悄悄放宽**：转组换掉了组层的设置，项目里每个环境都用新组的设置重新合并一遍，比原来宽的项同样固定成原来的生效值，写进各环境自己的设置（审计里记下哪个环境固定了哪些项）。之后要放宽，按上面的规则在环境层改。另外注意，**授权跟着范围走**：原组范围的授权（包括原组授予的执行者）对转走的项目不再有效，目标组范围的授权开始有效；转组前请确认执行者在新组里有相应的授权。

同时提交的修改不会互相覆盖：每次修改都在同一个事务里读出当前设置、检查、写入，后到的修改按前一个修改之后的状态判断（例如先有人收紧成“仅限执行者”，另一个人基于旧页面的保存会被当作放宽检查）。

所有修改都写审计日志（哪一层、改动前后的设置、放宽了哪些项、被固定的项）。

## 执行者

**执行者**是被单独授权、可以在某些环境上做特权操作的用户或组，例如 DBA 组。

- 在“成员与授权”页添加授权时选择角色“执行者”，范围可以是**整个项目**或**某一个环境**；组级授权（组的全部项目）和实例级授权（管理后台 → 授权）也可以授予执行者。
- 执行者能**只读**查看授权范围内的项目（环境、版本、脚本），**不会**因此获得模型的编辑权限；需要编辑模型的话另外授予项目角色。同一个用户可以同时有项目角色和执行者授权。
- 谁能授予：和其他授权一样，项目管理员、组管理员、实例管理员按各自的范围授予。**例外**：生效策略为“仅限执行者”的**生产环境**，执行者只能由**实例管理员**授予——
  - 授予到这样的环境上时，非实例管理员在界面上不能选它（并说明原因），接口返回 403；
  - 项目管理员授予的项目级 / 组级执行者，对这样的生产环境**不算数**（对其他环境照常有效）；只有实例管理员授予的才算。授权列表里会标明“实例管理员授予”；
  - 这条规则在每次执行时判断：生产环境之后才收紧成“仅限执行者”，原来由项目管理员授予的执行者在它上面也就自动不算了。

## 前置环境

环境详情 → 执行策略 → **前置环境**：选同一个项目里的另一个环境（不能是自己，不能形成循环）。设了以后：

- **执行**到本环境时，目标版本的序号不能高于前置环境的**当前版本**。前置环境还没执行过任何版本时，本环境一律不能执行。被拒绝时，确认对话框里直接说明原因（例如“前置环境 staging 当前是 v3，目标 v4 比它新”），确认按钮不可用；接口返回 422，代码 `prerequisite_behind`；预演给出同样的代码和说明。
- 看的是前置环境的**当前版本**，不是“曾经执行过”：前置环境回滚了，本环境也就不能再往前。
- **回滚不受约束**：回滚是出问题时的出口，回到的是本环境之前已经到过的版本（当时它满足了这条规则），不应该被“前置环境也得先回滚”卡住。**标记为已执行**和**写入基线**不执行脚本，同样不受约束。这些豁免都写进审计。
- 被别的环境当作前置环境的环境不能删除，先在那个环境里移除前置环境（数据库里也有约束，并发操作同样删不掉）。删除整个项目不受影响。
- 如果设置的前置环境找不到了（正常情况下不会发生），本环境的执行一律拒绝（代码 `prerequisite_missing`），不会当作“没设前置环境”放行；在执行策略里重新选择前置环境即可。
- 去掉或换掉前置环境算放宽（见上）。
- 前置环境的当前版本取自 Dowel 记录的状态（每次执行、读取历史后更新），不实时连前置环境的库。

## 超时：语句超时与锁等待超时

- 执行时，每个迁移会话在执行步骤前设置 PostgreSQL 的 `lock_timeout` 和 `statement_timeout`（生效策略里的值），**事务步骤和不在事务里的步骤都生效**；步骤做完用 `RESET` 恢复，Dowel 自己的读回校验和写历史跑在库端原来的设置上。
- 策略里是“不限”（0）的项**不会去设置**：数据库或账号上已经配置的 `statement_timeout` / `lock_timeout`（`ALTER DATABASE … SET`、`ALTER ROLE … SET`）照常生效，Dowel 不会把它们改成不限。这种由库端配置取消的步骤按普通的失败报告（不是 `step_timeout`）。
- **`CREATE INDEX CONCURRENTLY`、`DROP INDEX CONCURRENTLY`、`REINDEX … CONCURRENTLY`（包括 `REINDEX (CONCURRENTLY) …` 的括号写法）不设锁等待超时**（语句超时照常）：它们只拿不阻塞读写的锁，等的是库里已有的事务结束，排队时不会把业务语句堵在后面——而锁等待超时要防的正是这一点。所以库里有长事务时，这类步骤会一直等到长事务结束，不会因为 5 秒的默认值反复失败、留下无效索引。重试前清理遗留无效索引的那一步也一样。
- **`ALTER TABLE … DETACH PARTITION … CONCURRENTLY` 照常受锁等待超时约束**：它的第二阶段要对分区拿 `ACCESS EXCLUSIVE`，排队时一样会挡住访问这个分区的业务。它的第一阶段提交后（分区已经标成“detach pending”），还要等库里已有的事务结束、再拿锁完成分离——这两段等待都可能超过锁等待超时（库里有长事务时前者更常见）。超时后分区停在 detach pending，**重试时 Dowel 会自动改为执行 `ALTER TABLE … DETACH PARTITION … FINALIZE`** 完成分离（同样受锁等待超时约束，可以反复重试，等长事务结束后就能完成），迁移照常从断点续跑。只有 Dowel 识别不了这条语句（例如表名没写 schema）时，才需要人工在目标库执行 `… FINALIZE`，再按“半途失败后手工补完”的方式处理（手工完成这次迁移剩下的步骤后，用“标记为已执行”）；失败信息里会提示。Dowel 不会自动生成这类语句，它只会出现在人工编辑过的脚本里。
- 某一步因为超时被取消时，失败原因写明是“等锁超过 N 秒（执行策略的锁等待超时）”还是“执行超过 N 秒（执行策略的语句超时）”，错误代码 `step_timeout`，和普通的 SQL 错误区分开。
- 失败后的处理和其他失败一样：事务型迁移整体回滚，稍后直接重试；含非事务步骤的迁移从断点续跑。
- 等项目锁（同一个项目的另一个执行正在进行）是另一回事，仍然是最多等 30 秒，不受这两个超时影响。

## 审批流程

审批流程决定执行（和回滚）之前要经过哪些人同意。怎么提交申请、怎么审批、紧急执行和收件箱见 [执行申请与审批](approvals.md)。

- 一个流程是若干个**审批环节**，每个环节规定审批人范围（项目管理员、项目所属组的组管理员、执行者、指定组的成员、指定组的组管理员、指定用户）和需要几个人批；可以设“最后一个审批人即执行者”（只有最后一个环节上的这个设置生效）。“指定用户”按名字或用户名搜索选择。
- **每一层只能在上级的环节之后追加环节**：生效流程 = 实例、组、项目、环境各层的环节按顺序拼起来。上级的环节在下级显示为锁定，不能删改。所以下级的流程一定包含上级的全部环节（顺序不变）——这就是审批流程的“更严”。
- **都没配置时是默认流程**：有执行权限的人直接执行；没有的人提交执行申请，由有执行权限的人“通过并执行”。
- **配置了环节之后**，执行和回滚都要提交执行申请、按环节审批——**实例管理员也一样**（实例管理员另有“紧急执行”）。写入基线、标记为已执行不跑脚本，不走审批（仍然受“谁能执行”约束）。
- **审批不给执行权限**：真正按“执行”（或“通过并执行”）的人，始终要满足这个环境的“谁能执行”（或是执行者）。所以下级追加的环节只会多加限制，不可能借审批绕过上级的“仅限执行者”。
- 同一个人可以出现在多个环节的审批人范围里（配置页会提示可能重叠的环节），但每个环节要**单独确认**。
- 审批人只算**能看到这个项目的人**：例如要让 DBA 组审批，除了把它写进审批人范围，还要给它执行者或查看者授权。

**执行申请有效期**：申请提交之后多久没执行完就过期（默认 24 小时）。越短越严，上级设了 8 小时，下级只能设得更短。
