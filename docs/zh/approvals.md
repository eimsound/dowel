# 执行申请与审批

当用户没有直接执行权限，或环境配置了审批流程时，执行和回滚均通过**执行申请**完成：提交申请 → 按审批流程逐环节审批 → 有执行权限的人触发执行。关于四层策略合并规则与审批流程配置见 [执行策略与执行者](execution-policy.md#approval-flow)，通知集成见 [组级 Webhook](webhooks.md)。

## 何时需要提交申请 {#when-to-request}

| 环境的审批流程配置       | 有执行权限的人                           | 没有执行权限的人                             |
| ------------------------ | ---------------------------------------- | -------------------------------------------- |
| 默认（未配置审批环节）   | 直接点击“执行” / “回滚”                  | 提交申请，由有执行权限的人“通过并执行”       |
| 配置了一个或多个审批环节 | **同样必须先提交申请**（实例管理员亦同） | 提交申请，全部环节通过后由有执行权限的人执行 |

需要走申请流程时，环境详情页的动作按钮显示为“提交执行申请”或“申请回滚”。**项目编辑者及以上**或拥有该环境**执行者**权限的成员可以提交申请，查看者不能提交。写入基线和[标记为已执行](execution.md#mark-as-applied)不运行业务 DDL，不走审批，但仍受“谁能执行”档位约束。

## 提交与绑定失效 {#submit-and-invalidation}

打开申请确认框时会自动触发一次完整的[预演](execution.md#dry-run)，**预演不通过不能提交申请**。提交时可附带申请说明，申请会锁定以下快照绑定状态：

- 起始版本（提交时环境的当前版本）、目标版本与操作方向（执行或回滚）；
- 路径上每个迁移的 `checksum`；
- 提交时环境生效的审批流程快照；
- 环境的连接配置指纹与“生产”标记。

### 什么情况会导致申请失效 {#invalidation-reasons}

只要环境的底层状态在申请完成前发生变化，申请会自动标记为**失效**并通知申请人：

- 环境的当前版本发生变化（其他申请或 CI 令牌先执行了、手工执行或回滚了、标记为已执行了）；
- 检测到线上漂移；
- 待执行链路中的脚本被编辑或目标版本变更；
- 环境的连接串或“生产”标记被修改；
- 审批流程被**收紧**（新增了环节、调整了条件或提高了审批人数；若流程被放宽，已提交的申请仍按提交时的较严流程继续执行）。

此外，申请会在超过策略设定的有效期（默认 24 小时，可在 `1`–`720` 小时内逐层收紧）后自动**过期**。

服务端通过分布式巡检周期校验未完结申请，同时在执行、漂移检查、改脚本、改策略等事件后即时重检。最终触发执行时，执行器还会在目标库项目锁内再次核对目标库真实的当前版本与各迁移校验和，确保不会基于过期缓存跳过失效校验。

## 审批与执行交接 {#approval-and-handover}

- **逐环节顺序推进**：每个环节达到要求通过人数后才解锁下一环节并向下一环节审批人发送通知；任意环节**驳回**（须填写意见）即结束申请。
- **四眼原则与逐环节确认**：**申请人不能审批自己的申请**，即使申请人自身属于某环节审批人范围；同一个审批人出现在多个环节时，一次点击只确认当前环节。
- **按审批时刻动态判定资格**：审批权限依据操作当下的成员关系、授权与项目访问权限判断。
- 若当前环节因成员调整导致有资格的人数不足要求人数，详情页会发出提示，需管理员调整授权或审批流程。

### 由谁触发最终执行 {#who-triggers-execution}

**审批通过本身不授予执行权**，实际按下“执行”或“通过并执行”的操作者必须满足该环境的“谁能执行”要求（或为执行者）：

- **启用了“最后一个审批人即执行者”**（默认单环节流程即如此）：当最后一个环节需要最后一个名额时，操作者点击**“通过并执行”**一次性完成最终审批并开始执行；没有执行权限的审批人在此位置无法执行，页面会提示由有执行权限的审批人接手。
- **未启用该选项**：全部审批环节通过后，申请进入“待执行”状态，由拥有执行权限的人点击**“执行”**（若申请人自身具备执行权限也可触发）。

生产环境执行时同样需要输入环境名称。若执行中途因锁等待超时等可恢复原因失败，只要绑定的状态仍然有效即可在申请页“重试执行”；若环境当前版本已被改写则转为失效。执行尚未开始前，申请人可随时**撤回**申请。

## 紧急执行 {#emergency-execution}

在生产突发事件等需要跳过审批的场景下，**只有实例管理员**可以在环境详情页发起**紧急执行**（或紧急回滚）：

- **只绕过审批流程，绝不绕过安全检查**：项目锁、版本完整性、实例认领、漂移检测与迁移已验证要求照常强制生效；
- 必须填写紧急原因并勾选确认（生产环境还需输入环境名称）；
- 记录专用审计日志，并在执行开始与结束（成功、失败或因状态变更未执行）时通过站内收件箱和组级 Webhook **通知该环境审批流程中的所有审批人**；
- 紧急执行记录在申请列表可见并标有“紧急执行”标识。失败的紧急执行**不支持重试或撤回**，需重新核对状态并重新发起一次紧急执行（或提交常规申请）。

## 收件箱与审计 {#inbox-and-audit}

顶部或侧栏收件箱图标实时显示未读角标（外部 PostgreSQL 多副本 HA 下通过 `LISTEN/NOTIFY` 跨副本同步推送至 SSE 连接）：

- **待我处理**：当前轮到自己审批的申请，以及审批已全部通过、等待自己触发执行的申请；
- **通知**：新的待审批提醒、本人提交申请的状态变更（通过、驳回、失效、过期、执行成功/失败）、紧急执行通知，以及**生产环境的 CI 令牌执行通知**（仅在产生实际变更或执行失败时发给项目管理员与该环境审批流程审批人；非生产环境、无变更空跑、预演与预检拒绝不发，见 [CI HTTP API](api.md#execution-rules)）；
- **我的申请**：本人发起的所有申请记录。

只推送和计入当前用户**有权查看**的项目通知；若某人后续失去了项目访问权，对应通知不再显示且不计入未读数。提交、各环节审批、驳回、撤回、失效、过期、开始与结束执行、紧急执行均完整记入审计日志并在申请时间线中展现。

## 已知限制 {#limitations}

- 多副本 HA 架构说明（包括无 Redis 共享、队列持久化与崩溃副本租约超时回收执行中申请）见 [部署与配置](deployment.md#ha)。
- 不内置邮件（SMTP）通知，请使用站内收件箱或对接[组级 Webhook](webhooks.md)。
