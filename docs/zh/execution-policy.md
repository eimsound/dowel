# 执行策略与执行者

执行策略决定**谁能对某个环境执行特权操作**、执行前要经历怎样的**审批流程**，以及迁移语句与锁等待**最多等多久**。策略分四层配置，逐层只能收紧不能放宽。执行流程见 [执行迁移、回滚与漂移](execution.md)。

## 四层配置与合并规则 {#policy-layers}

| 层级 | 配置位置            | 谁能修改   |
| ---- | ------------------- | ---------- |
| 实例 | 管理后台 → 执行策略 | 实例管理员 |
| 组   | 组首页 → 执行策略   | 组管理员   |
| 项目 | 项目设置 → 执行策略 | 项目管理员 |
| 环境 | 环境详情 → 执行策略 | 项目管理员 |

- 实例、组、项目三层均分别维护**生产环境**与**非生产环境**两套规则；环境层只有自身一套规则，根据环境的“生产”标记自动继承对应上级的规则组。
- **未设置即继承**，四层均未配置时使用默认值。配置界面在每一项旁边都会显示**当前生效值及其来源层**。
- **逐层只收紧不放宽**：任一上级配置了更严的限制后，下级界面会将其标注为锁定，不能选择更宽的值，直接调用接口也会被拒绝（422）。

## 配置项、默认值与收紧方向 {#policy-items}

| 策略项           | 可选值                               | 默认（非生产 / 生产）          | 收紧方向（更严）                     |
| ---------------- | ------------------------------------ | ------------------------------ | ------------------------------------ |
| 谁能执行         | 项目编辑者 / 项目管理员 / 仅限执行者 | 项目编辑者 / 项目管理员        | 仅限执行者 > 项目管理员 > 项目编辑者 |
| 锁等待超时       | 秒数，`0` = 不限                     | `5` 秒 / `5` 秒                | **越短越严**，不限最宽               |
| 语句超时         | 秒数，`0` = 不限                     | 不限 / 不限                    | **越短越严**，不限最宽               |
| 允许 CI 令牌执行 | 允许 / 不允许                        | 允许 / 不允许                  | 不允许更严                           |
| 执行申请有效期   | `1`–`720` 小时                       | `24` 小时 / `24` 小时          | **越短越严**                         |
| 审批流程         | 若干顺序审批环节                     | 单环节（有执行权限者直接执行） | 只能在上级末尾追加环节               |

- **谁能执行**：选择“项目编辑者”包含项目编辑者、项目管理员和执行者；“项目管理员”包含项目管理员和执行者；“仅限执行者”只允许被授予执行者权限的用户或组。**实例管理员不受此项限制**。
- **默认值不是下限**：只要上级没有显式设定，下级仍可自由设置比默认更宽的规则（例如在未锁定生产策略时把单个生产环境设为项目编辑者可执行）。
- **允许 CI 令牌执行**：CI 令牌执行（见 [CI HTTP API](api.md)）只看这一项，**不受“谁能执行”和审批流程约束**。非生产环境默认允许，所以把非生产收紧（“谁能执行”改为项目管理员或仅限执行者、或配置了审批环节）而这一项仍为“允许”时，被允许创建 CI 令牌的成员仍可签发令牌免审批向前执行。配置页会在非生产那一套底部提示这一点，有修改权限的人可以一键把它设为“不允许”（只改正在编辑的内容，保存执行策略后生效；关掉令牌执行属于收紧，不受上级锁定影响）。默认值不变：需要 CI 自动部署的团队可以保留它。

## 受策略约束的特权操作 {#privileged-ops}

以下操作统称**特权操作**：

- 执行、回滚与[标记为已执行](execution.md#mark-as-applied)（含预演）；
- 修改连接串与影子库配置、取消环境的“生产”标记、删除环境；
- [给已有项目添加环境并接入已有历史](takeover.md#attach-existing)。

其中修改连接串、取消生产标记、删除环境和接入已有历史等配置类操作**另外至少要求项目管理员角色**——单纯拥有执行者授权但不是项目管理员的人，只能执行迁移而不能更改环境配置。模型的编辑、发布与手动漂移检测按项目角色判断，不受执行策略约束。

## 修改策略本身与转组保护 {#changing-policy}

- **收紧策略**：当前层的管理员（实例 / 组 / 项目管理员）随时可以直接收紧策略或追加审批环节。
- **放宽策略**：将任一项改宽或删减审批环节会削弱环境防护，属于特权操作——除了当前层管理员权限外，修改者还必须满足**修改前生效的“谁能执行”规则**（放宽本身不走审批申请，但写入审计日志）。例如已设成“仅限执行者”的环境，非执行者的项目管理员无法自行取消，须由授权内的执行者或实例管理员调整。
- **取消“生产”标记**：环境的“生产”标记取消时，所继承的上级策略会从生产套切为非生产套；对于新套规则中比原有生效值更宽的项，系统自动将原先的生效值固化写入该环境自己的环境层设置，确保不会静默放宽。
- **项目转组**：项目转移到另一个组时，各环境按新组的规则重新合并，比原生效值更宽的项同样自动固化到环境层（转组前请注意检查执行者在新组范围是否依然有效）。
- **并发与已有申请**：所有策略保存均在事务内重新读出当前设置并校验，不会因页面过时而静默放宽。流程变严会导致处于等待中的执行申请立即失效，流程变宽时已提交的申请仍按提交时的较严流程走完。

## 执行者 {#executors}

**执行者**是可以绕开项目角色限制、在授权范围内执行特权操作的用户或组（例如 DBA 组）。

- 可在项目“成员与授权”、组首页或管理后台，在“环境 / 单个项目 / 组的全部项目 / 全实例”四种范围授予用户或组“执行者”角色。
- 执行者自动具备对应范围的只读查看权限（不可编辑模型；如需编辑模型可另行授予项目角色）。
- **生产环境收紧保护**：当某个生产环境的生效“谁能执行”为“仅限执行者”时，**只有实例管理员能向其授予执行者**。此前由项目管理员或组管理员在项目级/组级授予的执行者，在该生产环境下自动不生效（授权列表会注明“由实例管理员授予”）。

## 超时：语句超时与锁等待超时 {#timeouts}

执行或回滚每个迁移步骤前，执行器根据环境生效策略的设置，在目标数据库会话上应用锁等待超时与语句超时，步骤结束后立即恢复会话默认值（Dowel 自身的读回校验与写历史不受此超时限制）。策略中设为“不限（`0`）”的项不会覆盖数据库或角色本身的默认配置。

| 方言       | 锁等待超时机制                                                                                           | 语句超时机制                                         |
| ---------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| PostgreSQL | `SET lock_timeout = <ms>`（`CREATE/DROP INDEX CONCURRENTLY` 与 `REINDEX … CONCURRENTLY` 不设，见下说明） | `SET statement_timeout = <ms>`                       |
| SQLite     | `PRAGMA busy_timeout = <ms>`                                                                             | 无服务端语句超时（仅锁等待受控）                     |
| MySQL      | `SET SESSION lock_wait_timeout = <秒>`（毫秒按秒向上取整，至少 1 秒）                                    | `SET SESSION max_execution_time = <ms>`              |
| SQL Server | `SET LOCK_TIMEOUT <ms>`（错误号 `1222` 识别为超时）                                                      | 由驱动在超过 `<ms>` 后主动取消请求（`req.cancel()`） |

PostgreSQL 特殊处理说明：

- **`CONCURRENTLY` 建/删/重建索引不设 `lock_timeout`**：`CREATE INDEX CONCURRENTLY`、`DROP INDEX CONCURRENTLY` 与 `REINDEX … CONCURRENTLY` 不阻塞正常业务读写，仅等待存量长事务结束，因此保留 `statement_timeout` 而豁免默认的 5 秒锁等待限制（重试前清理无效索引同理）。
- **`DETACH PARTITION … CONCURRENTLY` 照常受 `lock_timeout` 约束**：因其第二阶段会申请强锁阻塞读写，若超时停在 `detach pending`，重试时 Dowel 自动转为执行 `ALTER TABLE … DETACH PARTITION … FINALIZE`。

因策略超时取消的步骤返回错误码 `step_timeout`（日志会写明超时种类与设定秒数），事务型迁移整体回滚后可直接重试，非事务与 MySQL 迁移从断点续跑。等到项目锁本身的上限固定为 30 秒，不受上述策略影响。

## 审批流程 {#approval-flow}

审批流程规定执行和回滚迁移之前须依次经由哪些人同意（提交审批与收件箱详情见 [执行申请与审批](approvals.md)）：

- 每个**审批环节**配置审批人范围（项目管理员、项目所属组的组管理员、执行者、指定组的成员、指定组的组管理员或指定用户）和所需审批人数；最后一个环节可开启“最后一个审批人即执行者”。
- **分层追加合并**：最终生效审批流程 = 实例层 → 组层 → 项目层 → 环境层的所有环节依次拼接。上级环节在下级显示为锁定，不可删改。
- **未配置环节时**：使用默认单环节规则——有执行权限的人直接点“执行”，无执行权限的人提交申请后由有执行权限的人“通过并执行”。
- **配置了任意环节后**：除[标记为已执行](execution.md#mark-as-applied)（不跑脚本，仍受“谁能执行”限制）外，所有执行和回滚均必须走审批流程，**实例管理员同样受约束**（应急场景除外，可使用[紧急执行](approvals.md#emergency-execution)）。
- **审批不授予执行权限**：最终执行者或“通过并执行”的人始终必须同时满足环境的“谁能执行”或具备执行者授权。同一个人即使出现在多个环节中也需逐个单独确认，且仅能看到本项目的用户才计入有效审批人。
