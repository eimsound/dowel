# 接手现有项目与灾难恢复

目标库里的 `dowel` 迁移历史（PostgreSQL 与 SQL Server 存储在 `dowel` schema，SQLite 与 MySQL 存储在同库 `dowel_` 前缀表）保存着每个已发布版本的完整模型（含对象 ID）和冻结脚本。只要目标库还在，就能重新恢复出平台项目——无论换了新的 Dowel 实例、平台数据库损坏丢失，还是同一个库曾被另一个实例管理。

## 在向导里接手现有项目 {#takeover-wizard}

在新建项目向导（`/new`）选择项目方言，并在“初始内容”选择**接手现有项目**：

1. **填连接串**：可以一次提供同一项目的**多个环境**（例如 `dev` 与 `prod`）。Dowel 只读检查每个库，列出已登记在目标库历史里的项目名称、版本数量、最新版本与当前版本、最近一次执行时间，以及当前认领它的实例 ID。
2. **选定项目**：Dowel 在平台库新建项目，并**沿用目标库里的项目 ID**（目标库历史按项目 ID 存储）。若本实例已经存在同一项目 ID，不能重复接手（如需为其补充环境，请使用下面的[给已有项目添加环境并接入已有历史](#attach-existing)）；若该已存在项目对当前用户不可见，服务端只返回“已存在，请联系管理员”，不泄露名称与归属。
3. **确认认领（如由其他实例认领）**：若目标库中的项目当前由另一个 Dowel 实例认领，必须由**本实例的实例管理员**确认“认领”。确认后会告知后果：原实例之后再向这些目标库执行会被拒绝（只读的漂移检测和读历史不受影响）。普通组管理员只能接手尚未被其他实例认领的历史；若认领者本来就是本实例，无需再确认认领。
4. **创建恢复**：接手等价于新建项目，需要拥有目标组的建项目权限。

## 恢复哪些内容 {#what-is-restored}

- **完整版本链与对象 ID**：原样恢复版本 ID、序号、父版本、`model`（保留全部稳定对象 ID 与名称锁定状态）、冻结的 `up_steps` / `down_steps`、`checksum`、冻结时的 `scope`（schema 范围）以及发布时间。接手后在模型里继续改表名或列名，仍会生成 `RENAME` 而非删建。
- **工作副本与范围**：工作副本设为链头版本的模型，项目的 schema 范围设为链头版本的 `scope`。
- **各环境的当前版本与执行记录**：每个环境的当前版本设为各自目标库历史里最后一条 `done` 记录到达的版本，同时写上各环境已执行版本的历史与“已执行”保护（防止已执行版本的脚本被修改）。
- **接手后漂移检测**：恢复完成后立刻为每个环境执行一次漂移检测。**接手本身不会自动修改目标库或处理漂移**，若目标库当前结构与自身当前版本不一致，接手后在环境页按常规[漂移处理流程](execution.md#drift)处理。
- **认领发生在平台写入之后**：平台项目先建好，再到各目标库加锁校验并写入认领记录。如果部分环境认领失败（例如数据库账号无写 `dowel` 权限）或读取期间原实例又往前执行了新版本，已建好的项目仍保留并输出警告：前者可在环境页补全权限后重试认领，后者需删除项目后重新接手。

## 接手前强制影子库验证 {#forced-shadow-verify}

在向平台数据库写入任何恢复数据之前，Dowel 必须用本实例的影子库按版本链顺序（`v0 → v1 → … → vN`）对合并后的**整条历史链**完成闭环验证：

- SQLite 项目直接采用内置 `:memory:` 影子库完成校验；
- PostgreSQL、MySQL 与 SQL Server 项目支持在向导里为环境指定独立影子库连接串，或勾选“允许在同一实例上建影子库”（生产环境默认禁止同实例）；
- 若找不到可用影子库，或链上任意版本的升级/回滚闭环验证失败，**直接拒绝接手**（不写平台库，也不认领目标库），并指明失败的版本号与具体原因；
- 全部验证通过后，恢复入库的每个版本都会记录 `verified_at` 与验证报告，并标明“接手恢复”来源，后续可直接执行或回滚。

## 什么时候拒绝接手 {#takeover-rejection}

存在以下任一问题时，接手会在写库与认领之前直接拒绝并给出原因：

- 单个环境内部历史不完整：版本号不连续、`parent_id` 断链，或按脚本内容重算的 `checksum` 与记录不匹配；
- 同一个版本 ID 在不同环境里的内容（`checksum`、模型、序号、父版本、名称、schema 范围）不一致；
- 多环境版本链存在分叉（同一父版本下出现不同子版本，或链起点不同）；
- 提供的目标库中没有该项目的迁移历史，或历史格式版本高于当前 Dowel 支持版本；
- 找不到可用影子库，或任意版本闭环验证失败。

## 多环境合并规则 {#multi-env-merge}

接手多个环境时，Dowel **按版本 ID 将各环境历史合并为同一条链**。链不能分叉，同一版本 ID 必须完全一致，但**允许环境进度一前一后**（例如 `dev` 已到 `v3`、`prod` 停在 `v2`）。接手后的项目版本链取最长的 `v0～v3`，`dev` 当前版本记为 `v3`、`prod` 记为 `v2`，`v3` 对 `prod` 显示为待执行。

## 给已有项目添加环境并接入已有历史 {#attach-existing}

向已有项目添加新环境（例如挂载由生产备份恢复出的数据库或曾由另一实例管理过的库）时，如果该目标库里已经存有同项目 ID 的历史记录，Dowel 会将其接入：

- **权限要求**：属于[特权操作](execution-policy.md#privileged-ops)，至少需要项目管理员且满足该环境的“谁能执行”档位。
- **与平台版本链比对**：该环境历史必须与平台链**一致**，或者属于平台链的**严格领先延伸**（包含平台链全部版本且末尾多出 1 个或多个连续版本，无分叉）。有分叉或任一既有版本内容不同时拒绝接入。
- **目标库严格领先于平台链时**：
  1. 以原平台链头模型为基线，按顺序在影子库中逐个闭环验证所有领先版本；找不到可用影子库或验证失败时直接拒绝接入；
  2. 验证通过后，将领先版本补全进平台链（附带验证报告与“接手恢复”标记）并推进工作副本到新链头。若当前工作副本存在未发布的修改，接入前会展示覆盖画布前后的差异对比与领先版本列表供确认（覆盖前的状态仍保留在[画布修改历史](modeling.md#canvas-history)中）。
- **认领与顺序**：若目标库由其他实例认领，须由**实例管理员**确认认领；环境先入库再执行认领与状态同步，认领失败或同步失败会作为警告返回，可在环境页完善连接权限后重试认领。若库中并无本项目的历史记录，则按普通新环境添加。

## 灾难恢复 {#disaster-recovery}

当平台数据库损毁且没有备份，或重装 Dowel 导致 `instance_id` 变化时，只要目标数据库仍在：

1. 部署并初始化新的 Dowel 实例（配置 `DOWEL_SECRET`，通过 `/setup` 或无人值守环境变量创建首个实例管理员）。
2. 实例管理员使用[新建项目向导](#takeover-wizard)，选择对应的方言并点**接手现有项目**，输入项目下所有已知环境的连接串（以及所需的影子库连接串或允许同实例选项），选择列表中检出的项目。
3. **确认认领**：即使是从原机器重装，因为新实例的 `instance_id` 已改变，系统也会提示需要实例管理员确认认领。通过后，Dowel 完成整条历史链的影子库闭环验证并重建平台项目，同时通知目标库拒绝对旧实例继续放行执行。
4. 在项目页面核对恢复出的版本链、各环境当前版本与最新漂移检查结果，即可继续建模、发布和执行。

### 灾难恢复的数据边界 {#dr-data-scope}

- **会丢失的内容（仅存在于平台库的数据）**：工作副本中尚未发布的修改、画布节点位置与分组布局、平台用户、组与权限授权（接手人成为项目管理员，其余成员需重新授权）、平台审计日志、项目设置以及各环境的策略档位与生产标记（接手时在向导中重新配置）。
- **不会丢失的内容**：全部已发布的版本（完整模型、稳定对象 ID、推导/锁定名称、冻结的升级与回滚脚本）以及各目标库内的历史执行记录。
